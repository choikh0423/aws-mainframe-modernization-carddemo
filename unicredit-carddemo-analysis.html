System Overview and Processing Architecture

CardDemo is a comprehensive mainframe credit-card management system built to simulate real-world card-issuer operations. It manages the full lifecycle of credit-card accounts—from customer on-boarding and card issuance through transaction processing, billing, and reporting. The system operates in dual processing modes:

  • Online (CICS) — interactive terminal sessions for account inquiries, updates, card management, and user administration.
  • Batch (JCL) — nightly cycle for transaction posting, interest calculation, statement generation, and file maintenance.

1.4 Component Interaction Patterns

  • CICS XCTL — primary navigation between screens (e.g., COSGN00C → COMEN01C → COACTVWC). No return; each program owns the terminal until it transfers.
  • COMMAREA-based — all inter-program data passing uses the COMMAREA (copybook COCOM01Y), carrying user context, flags, and screen state across pseudo-conversational cycles.
  • Batch CALL — batch programs use static CALL for subroutines (e.g., CBTRN02C calls date-conversion utilities).
  • MQ async — authorization requests (COPAUA0C) use MQ put/get with correlation IDs for request-response pattern.
  • Online-to-Batch — CLOSEFIL/OPENFIL JCL jobs hand VSAM file control between CICS and batch.

1.5 Error Handling and Recovery Patterns

  • CICS programs check RESP / RESP2 codes after every EXEC CICS command and route to error-display paragraphs.
  • VSAM file-status codes are evaluated in both online and batch programs; non-zero statuses trigger user messages or job abends.
  • Batch JCL uses COND codes for step-level conditional execution; POSTTRAN verifies record counts before posting.
  • Signon program (COSGN00C) validates user credentials against USRSEC VSAM file and locks after repeated failures.

4.2 VSAM File I/O Patterns

  • READ — direct keyed reads via EXEC CICS READ FILE with RIDFLD pointing to working-storage key fields.
  • BROWSE — STARTBR / READNEXT / ENDBR pattern for list screens (COTRN00C, COCRDLIC, COUSR00C).
  • REWRITE — UPDATE mode read followed by REWRITE for account/card/user updates.
  • WRITE — new record insertion for transaction add (COTRN02C) and user creation (COUSR01C).
  • DELETE — keyed delete for user removal (COUSR03C).

4.3 MQ Message Contracts (Optional Module)

  • Authorization Request — MQ PUT to authorization queue with card number, amount, and merchant data; response via correlation-ID-matched GET.
  • System Date Inquiry (CDRD) — lightweight MQ request/response for current mainframe date.
  • Account Inquiry (CDRA) — MQ-based account details retrieval for distributed consumers.

5.2 Naming Conventions

  • Online programs: CO<func><seq>C (e.g., COSGN00C, COTRN01C)
  • Batch programs: CB<func><seq>C (e.g., CBTRN02C, CBACT04C)
  • Copybooks: CV<entity><seq>Y for data records; CO<xxx>Y for communication; CS<xxx>Y for system
  • BMS maps: CO<func><seq> matching their parent program
  • CICS transactions: 4-char codes — CC00 (sign-on), CM00 (menu), CA/CU/CT/CR/CB (functional)

5.3 Paragraph Structure Pattern

All online COBOL programs follow a consistent paragraph pattern:

MAIN-PARA.
    EVALUATE TRUE
      WHEN CDEMO-PGM-REENTER = 'N'   →  SEND-MAP (first display)
      WHEN CDEMO-PGM-REENTER = 'Y'   →  RECEIVE-MAP → PROCESS-INPUT
    END-EVALUATE.
    EXEC CICS RETURN TRANSID(ws-txn) COMMAREA(ws-comm) END-EXEC.

SEND-MAP.             -- Format and SEND BMS map
RECEIVE-MAP.          -- RECEIVE BMS map data
PROCESS-INPUT.        -- Validate, read VSAM, update, route
RETURN-TO-PREV-SCREEN.-- XCTL back to calling program
SEND-PLAIN-TEXT.      -- Error message display
ABEND-ROUTINE.        -- Handle unexpected failures

Security Implementation Details

7.1 Application-Level Security

  • Authentication: COSGN00C validates user/password against the USRSEC VSAM file (CSUSR01Y copybook).
  • User Types: SEC-USR-TYPE = 'A' (Admin) grants access to CA00/CU00-03; 'R' (Regular) restricts to standard functions.
  • Session Management: User context flows via COMMAREA across all pseudo-conversational cycles; session ends on sign-off or terminal disconnect.
  • Default Credentials: ADMIN001/PASSWORD (admin), USER0001/PASSWORD (regular) — loaded via DUSRSECJ job.

7.2 RACF / External Security

  • Dataset-level access rules protect VSAM clusters and JCL libraries under HLQ AWS.M2.
  • CICS transaction security can be layered via RACF TCICSTRN class.
  • Program access authorization via RACF PROGRAM class for sensitive batch programs.

7.3 Sensitive Data Handling

  • Card numbers (PAN) stored in plain text across VSAM files — modernization candidate for tokenization.
  • CVV codes stored in CARD-RECORD — should be excluded from non-authorization flows.
  • SSN stored in customer record — encryption-at-rest recommended for production.
  • Passwords stored in cleartext in USRSEC file — hashing recommended for modernization.
Modernization Note: PCI-DSS compliance requires PAN tokenization, CVV exclusion from storage, and encryption of sensitive PII. These are high-priority items in any migration assessment.

File and Database Design

8.1 VSAM Design

  • All primary files are KSDS (Key-Sequenced Data Sets) with fixed-length records.
  • TRANSACT file has an Alternate Index (AIX) defined via TRANIDX job for secondary access paths.
  • CLOSEFIL/OPENFIL jobs manage VSAM file sharing between CICS (online) and batch windows.
  • IDCAMS REPRO is used for bulk data loads from sequential datasets.

8.2 DB2 Design (Optional Module)

  • Transaction type and category reference tables managed via DB2.
  • CREADB21 job creates the database schema and loads initial data via DSNTEP4.
  • TRANEXTR job uses DSNTIAUL to unload DB2 data into sequential files for VSAM loading.
  • Online DB2 access via embedded SQL in COTRTUPC and COTRTLIC programs.

8.3 IMS DB Design (Optional Module)

  • Hierarchical database for pending authorization data (DBPAUTP0, DBPAUTX0).
  • PSB definitions (PSBPAUTB, PSBPAUTL) control program access to IMS segments.
  • Batch unload/reload procedures for IMS data migration testing.

8.4 GDG Management

  • DEFGDGB job defines Generation Data Group bases for transaction backups.
  • DEFGDGD extends GDG definitions for DB2-related datasets.
  • GDG provides automatic versioning of backup datasets for rollback capability.

Performance and Capacity Analysis

12.1 Batch Window Analysis

  • Critical path: CLOSEFIL → POSTTRAN → INTCALC → COMBTRAN → CREASTMT → OPENFIL
  • Parallelization opportunities: ACCTFILE, CARDFILE, CUSTFILE, XREFFILE can run concurrently after CLOSEFIL.
  • Bottleneck: POSTTRAN (CBTRN02C at 1,030 LOC) — processes all daily transactions sequentially.
  • WAITSTEP job uses COBSWAIT (assembler) for configurable inter-step delays.

12.2 CICS Performance Considerations

  • COACTUPC (4,236 LOC) is the most complex online program — account update with extensive input validation.
  • Pagination in COTRN00C and COCRDLIC uses VSAM BROWSE (STARTBR/READNEXT) which may degrade with large datasets.
  • All transactions are pseudo-conversational, minimizing CICS region resource holding.

Testing Strategy and Test Cases

13.1 Unit Testing

  • Individual COBOL programs tested with sample VSAM data loaded via IDCAMS REPRO.
  • Test data provided in app/data/ASCII/ (portable) and app/data/EBCDIC/ (mainframe-native).

13.2 Integration Testing

  • Full batch cycle execution: CLOSEFIL → all loads → POSTTRAN → INTCALC → COMBTRAN → CREASTMT → OPENFIL.

  • MQ integration: end-to-end authorization request-response with IMS and DB2 (optional module).

13.3 Regression Testing

  • SUPERC comparison of VSAM file snapshots before/after batch runs.
  • BMS screen capture comparison for all online transaction flows.
  • CBEXPORT/CBIMPORT utilities enable data round-trip validation for migration testing.
