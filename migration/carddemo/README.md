# CardDemo — consolidated application

One Spring Boot backend (`backend/`) and one React app (`frontend/`) for the whole CardDemo estate.
This directory is the foundation the ~16 parallel stream-migration sessions build on: the schema, the
shared services, the sign-on/menu shell and the conventions below are already in place, and the streams
add code **only** in the places this document reserves for them.

`migration/transaction-management/**` stays as the v1 reference of the Transaction Management stream.
The live code for that stream is here, under `com.carddemo.transaction` and `frontend/src/pages/transaction`.

---

## 2. Schema (already complete — do not redefine these tables)

`V1__baseline_carddemo_estate.sql` creates the whole estate from the copybooks, DCLGEN members and DBDs.
Column names, lengths, signs and decimal scales follow the PICs; do not change them.

| Table | Source | Table | Source |
| --- | --- | --- | --- |
| `accounts` | ACCTDAT / `CVACT01Y` | `transaction_types` | `CVTRA03Y` |
| `customers` | CUSTDAT / `CVCUS01Y` | `transaction_categories` | `CVTRA04Y` |
| `cards` | CARDDAT / `CVACT02Y` | `sec_users` | USRSEC / `CSUSR01Y` |
| `card_xref` | CCXREF / `CVACT03Y` (+ `CXACAIX` index) | `db2_transaction_type` | `TRANTYPE.ddl` / `.dcl` |
| `transactions` | TRANSACT / `CVTRA05Y` | `db2_transaction_type_category` | `TRANCATG.ddl` / `.dcl` |
| `daily_transactions` | DALYTRAN / `CVTRA06Y` | `auth_fraud` | `AUTHFRDS.ddl` |
| `transaction_category_balances` | TCATBALF / `CVTRA01Y` | `pending_auth_summary` | IMS `PAUTSUM0` segment |
| `disclosure_groups` | DISCGRP / `CVTRA02Y` | `pending_auth_detail` | IMS `PAUTDTL1` segment (FK to summary) |

The `CXACAIX` alternate index is an index on `card_xref(acct_id)`; the `PAUTINDX` secondary index is an
index on the detail table's authorization key. Every table has a JPA entity in `com.carddemo.common.domain`
and a Spring Data repository in `com.carddemo.common.repository`.

Seed data: `db/seed/R__seed_carddemo_data.sql`, generated by `tools/generate_seed_sql.py` from
`app/data/ASCII/**` (never the EBCDIC copies). It is on the Flyway path for the `h2` profile automatically,
and loadable for PostgreSQL (§5). This replaces the S-18 IDCAMS load jobs.

## 4. Adding a frontend route

1. Add `frontend/src/pages/<stream>/<Screen>Page.js`.
2. Change **one** line in `frontend/src/routes/registry.js`: the entry for your program already exists with
   `element: null` (rendered as a placeholder). Import your page and replace `null` with `<YourPage />`.

Registry entry shape — `program` (COBOL name), `tranId` (CICS transaction), `path`, `title`, `stream`,
`element`. Backend COMMAREA navigation resolves through `pathForProgram(program)`, so a screen becomes
reachable from the menus the moment its entry exists; do not hard-code paths in menu code.

Screen fidelity: labels, field order, PF-key lines and message text come verbatim from the BMS map and the
program literals. Do not reword them.

## 5. Running it

Backend tests (H2, no container needed):

```bash
cd migration/carddemo/backend
mvn -B test
```

Run against H2 (default profile, schema + seed applied at boot):

```bash
mvn spring-boot:run
```

Run against PostgreSQL (the real target):

```bash
docker run -d --name carddemo-pg -e POSTGRES_PASSWORD=carddemo -e POSTGRES_USER=carddemo \
  -e POSTGRES_DB=carddemo -p 5432:5432 postgres:16
mvn spring-boot:run -Dspring-boot.run.profiles=postgres
# with demo data:
mvn spring-boot:run -Dspring-boot.run.profiles=postgres \
  -Dspring-boot.run.arguments=--spring.flyway.locations=classpath:db/migration,classpath:db/seed
```

Frontend (Node 20; dev server proxies to `http://localhost:8080`):

```bash
cd migration/carddemo/frontend
npm ci
npm start      # dev
npm run build  # what CI runs
```

Sign-on uses the USRSEC-derived `sec_users` rows from the seed (user type `A` reaches the admin menu,
`U` the main menu only).

If Maven Central returns HTTP 429, mirror it in `~/.m2/settings.xml` to
`https://maven-central.storage-download.googleapis.com/maven2`.

## 6. Adding a Spring Batch job

One `@Configuration` class per JCL job in `com.carddemo.batch.<job>`, one `@Bean` `Step` per `EXEC PGM=`
in the JCL, chunk-oriented, restartable through the shared `JobRepository`. `com.carddemo.batch.dataload.DataLoadJobConfiguration`
is the worked example (job `DATALOAD`, one step per input file) — copy its shape.

Jobs never auto-run: `spring.batch.job.enabled=false`, and `com.carddemo.batch.BatchJobLauncher` runs only
the job named on the command line, exiting 0 on success and 12 (the JCL failure condition code) otherwise:

```bash
java -jar target/carddemo.jar --spring.main.web-application-type=none \
     --spring.profiles.active=postgres --spring.batch.job.name=DATALOAD
```

Instead of `CALL 'CEE3ABD'`, call `com.carddemo.common.batch.AbendService`: it logs the abend reason and
fails the step, which the launcher turns into exit code 12 (boundary B-01).

## 8. Intentionally empty extension points

These are deliberately unimplemented, and are the only "not yet built" things in this tree:

- **Screen routes with `element: null`** in `frontend/src/routes/registry.js` — every not-yet-migrated
  legacy screen. They render `PlaceholderPage`, which names the program, stream and route, so both menus
  are navigable end to end today.
- **Stream backend packages** — only `com.carddemo.authshell` and `com.carddemo.transaction` exist. The
  other packages in §1 are created by their stream session.
- **Batch job packages** — only `com.carddemo.batch.dataload` exists; the other JCL jobs are their stream's
  work.
- **The MQ seam** — configured and tested, off behind `carddemo.mq.enabled=false`. S-09/S-10 enable it and
  add their own `@JmsListener`s; no listener ships here because no MQ program has been migrated yet.

## 9. CI

`.github/workflows/carddemo-ci.yml` runs `mvn -B test` (H2) for the backend and `npm ci && CI=true npm run build`
for the frontend on every push to `devin/**` and every PR touching `migration/carddemo/**`. Both must be
green before a stream PR merges; `CI=true` makes React build warnings fatal, so keep the build warning-free.
