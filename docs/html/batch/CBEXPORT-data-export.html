Business Flow Analysis

1.1 Business Context

  • What: Reads all five CardDemo VSAM master files (Customer, Account, Cross-Reference, Transaction, Card) sequentially and writes a combined multi-record-type export file (EXPORT.DATA) in VSAM KSDS format. Each source record is mapped into a 500-byte export record with a record-type indicator, timestamp, sequence number, branch ID, and region code.
  • Who: Consumed by the companion CBIMPORT program at the target branch, or by any downstream migration tooling that reads the multi-record export format.
  • When: Triggered on-demand when a branch migration or data transfer is required. Typically run during a maintenance window after CICS files are closed.
  • Why: Provides a portable, self-describing export of all customer-facing data for branch-to-branch migration. Consolidates five separate VSAM files into a single transport file with record-type tags for easy parsing at the target site.
  • Outcome: A single VSAM KSDS file (EXPORT.DATA) containing all customer, account, cross-reference, transaction, and card records with export metadata (timestamp, sequence, branch, region). Console statistics report counts per record type.

2.2 Technical Flow Diagram – Detailed (Step-by-Step)

  STEP01 - EXEC PGM=IDCAMS
    SYSIN (inline):
      DELETE AWS.M2.CARDDEMO.EXPORT.DATA CLUSTER PURGE
      SET MAXCC = 0
      DEFINE CLUSTER (NAME(AWS.M2.CARDDEMO.EXPORT.DATA)
                      INDEXED
                      KEYS(4 28)
                      RECORDSIZE(500 500)
                      CYLINDERS(10 5)
                      FREESPACE(10 10)
                      SHAREOPTIONS(2 3))
             DATA  (NAME(AWS.M2.CARDDEMO.EXPORT.DATA.DATA))
             INDEX (NAME(AWS.M2.CARDDEMO.EXPORT.DATA.INDEX))
    RC: 0 = success (SET MAXCC=0 ensures delete failure is masked)

  STEP02 - EXEC PGM=CBEXPORT
    INPUTS (all sequential read of VSAM KSDS):
      - CUSTFILE: AWS.M2.CARDDEMO.CUSTDATA.VSAM.KSDS   (500-byte, key=CUST-ID)
      - ACCTFILE: AWS.M2.CARDDEMO.ACCTDATA.VSAM.KSDS   (300-byte, key=ACCT-ID)
      - XREFFILE: AWS.M2.CARDDEMO.CARDXREF.VSAM.KSDS   (50-byte, key=XREF-CARD-NUM)
      - TRANSACT: AWS.M2.CARDDEMO.TRANSACT.VSAM.KSDS   (350-byte, key=TRAN-ID)
      - CARDFILE: AWS.M2.CARDDEMO.CARDDATA.VSAM.KSDS   (150-byte, key=CARD-NUM)
    OUTPUT:
      - EXPFILE:  AWS.M2.CARDDEMO.EXPORT.DATA            (500-byte, key=SEQ# at offset 28)

    PROCESSING:
      1. 1000-INITIALIZE
         a. 1050-GENERATE-TIMESTAMP: ACCEPT date/time, format YYYY-MM-DD HH:MM:SS.00
         b. 1100-OPEN-FILES: Open 5 inputs + 1 output (ABEND if any fail)
      2. 2000-EXPORT-CUSTOMERS: READ CUSTFILE until EOF
         For each: INITIALIZE EXPORT-RECORD, set type='C', map customer fields, WRITE
      3. 3000-EXPORT-ACCOUNTS: READ ACCTFILE until EOF
         For each: INITIALIZE EXPORT-RECORD, set type='A', map account fields, WRITE
      4. 4000-EXPORT-XREFS: READ XREFFILE until EOF
         For each: INITIALIZE EXPORT-RECORD, set type='X', map xref fields, WRITE
      5. 5000-EXPORT-TRANSACTIONS: READ TRANSACT until EOF
         For each: INITIALIZE EXPORT-RECORD, set type='T', map transaction fields, WRITE
      6. 5500-EXPORT-CARDS: READ CARDFILE until EOF
         For each: INITIALIZE EXPORT-RECORD, set type='D', map card fields, WRITE
      7. 6000-FINALIZE: CLOSE all files, DISPLAY export statistics
      8. GOBACK (RC = 0)
    RC: 0 = success, ABEND via CEE3ABD on any I/O failure

2.3 Step Dependency and Condition Code Logic

StepProgramExecutes IfCondition Code Meaning
STEP01IDCAMSAlways0 = VSAM cluster defined successfully (SET MAXCC=0 masks delete-not-found)
STEP02CBEXPORTAlways (no COND= coded)0 = All records exported successfully
ABEND via CEE3ABD = file open or I/O failure
Note: STEP01 uses SET MAXCC = 0 after the DELETE command, ensuring that STEP02 always executes even if the EXPORT.DATA cluster did not previously exist.

3.3 GDG Usage

N/A: This job does not use Generation Data Groups. The output EXPORT.DATA is a standard VSAM KSDS cluster, deleted and redefined each run by STEP01 (IDCAMS).

3.4 Scheduler Dependencies

Note: CBEXPORT is not in the Control-M schedule. It is an on-demand migration utility. It should be run when CICS files are not locked (i.e., after CLOSEFIL or during a maintenance window) to ensure shared access to the VSAM input files.

Checkpoint, Restart, and Recovery

8.1 Checkpoint Strategy

No checkpoint/restart mechanism is implemented. The program runs as a single uninterruptible unit. If a failure occurs mid-export, the EXPORT.DATA file will contain a partial dataset with no way to resume from the point of failure.

8.2 Restart Procedures

  • STEP01 failure: Resubmit the entire job. IDCAMS will re-attempt DELETE/DEFINE.
  • STEP02 failure (mid-export): Resubmit from STEP01. The IDCAMS DELETE/DEFINE will recreate an empty EXPORT.DATA cluster, and CBEXPORT will re-export all records from the beginning. No partial recovery is possible.

Recovery advantage: Since all 5 input files are opened INPUT (read-only), a mid-run failure does not corrupt any source data. The only file that may be in an inconsistent state is EXPORT.DATA, which is always recreated from scratch by STEP01.

Performance and Batch Window Analysis

11.1 I/O Characteristics

FileAccess PatternI/O Count (per run)Record SizeNotes
CUSTFILESequential readNcust + 1 (EOF)500 bytesFull file scan
ACCTFILESequential readNacct + 1 (EOF)300 bytesFull file scan
XREFFILESequential readNxref + 1 (EOF)50 bytesFull file scan

EXPFILESequential write (keyed)Ntotal500 bytesOne write per source record

Total I/O operations: 2 × Ntotal + 5 (one read + one write per record, plus 5 EOF reads). This is a purely I/O-bound job with no CPU-intensive validation or computation.

11.2 Batch Window Fit

  • Processing model: Single-pass sequential read of each source file. No random I/O, no lookups, no joins.
  • Scalability: Linear with total record count across all 5 files. For typical CardDemo volumes (thousands of records), expected elapsed time is seconds to low minutes.
  • Bottleneck: VSAM I/O on the export file (500-byte keyed writes). FREESPACE(10 10) allocation helps with CI/CA splits.
  • Parallelism: None. Files are processed sequentially (Customers → Accounts → XRefs → Transactions → Cards). No opportunity for intra-job parallelism.
