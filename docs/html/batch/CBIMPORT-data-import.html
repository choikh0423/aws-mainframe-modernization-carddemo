Business Flow Analysis

1.1 Business Context

  • What: Reads a multi-record indexed VSAM export file (produced by CBEXPORT) containing interleaved customer, account, card cross-reference, transaction, and card records. Splits the export file by record type into five separate normalized sequential files, routing any unrecognized record types to an error file with timestamps and diagnostic messages.
  • Who: Downstream consumers include the target-system data loading jobs that ingest each normalized file independently (CUSTDATA.IMPORT, ACCTDATA.IMPORT, CARDXREF.IMPORT, TRANSACT.IMPORT, CARDDATA.IMPORT). Operations teams review the IMPORT.ERRORS file for data quality issues.
  • When: Runs on-demand during branch migration events. Typically executed after CBEXPORT has produced the consolidated export file from the source branch.
  • Why: Branch migrations require moving complete customer portfolios (customers, accounts, cards, cross-references, and transaction history) from one system to another. The export file is a single consolidated dataset; the target system requires separate, normalized files per entity type.
  • Outcome: Five normalized sequential output files ready for target-system ingestion, plus an error file capturing any unknown or malformed records with diagnostic details.

2.2 Technical Flow Diagram – Detailed (Step-by-Step)

  STEP01 - EXEC PGM=CBIMPORT
    INPUTS:
      - EXPFILE: AWS.M2.CARDDEMO.EXPORT.DATA  (VSAM KSDS, sequential read)
    OUTPUTS:
      - CUSTOUT: AWS.M2.CARDDEMO.CUSTDATA.IMPORT  (Sequential FB, LRECL=500)
      - ACCTOUT: AWS.M2.CARDDEMO.ACCTDATA.IMPORT  (Sequential FB, LRECL=300)
      - XREFOUT: AWS.M2.CARDDEMO.CARDXREF.IMPORT  (Sequential FB, LRECL=50)
      - TRNXOUT: AWS.M2.CARDDEMO.TRANSACT.IMPORT  (Sequential FB, LRECL=350)
      - CARDOUT: *NOT IN JCL* (Sequential FB, LRECL=150)
      - ERROUT:  AWS.M2.CARDDEMO.IMPORT.ERRORS     (Sequential FB, LRECL=132)

    PROCESSING:
      1. 1000-INITIALIZE:
         a. Capture current date and time (WS-IMPORT-DATE, WS-IMPORT-TIME)
         b. 1100-OPEN-FILES: Open EXPORT-INPUT (INPUT), all 5 output files
            (OUTPUT), and ERROR-OUTPUT (OUTPUT). ABEND if any OPEN fails.
      2. 2000-PROCESS-EXPORT-FILE:
         a. 2100-READ-EXPORT-RECORD: READ EXPORT-INPUT INTO EXPORT-RECORD
         b. PERFORM UNTIL WS-EXPORT-EOF:
            i.   ADD 1 TO WS-TOTAL-RECORDS-READ
            ii.  2200-PROCESS-RECORD-BY-TYPE:
                 EVALUATE EXPORT-REC-TYPE:
                   'C' → 2300-PROCESS-CUSTOMER-RECORD
                   'A' → 2400-PROCESS-ACCOUNT-RECORD
                   'X' → 2500-PROCESS-XREF-RECORD
                   'T' → 2600-PROCESS-TRAN-RECORD
                   'D' → 2650-PROCESS-CARD-RECORD
                   OTHER → 2700-PROCESS-UNKNOWN-RECORD
            iii. 2100-READ-EXPORT-RECORD (next record)
      3. 3000-VALIDATE-IMPORT:
         Display "validation completed" (stub — no actual validation)
      4. 4000-FINALIZE:
         a. CLOSE all 7 files
         b. DISPLAY import statistics (totals by record type)
      5. GOBACK

    RC: 0 = Normal completion, ABEND via CEE3ABD = file I/O error

2.3 Step Dependency and Condition Code Logic

StepProgramExecutes IfCondition Code Meaning
STEP01CBIMPORTAlways (single-step job)0 = All records processed and split successfully
ABEND (U0xxx) = Fatal file I/O error via CEE3ABD
Note: CBIMPORT does not set a non-zero return code for unknown record types. Unknown records are silently written to the error file and processing continues. The only failure mode is an ABEND on file I/O errors.

3.3 GDG Usage

Not applicable. CBIMPORT does not use Generation Data Groups. All output datasets are created with DISP=(NEW,CATLG,DELETE) — simple cataloged sequential files.

3.4 Scheduler Dependencies

Note: CBIMPORT is not in the Control-M schedule (app/scheduler/CardDemo.controlm). It is an on-demand data migration utility, logically positioned after CBEXPORT produces the consolidated export file. There are no automated predecessor or successor dependencies.

9.4 File Status Handling

CBIMPORT checks file status after every I/O operation using 88-level condition names:

  • WS-EXPORT-OK (value ‘00’): Successful read from EXPORT-INPUT
  • WS-EXPORT-EOF (value ‘10’): End-of-file on EXPORT-INPUT — normal loop termination
  • WS-CUSTOMER-OK, WS-ACCOUNT-OK, WS-XREF-OK, WS-TRANSACTION-OK, WS-CARD-OK: Successful WRITE to respective output
  • WS-ERROR-OK: Successful WRITE to ERROR-OUTPUT
  • Any non-OK status on OPEN or WRITE (except error file) triggers 9999-ABEND-PROGRAM → CALL 'CEE3ABD'

Performance and Batch Window Analysis

11.1 Performance Characteristics

CBIMPORT is I/O-bound with a simple processing pattern: 1 VSAM READ + 1 sequential WRITE per record.

  1. READ EXPORT-INPUT (sequential by VSAM key — optimal CI/CA buffer usage)
  2. EVALUATE record type (in-memory, negligible CPU)
  3. INITIALIZE target record + MOVE fields (in-memory)
  4. WRITE to one of 6 output files (sequential — efficient buffering)
Performance note: The I/O pattern is highly efficient: one sequential VSAM read plus one sequential write per record. No random access, no lookups, no REWRITE operations. Throughput is limited primarily by DASD bandwidth. For large export files, increasing BLKSIZE on output DDs (currently BLKSIZE=0, system-determined) and adding BUFNI/BUFND on the VSAM input can improve throughput.
