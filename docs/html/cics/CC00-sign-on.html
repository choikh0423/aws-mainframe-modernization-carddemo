Business Flow Analysis

1.1 Business Context

The Sign-On transaction (CC00) is the authentication gateway for the CardDemo application. It is the first transaction a user encounters and serves as the entry point to the entire system. Every user — whether a regular cardholder or an administrator — must authenticate through this screen before accessing any CardDemo functionality.

  • Who uses it: All CardDemo users (regular users and administrators)
  • When: At system login, before any other transaction can be accessed
  • Business outcome: Authenticated users are routed to the appropriate menu — regular users to the Main Menu (COMEN01C / CM00), administrators to the Admin Menu (COADM01C / CA00)
  • Data accessed: The USRSEC VSAM KSDS file containing user credentials and role types

7.2 Return Code Conventions

COSGN00C uses the WS-RESP-CD variable (PIC S9(09) COMP) to capture CICS RESP codes from the READ and RECEIVE commands. The program evaluates these as follows:

RESP CodeMeaningAction
0 (NORMAL)Record found successfullyProceed with password comparison
13 (NOTFND)User ID not found in USRSECDisplay "User not found. Try again ..."
OTHERAny other CICS errorDisplay "Unable to verify the User ..."

7.3 Conversation State Management

State is preserved between pseudo-conversational iterations via the CARDDEMO-COMMAREA:

  • First entry (EIBCALEN = 0): No COMMAREA exists — the program displays the empty sign-on screen and issues RETURN TRANSID('CC00') COMMAREA(CARDDEMO-COMMAREA).
  • Subsequent entries (EIBCALEN > 0): The COMMAREA is available via DFHCOMMAREA. The program evaluates EIBAID and processes user input. On failed login, it returns again with TRANSID('CC00'), preserving the COMMAREA for the next iteration.
  • Successful login: State transitions via XCTL — control passes entirely to COADM01C or COMEN01C with the populated COMMAREA. No RETURN is issued.
  • PF3 exit: RETURN is issued with no TRANSID, ending the pseudo-conversational loop.
Key observation: COSGN00C does not reference the incoming DFHCOMMAREA data (beyond checking EIBCALEN). It relies entirely on fresh terminal input each iteration rather than storing partial state. The COMMAREA serves only as an outbound contract for XCTL targets.

Security and Authorization

9.1 Transaction Security

CC00/COSGN00C is the authentication mechanism for the CardDemo application. It implements application-level security as follows:

  • Authentication flow: User enters an 8-character User ID and 8-character Password. Both are uppercased via FUNCTION UPPER-CASE. The User ID is used as the key to read the USRSEC VSAM file. The stored SEC-USR-PWD is compared directly with the input password.
  • Password handling: The Password field on the BMS map uses the DRK (dark) attribute to prevent screen echo. However, passwords are stored and compared in clear text — no hashing or encryption is applied.
  • Role-based routing: The SEC-USR-TYPE field determines post-login routing:
    • 'A' (CDEMO-USRTYP-ADMIN) → XCTL to COADM01C (Admin Menu)
    • 'U' (CDEMO-USRTYP-USER, or any non-A value) → XCTL to COMEN01C (Main Menu)
  • Session identity: The authenticated CDEMO-USER-ID and CDEMO-USER-TYPE are carried in the COMMAREA through all subsequent transactions, establishing the user session context.
  • RACF/External security: No explicit RACF or CICS security manager calls are made. Transaction-level security (e.g., RACF transaction authorization for CC00) would be configured at the CICS region level, external to the program.

9.2 Data Access Authorization

The program performs a read-only access to the USRSEC file. There are no explicit data-level authorization checks beyond the file's FCT definition. The USRSEC file's access permissions would be controlled by the CICS FCT and underlying VSAM security (RACF dataset profiles).

9.3 Audit Trail

COSGN00C does not implement any explicit audit logging. There is no write to an audit file or TDQ on login success or failure. Audit capabilities would rely on:

  • CICS SMF records (Type 110) for transaction-level logging
  • RACF audit events if external security is configured
  • CICS journal records if journaling is enabled at the region level
Security observation: Passwords are stored and compared in plain text. There is no login attempt throttling, account lockout, or failed-login auditing within the application code.

10.2 Performance Considerations

  • Lightweight transaction: CC00 is one of the simplest transactions in the system. A single direct keyed VSAM READ is the only file I/O. No browse operations, no multi-file joins.
  • No locking contention: The READ does not specify UPDATE, so no record-level locking occurs. Multiple concurrent sign-on attempts will not contend.
