Business Flow Analysis

1.1 Business Context

The Credit Card List transaction (CCLI) enables customer-service representatives and cardholders to browse all credit cards on file. It provides:

  • Unfiltered browsing — when no account or card filter is entered, all cards in the CARDDAT VSAM file are listed (admin users).
  • Account-filtered browsing — the user may enter an 11-digit account number in ACCTSID to narrow the list to cards belonging to that account.
  • Card-filtered browsing — the user may enter a 16-digit card number in CARDSID to locate a specific card.
  • Navigation to detail/update — the user selects a row with S (view) or U (update) to transfer control to COCRDSLC (Credit Card View) or COCRDUPC (Credit Card Update) respectively.

The program header states: "List Credit Cards — (a) All cards if no context passed and admin user; (b) Only the ones associated with ACCT in COMMAREA if user is not admin."

7.2 Return Code Conventions

COCRDLIC does not use numeric return codes. State is communicated through:

  • CDEMO-PGM-CONTEXT: 0 = enter (fresh start), 1 = re-enter (subsequent interaction)
  • WS-RETURN-FLAG: '1' = returning from a called program, LOW-VALUES = normal
  • CA-NEXT-PAGE-EXISTS / CA-NEXT-PAGE-NOT-EXISTS: pagination boundary flags

7.3 Conversation State Management

State is preserved via the merged COMMAREA passed on EXEC CICS RETURN TRANSID('CCLI'):

  • Save: At COMMON-RETURN, CARDDEMO-COMMAREA is moved to the first part of WS-COMMAREA, followed by WS-THIS-PROGCOMMAREA appended at offset LENGTH OF CARDDEMO-COMMAREA + 1.
  • Restore: On re-entry (EIBCALEN > 0), DFHCOMMAREA is split back into the two structures at the same offset.
  • Pagination keys: WS-CA-FIRST-CARDKEY and WS-CA-LAST-CARDKEY carry the VSAM browse resume positions between iterations.
  • Fresh start detection: If CDEMO-PGM-ENTER is true and CDEMO-FROM-PROGRAM ≠ 'COCRDLIC', the program reinitializes WS-THIS-PROGCOMMAREA, resetting pagination to page 1.

Security and Authorization

9.1 Transaction Security

COCRDLIC does not perform its own authentication or transaction-level security checks. Access control relies on:

  • Menu routing: The Credit Card List option (#3) is available from the Main Menu (COMEN01C), which is reached only after successful sign-on via COSGN00C (CC00).
  • User type: The program defaults to SET CDEMO-USRTYP-USER TO TRUE. The CDEMO-USER-TYPE field in COMMAREA carries 'A' (admin) or 'U' (regular user) from the sign-on program.
  • CICS transaction security: Standard RACF/ESM transaction-level security may restrict which users can invoke CCLI.

9.2 Data Access Authorization

The program header notes that admin users see all cards, while regular users see only cards associated with their account (via the COMMAREA CDEMO-ACCT-ID). However, the current implementation applies application-level filtering in 9500-FILTER-RECORDS based on the user-entered filter fields, not the user type. True account-based restriction would require additional logic beyond what is currently coded.

9.3 Audit Trail

No explicit audit logging or journaling is performed by COCRDLIC. Standard CICS SMF/journal records provide the only audit trail for browse operations.

10.2 Performance Considerations

  • Application-level filtering: When an account filter is active, the program reads and discards non-matching records via 9500-FILTER-RECORDS. If matching records are sparse, many READNEXTs may be needed to fill 7 screen rows, increasing I/O cost.
  • CARDAIX unused: The LIT-CARD-FILE-ACCT-PATH alternate index (CARDAIX) is defined but never used for browse. Using it for account-filtered browses would significantly reduce I/O for large files.
  • No skip-sequential optimization: The browse always reads from the beginning of the matching key range; there is no optimization for skipping to a specific account's cards.
  • COMMAREA size: At ~2,000 bytes, the COMMAREA is moderately sized and should not cause performance concerns.
  • Repetitive code: The program uses hardcoded references for 7 screen rows (e.g., CRDSEL1O–CRDSEL7O) instead of BMS arrays, which increases program size but has no runtime performance impact.
