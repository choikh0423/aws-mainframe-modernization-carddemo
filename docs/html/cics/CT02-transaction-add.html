Business Flow Analysis

1.1 Business Context

The Transaction Add function (CT02) enables authorized CardDemo users to create a new credit-card transaction record. The user identifies the account either by Account ID or Card Number, fills in transaction details (type, category, source, description, amount, dates, merchant information), confirms the entry, and the system writes the new record to the TRANSACT VSAM KSDS file with a system-generated sequential transaction ID.

Users: Regular users and administrators who have navigated through the main menu (CM00) to the Transaction List screen (CT00) and selected the add option.
Business Outcome: A new transaction record is persisted with a unique auto-incremented ID, ready for downstream batch processing (daily post-transaction cycle).

7.3 Conversation State Management

State is preserved between pseudo-conversational iterations via CARDDEMO-COMMAREA. The field CDEMO-PGM-CONTEXT (88-level CDEMO-PGM-REENTER) distinguishes first entry (value 0) from re-entry (value 1). On first entry, the program sets CDEMO-PGM-REENTER = TRUE (value 1) and sends the blank screen. On re-entry, it receives user input and processes the AID key. The COMMAREA is passed on every EXEC CICS RETURN TRANSID('CT02') call to maintain context. The CDEMO-CT02-TRN-SELECTED field carries a card number from the Transaction List (CT00) screen for pre-population on first entry.

Security and Authorization

9.1 Transaction Security

Transaction CT02 does not implement its own authentication. Access is controlled at two levels:

  • CICS Transaction Security: The transaction ID CT02 can be secured via RACF or equivalent ESM (External Security Manager) to restrict which users can initiate it.
  • Application-Level Routing: Users must first sign on via CC00 (COSGN00C), which validates credentials and stores the user type (CDEMO-USER-TYPE: ‘A’ for admin, ‘U’ for regular user) in the COMMAREA. The main menu (CM00) then routes only to authorized transactions. If a user enters CT02 directly without a valid COMMAREA (EIBCALEN = 0), the program XCTLs to the sign-on screen (COSGN00C).

9.2 Data Access Authorization

No field-level or record-level security checks are implemented within the program. Any authenticated user who can reach this transaction can add a transaction against any valid account/card combination. VSAM file-level security is controlled by the CICS region’s FCT definitions and underlying OS/RACF dataset profiles.

9.3 Audit Trail

The program does not write explicit audit records. However, the transaction record itself contains TRAN-ORIG-TS and TRAN-PROC-TS (timestamp fields entered by the user). CICS journal/log facilities and SMF records would capture transaction-level audit data at the infrastructure level. Error conditions trigger DISPLAY statements that write RESP/REAS codes to the CICS CEEMSG/SYSOUT for operational monitoring.

10.2 Performance Considerations

  • Sequential ID Generation: Uses STARTBR at HIGH-VALUES + READPREV to find the last transaction ID. This browse/read is lightweight (single record) but serializes concurrent adds — two simultaneous users could generate the same ID, resulting in a DUPKEY error.
  • No Locking: The ID generation pattern (STARTBR → READPREV → ADD 1 → WRITE) is not wrapped in a task-level lock or ENQ/DEQ. Under high concurrency, DUPKEY responses are possible and must be retried by the user.
  • Date Validation: Two CALL statements to CSUTLDTC add a small but measurable overhead per iteration. The utility is a statically linked subroutine, so the overhead is minimal compared to file I/O.
  • Validation Short-Circuit: The VALIDATE-INPUT-DATA-FIELDS paragraph sends the screen and returns immediately on the first validation error found, avoiding unnecessary file I/O for invalid input.

Known Issues and Considerations

12.1 Known Issues

#IssueSeverityDetails
1Race condition in ID generationMediumThe STARTBR → READPREV → ADD 1 → WRITE pattern has no ENQ/DEQ or file-level lock. Concurrent users could read the same last TRAN-ID and attempt to WRITE with the same new ID, resulting in DUPKEY. The program handles DUPKEY but does not retry — the user must re-submit.
2VALIDATE-INPUT-DATA-FIELDS clears fields on key errorLowWhen ERR-FLG-ON is true from key field validation, all data fields (TTYPCD through MZIP) are moved to SPACES (lines 238–249). This forces the user to re-enter all data after an account/card error, even if they had already entered valid detail fields.
3No user-type checkLowUnlike some admin-only transactions (CU00–CU03), CT02 does not check CDEMO-USER-TYPE. Any authenticated user (admin or regular) can add transactions. This may or may not be intentional.
4Hardcoded file namesLowFCT names are hardcoded as working storage constants (WS-TRANSACT-FILE = 'TRANSACT', etc.) rather than being configurable. Standard practice for CICS programs but limits flexibility.
5DISPLAY statements in production codeLowError branches include DISPLAY 'RESP:' WS-RESP-CD 'REAS:' WS-REAS-CD which writes to SYSOUT. Acceptable for debugging but may produce excessive output in production under error conditions.
6Date fields stored as user inputLowTRAN-ORIG-TS and TRAN-PROC-TS in CVTRA05Y are PIC X(26) but the user enters only 10-character YYYY-MM-DD strings. The remaining 16 characters are spaces, potentially causing issues in downstream processing expecting full timestamps.
