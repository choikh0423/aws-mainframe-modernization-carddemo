Business Flow Analysis

1.1 Business Context

The Credit Card View transaction (CCDL) allows a CardDemo user to look up and display the detail of a specific credit card. The user provides an 11-digit account number and a 16-digit card number; the system reads the VSAM card file (CARDDAT) and returns the card’s embossed name, active status, and expiration date. This is a read-only inquiry—no updates are performed.

The transaction is typically invoked from the Credit Card List screen (CCLI / COCRDLIC), where the user selects a card. It can also be accessed directly via the CICS terminal by entering the CCDL transaction code with an account and card number.

7.2 Return Code Conventions

The program uses WS-RESP-CD (PIC S9(09) COMP) and WS-REAS-CD (PIC S9(09) COMP) to capture CICS RESP and RESP2 codes from file operations. On error, these are formatted into WS-FILE-ERROR-MESSAGE and displayed to the user. The 88-level flags on WS-INPUT-FLAG (INPUT-OK / INPUT-ERROR) control flow between validation and display.

7.3 Conversation State Management

State is preserved between pseudo-conversational iterations via the WS-COMMAREA (2000 bytes), which concatenates CARDDEMO-COMMAREA and WS-THIS-PROGCOMMAREA. On each RETURN, the combined data is passed back. On re-entry, the program splits DFHCOMMAREA back into the two areas. The key state fields are:

  • CDEMO-PGM-CONTEXT: 0 = first entry (CDEMO-PGM-ENTER), 1 = re-entry (CDEMO-PGM-REENTER)
  • CDEMO-ACCT-ID / CDEMO-CARD-NUM: persisted search criteria
  • CDEMO-FROM-PROGRAM / CDEMO-FROM-TRANID: calling context for PF3 return routing
  • CDEMO-LAST-MAPSET / CDEMO-LAST-MAP: last screen sent (used for attribute logic)

Security and Authorization

9.1 Transaction Security

Access to the CCDL transaction is controlled at the menu level. The sign-on program (COSGN00C) authenticates users and routes them based on CDEMO-USER-TYPE: regular users (‘U’) go to the main menu (COMEN01C), admin users (‘A’) go to the admin menu (COADM01C). Credit Card View is available from the main menu flow (Credit Card List → Credit Card View), making it accessible to both regular and admin users.

Within COCRDSLC, on PF3 exit the program sets CDEMO-USRTYP-USER unconditionally, meaning the return context always assumes regular user type regardless of the original user type.

9.2 Data Access Authorization

No data-level security checks are performed within the program. Any authenticated user who reaches this screen can view any card record by providing the card number. There is no row-level access control or ownership verification.

9.3 Audit Trail

No explicit audit logging is implemented in COCRDSLC. Standard CICS journal/log facilities would capture transaction-level activity at the region level, but the program does not write audit records to any application log file or queue.

10.2 Performance Considerations

  • Minimal I/O footprint: Only one direct-key VSAM READ per iteration makes this a very lightweight transaction.
  • No BROWSE operations: Unlike the list screens (CCLI, CT00), this transaction performs only keyed reads, avoiding sequential I/O overhead.
  • COMMAREA overhead: The 2000-byte COMMAREA is larger than strictly necessary for this transaction (most fields are unused), but within acceptable CICS limits.
  • Alternate index path: The 9150-GETCARD-BYACCT paragraph reads via the CARDAIX alternate index but is not invoked in the main flow — it exists as an alternative lookup method.
