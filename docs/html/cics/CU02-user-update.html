Business Flow Analysis

1.1 Business Context

The User Update transaction (CU02) allows a system administrator to modify an existing user record in the CardDemo security file (USRSEC). The administrator navigates to this screen from the Admin Menu (option 3 — “User Update (Security)”) or from the User List screen which pre-populates the User ID. Editable fields include First Name, Last Name, Password, and User Type (Admin/User). After validation, the record is rewritten to the VSAM KSDS file. This is an admin-only function; regular users cannot reach this transaction.

7.2 Return Code Conventions

The program uses WS-RESP-CD (PIC S9(09) COMP) and WS-REAS-CD (PIC S9(09) COMP) to capture CICS RESP/RESP2 codes from READ and REWRITE operations. Response codes are evaluated via DFHRESP(NORMAL), DFHRESP(NOTFND), and a catch-all OTHER branch. The error flag WS-ERR-FLG (PIC X(01), 88-levels ERR-FLG-ON / ERR-FLG-OFF) gates subsequent processing.

7.3 Conversation State Management

State is preserved between pseudo-conversational iterations via the CARDDEMO-COMMAREA passed on EXEC CICS RETURN TRANSID('CU02') COMMAREA(CARDDEMO-COMMAREA). The CDEMO-PGM-CONTEXT field distinguishes first entry (value 0, CDEMO-PGM-ENTER) from re-entry (value 1, CDEMO-PGM-REENTER). On first entry, the program sets CDEMO-PGM-REENTER to TRUE and initializes the screen. If CDEMO-CU02-USR-SELECTED was set by the calling program (User List), the user record is automatically fetched on first entry. On exit via PF3/PF12, CDEMO-PGM-CONTEXT is reset to ZEROS before XCTL to the target program.

09

Security and Authorization

9.1 Transaction Security

The CU02 transaction is admin-only. Access control is enforced at the menu level:

  • The Admin Menu (COADM01C) is only reachable by users with CDEMO-USER-TYPE = 'A' (set during sign-on by COSGN00C).
  • Option 3 in COADM02Y.cpy maps to “User Update (Security)” → COUSR02C.
  • If EIBCALEN = 0 (no COMMAREA — direct invocation without authentication), the program redirects to COSGN00C via XCTL.
Note: There is no explicit RACF transaction-level security check within the program itself. Security relies on the menu-routing architecture and the COMMAREA being set by the sign-on program.

9.2 Data Access Authorization

The program reads and rewrites any record in the USRSEC file without additional authorization checks beyond the menu-level admin gate. An admin user can modify any other user’s record, including passwords and user types.

Security Observation: Passwords are stored in plaintext in the SEC-USR-PWD field (PIC X(08)) and displayed on the BMS map (though the PASSWD field uses the DRK attribute to hide display). No hashing or encryption is applied.

9.3 Audit Trail

N/A — The program does not write audit records for user modifications. The only logging is DISPLAY statements to CEEMSG/SYSOUT for unexpected RESP codes during READ and REWRITE operations. No timestamp, operator ID, or change log is maintained.

10.2 Performance Considerations

  • Record locking: The READ with UPDATE option acquires an exclusive record lock. If the user fetches a record and walks away, the lock persists until the task times out or the user acts. This could block other admin users attempting to update the same user.
  • Double READ on save: The UPDATE-USER-INFO paragraph performs a second READ-USER-SEC-FILE (with UPDATE) before comparing fields and issuing REWRITE. This ensures current data but doubles the I/O on save operations.
  • Small record size: The USRSEC record is only 80 bytes, so I/O and COMMAREA overhead are minimal.
  • No BROWSE operations: This is a single-record update program with no STARTBR/READNEXT, so performance impact is inherently low.
