Business Flow Analysis

1.1 Business Context

COMEN01C is the Main Menu for Regular Users in the CardDemo application. After a successful sign-on via COSGN00C (transaction CC00), regular users are routed here. The program presents a numbered list of 11 application functions and dispatches the user to the selected sub-application via EXEC CICS XCTL. It acts purely as a navigation hub — it performs no file I/O and holds no business data of its own.

  • Who uses it: Regular (non-admin) cardholders and operators
  • When: Immediately after sign-on; also returned to via PF3 from child screens
  • Business outcome: Routes users to the correct functional area (account view, credit card management, transactions, billing, reports)

7.2 Return Code Conventions

COMEN01C does not use formal return codes. The WS-ERR-FLG flag ('Y'/'N') with 88-levels ERR-FLG-ON / ERR-FLG-OFF controls whether an error message is displayed and whether the XCTL dispatch is attempted. The WS-RESP-CD and WS-REAS-CD fields capture the CICS RECEIVE response but are not explicitly evaluated in the code.

7.3 Conversation State Management

State is managed via CDEMO-PGM-CONTEXT in the COMMAREA:

  • Value 0 (CDEMO-PGM-ENTER): First entry from sign-on — skip RECEIVE, initialize map output to LOW-VALUES, and SEND the menu screen.
  • Value 1 (CDEMO-PGM-REENTER): Subsequent entries — RECEIVE user input, process AID key, and either dispatch or re-display with error.

On each successful EXEC CICS RETURN TRANSID('CM00') COMMAREA(CARDDEMO-COMMAREA), the COMMAREA is preserved by CICS and supplied back on the next invocation via DFHCOMMAREA. Before XCTL to a child program, CDEMO-PGM-CONTEXT is reset to ZEROS so the child treats it as a first entry.

Security and Authorization

9.1 Transaction Security

Access to transaction CM00 is controlled by the sign-on flow. If EIBCALEN = 0 (no COMMAREA passed, meaning no prior authentication), the program immediately transfers control to COSGN00C — effectively redirecting unauthenticated users to the sign-on screen.

The user type (CDEMO-USER-TYPE) is set by COSGN00C after validating credentials against the USRSEC VSAM file. COMEN01C reads this field to enforce menu-level authorization:

  • User type 'U' (regular): Can access all options marked with USRTYPE = 'U'. Denied options marked 'A'.
  • User type 'A' (admin): Would be routed to COADM01C (admin menu) instead, not to this program.

In the current COMEN02Y configuration, all 11 options are marked 'U' (user-accessible), so no admin-only restrictions are active on the main menu. However, the enforcement logic is in place should any option's USRTYPE be changed to 'A'.

9.2 Data Access Authorization

COMEN01C performs no file I/O and therefore has no data-level authorization requirements. Data access authorization is delegated to the individual child programs invoked via XCTL.

9.3 Audit Trail

COMEN01C does not implement any explicit audit logging or journaling. Menu navigation events are not recorded. CICS system-level SMF records would capture transaction attachment/detachment events if configured at the region level.

10.2 Performance Considerations

  • Lightweight: COMEN01C is one of the lightest programs in the application — no file access, no DB2, no TSQ/TDQ usage.
  • Menu build loop: The BUILD-MENU-OPTIONS paragraph iterates 1–11 times using a PERFORM VARYING with STRING operations. This is negligible overhead.
  • INQUIRE PROGRAM: Option 11 (COPAUS0C) triggers an EXEC CICS INQUIRE PROGRAM on every selection. This is a lightweight CICS system call but is only invoked when option 11 is specifically selected.
  • Pseudo-conversational: Program is not held in memory between user interactions. COMMAREA is small (~120 bytes) and preserved by CICS efficiently.
