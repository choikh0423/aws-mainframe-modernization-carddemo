Business Flow Analysis

1.1 Business Context

The User Add transaction (CU01) allows a CardDemo administrator to create a new user account in the USRSEC security file. This is an admin-only function accessible from option 2 on the Admin Menu (COADM01C). The business outcome is a new security record that enables the created user to sign on to CardDemo via the CC00 (Sign-On) transaction. Administrators assign the user’s first name, last name, user ID (8 chars), password (8 chars), and user type (A=Admin or U=Regular User).

7.2 Return Code Conventions

The program uses WS-RESP-CD (PIC S9(09) COMP) to capture the CICS RESP code from EXEC CICS WRITE and EXEC CICS RECEIVE. Response codes are evaluated with DFHRESP(NORMAL), DFHRESP(DUPKEY), and DFHRESP(DUPREC). The program does not pass application-level return codes to other programs.

7.3 Conversation State Management

State is preserved via the CARDDEMO-COMMAREA passed on EXEC CICS RETURN TRANSID('CU01'). The key state variable is CDEMO-PGM-CONTEXT:

  • Value 0 (CDEMO-PGM-ENTER): First entry — display blank form, then set to 1
  • Value 1 (CDEMO-PGM-REENTER): Subsequent entries — receive input, process, redisplay

On PF3 exit, CDEMO-PGM-CONTEXT is reset to ZEROS before XCTL to the Admin Menu, so re-entry from the menu will display a fresh form.

Security and Authorization

9.1 Transaction Security

Access to CU01 is controlled by the Admin Menu routing in COADM01C. Only users whose CDEMO-USER-TYPE is 'A' (Admin) are routed to the Admin Menu after sign-on in COSGN00C. Regular users (CDEMO-USER-TYPE = 'U') are routed to the Main Menu (COMEN01C) and never see the Admin Menu options.

If a user attempts to invoke CU01 directly (without a valid COMMAREA, i.e., EIBCALEN = 0), the program immediately XCTLs to COSGN00C (Sign-On), effectively rejecting the request.

Note: The program itself does not check CDEMO-USER-TYPE — it relies on the upstream routing logic in COSGN00C and COADM01C to ensure only admins reach this transaction.

9.2 Data Access Authorization

The program performs a WRITE to the USRSEC file without additional authorization checks. File-level security is managed by CICS resource definitions (FCT) and any RACF rules governing the USRSEC dataset.

Security Concern: Passwords are stored in plaintext in the SEC-USR-PWD field (PIC X(08)). There is no hashing, encryption, or masking at the storage level. The BMS map uses DRK (dark) attribute on the password input field to prevent screen display, but this does not protect the stored value.

9.3 Audit Trail

The program does not generate any explicit audit records or log entries when a new user is created. The only implicit audit is the CICS journal/SMF records produced by CICS itself for the WRITE command.

10.2 Performance Considerations

  • Minimal I/O footprint: Only a single VSAM WRITE per successful add operation — no browse, no multi-file access.
  • Small COMMAREA: The CARDDEMO-COMMAREA is compact (~278 bytes based on the COCOM01Y layout), keeping inter-transaction overhead low.
  • Short path length: The program is only 299 LOC with a straightforward validate-and-write pattern. No complex loops or nested file operations.
  • No BROWSE operations: Unlike user list (CU00), this transaction does not use STARTBR/READNEXT.
  • Validation short-circuits: The EVALUATE TRUE structure exits on the first validation failure, minimizing unnecessary processing.

Known Issues and Considerations

12.1 Known Issues

#IssueSeverityDetails
KI-1 Plaintext password storage High Passwords are stored as plaintext in SEC-USR-PWD (PIC X(08)). No hashing or encryption is applied.
KI-2 No User Type validation Medium The program checks that USRTYPEI is not empty but does not validate that the value is ‘A’ or ‘U’. An admin could enter any character.
KI-3 No in-program authorization check Medium COUSR01C does not verify CDEMO-USER-TYPE = 'A' from the COMMAREA. It relies entirely on upstream routing in COSGN00C/COADM01C.
KI-4 PF12 listed on screen but not handled Low The BMS map footer shows “F12=Exit” but there is no DFHPF12 handler — it triggers the generic invalid-key error message.
KI-5 No audit logging Medium No explicit audit record is created when a new user is provisioned. Only implicit CICS journaling captures the event.
KI-6 SEC-USR-FILLER not initialized Low The 23-byte filler field in SEC-USER-DATA is never explicitly initialized before the WRITE, potentially writing residual working-storage data.
