Business Flow Analysis

1.1 Business Context

The User Delete transaction (CU03) allows an administrator to permanently remove a security user record from the CardDemo system. It is accessed exclusively from the Admin Menu (COADM01C, option 4 — "User Delete (Security)"). The administrator enters a User ID, the system retrieves and displays the user's details (first name, last name, user type), and upon confirmation via PF5, the record is deleted from the USRSEC VSAM KSDS file. This transaction enforces administrative control over system access by ensuring only authorized admin-type users can remove credentials.

7.3 Conversation State Management

State is preserved between pseudo-conversational iterations via the CARDDEMO-COMMAREA passed on EXEC CICS RETURN TRANSID('CU03') COMMAREA(CARDDEMO-COMMAREA). On reentry, DFHCOMMAREA is moved back into CARDDEMO-COMMAREA.

  • CDEMO-PGM-CONTEXT: Distinguishes first entry (0) from reentry (1). Set to 1 after first map send.
  • CDEMO-CU03-USR-SELECTED: Carries pre-selected User ID from the User List screen (COUSR00C) so the delete screen can auto-populate and fetch on first entry.
  • CDEMO-FROM-PROGRAM: Remembers the calling program so PF3 can return to the correct screen.
  • On XCTL to another program, CDEMO-PGM-CONTEXT is reset to ZEROS and CDEMO-FROM-TRANID/CDEMO-FROM-PROGRAM are set to this program's identity.

Security and Authorization

9.1 Transaction Security

Access to CU03 is restricted to administrator users through the application's menu routing architecture:

  • The sign-on program (COSGN00C) authenticates the user and sets CDEMO-USER-TYPE in the COMMAREA.
  • Admin users (type 'A') are routed to the Admin Menu (COADM01C), which presents "User Delete (Security)" as option 4.
  • Regular users (type 'U') are routed to the Main Menu (COMEN01C), which does not include user management options.
  • If COUSR03C is started without a COMMAREA (EIBCALEN = 0), it immediately transfers control to COSGN00C, preventing unauthorized direct invocation.
Note: COUSR03C itself does not perform an explicit CDEMO-USER-TYPE check. Security is enforced by the menu routing layer — only admin users can reach this program through normal navigation.

9.2 Data Access Authorization

No additional data-level authorization checks are performed within COUSR03C. Any user who reaches this program (i.e., an admin) can delete any user record from the USRSEC file, including other admin accounts. There is no self-deletion prevention (an admin could delete their own user ID).

9.3 Audit Trail

COUSR03C does not implement explicit audit logging. The only diagnostic output is the DISPLAY statement for unexpected RESP codes, which writes to the CICS CEEMSG/CESE log. No record of which admin deleted which user is captured.

Gap: The absence of audit logging for user deletion is a significant security concern. In a production environment, deletion of security credentials should be logged with the admin's identity, timestamp, and the deleted user ID.

10.2 Performance Considerations

  • UPDATE lock duration: The READ with UPDATE acquires a record-level lock on the USRSEC file. If the user delays pressing PF5 after the fetch, this lock is held across the pseudo-conversational boundary (CICS releases locks at task end, but the DELETE expects the lock from the same task — the program re-reads with UPDATE on PF5). In practice, the lock is released between iterations, and PF5 re-acquires it via DELETE-USER-INFO calling READ-USER-SEC-FILE again.
  • No browse operations: This program uses only direct keyed access — no STARTBR/READNEXT loops that could cause performance concerns.
  • Minimal CPU: No complex data transformations, calculations, or string processing beyond the simple STRING for the success message.

12.1 Known Issues

#IssueSeverityDetails
KI-1No audit logging for deletionsHighNo record is kept of which admin deleted which user. Only DISPLAY for unexpected errors is present.
KI-2No self-deletion preventionMediumAn admin can delete their own user ID, potentially locking themselves out of the system.
KI-3Misleading error message on DELETE failureLowDELETE-USER-SEC-FILE OTHER branch says "Unable to Update User…" instead of "Unable to Delete User…" — copy-paste artifact.
KI-4No confirmation dialog beyond PF5LowDeletion is immediate upon PF5 — there is no "Are you sure?" secondary confirmation. The two-step fetch-then-delete provides some protection.
KI-5Hardcoded file nameLowWS-USRSEC-FILE is hardcoded to 'USRSEC ' in WORKING-STORAGE rather than being externally configurable.
KI-6No cascading deleteMediumDeleting a user from USRSEC does not remove any related data from other files (e.g., no check if the user has active sessions or associated records).
