Business Flow Analysis

1.1 Business Context

The Bill Payment transaction (CB00) allows a cardholder to pay their account balance in full via the online CICS terminal interface. The user enters an Account ID, the system retrieves the current balance from the ACCTDAT file, and after the user confirms with Y, the program creates a new transaction record in the TRANSACT file and sets the account balance to zero. This is a same-session, real-time payment — no batch cycle is required.

Who uses it: Regular cardholders (user type U) via menu option 10 on the Main Menu (COMEN01C).
When: When a cardholder wants to clear their outstanding balance.
Business outcome: Account balance is zeroed and a bill-payment transaction record is persisted for audit and reporting.

7.2 Return Code Conventions

No explicit return codes are passed back in the COMMAREA. The program uses WS-RESP-CD and WS-REAS-CD internally to capture CICS RESP/RESP2 values. Error conditions are communicated to the user via WS-MESSAGE displayed in the ERRMSG field.

7.3 Conversation State Management

  • State flag: CDEMO-PGM-CONTEXT — 0 on first entry, set to 1 (CDEMO-PGM-REENTER) after initial screen send.
  • Preserved via: EXEC CICS RETURN TRANSID('CB00') COMMAREA(CARDDEMO-COMMAREA) — the entire COMMAREA is passed back to CICS and returned on the next terminal input.
  • Pre-selection: If CDEMO-CB00-TRN-SELECTED is populated on first entry, the program auto-fills the Account ID and runs PROCESS-ENTER-KEY immediately.
  • Confirmation flag: WS-CONF-PAY-FLG tracks whether the user has confirmed — not persisted across iterations; re-evaluated each time from CONFIRMI.

Security and Authorization

9.1 Transaction Security

  • Authentication gate: If EIBCALEN = 0 (no COMMAREA), the program immediately XCTLs to COSGN00C (Sign-On), preventing unauthenticated access.
  • Menu-level control: Bill Payment is menu option 10, marked with user type 'U' in COMEN02Y.cpy, meaning both regular users and admins can access it.
  • No RACF/security commands: The program does not issue any EXEC CICS QUERY SECURITY or VERIFY PASSWORD commands. Access control relies on the sign-on gate and menu routing.

9.2 Data Access Authorization

No data-level authorization checks are performed within the program. Any authenticated user who reaches the Bill Payment screen can pay any account by entering its Account ID. There is no validation that the account belongs to the logged-in user (CDEMO-USER-ID is not checked against the account ownership).

Security observation: The program allows payment on any account ID, not just accounts belonging to the current user. In a production system this would be a significant authorization gap.

9.3 Audit Trail

Each bill payment creates a TRAN-RECORD in the TRANSACT file with:

  • Unique TRAN-ID (sequentially generated)
  • TRAN-TYPE-CD = '02' (bill payment type)
  • TRAN-DESC = 'BILL PAYMENT - ONLINE'
  • TRAN-ORIG-TS and TRAN-PROC-TS — timestamps from ASKTIME/FORMATTIME
  • TRAN-CARD-NUM — the card associated with the account
  • TRAN-AMT — the payment amount (= prior balance)

However, the user ID who initiated the payment is not recorded in the transaction record, which limits post-hoc auditability.

10.2 Performance Considerations

  • UPDATE lock held across user think-time: The READ ACCTDAT with UPDATE option acquires an exclusive lock. When the confirm flag is Y, both READ (UPDATE) and REWRITE happen in the same iteration, which is acceptable. However, if the CONFIRM is SPACES (initial lookup), the record is read with UPDATE but never rewritten in that iteration — the lock is released only when the task ends (pseudo-conversational RETURN).
  • STARTBR/READPREV for ID generation: Reading backwards from HIGH-VALUES to find the last transaction ID is an O(1) operation on a KSDS (positions at end, reads one record). This is efficient but creates a serialization point for concurrent bill payments.
  • No browse loops: Only a single READPREV is issued, so there is no risk of run-away browsing.
  • Small record sizes: ACCOUNT-RECORD (300 bytes), CARD-XREF-RECORD (50 bytes), TRAN-RECORD (350 bytes) — all well within efficient I/O ranges.
