1. Business purpose

On the Tesco Bank Clubcard Credit Card platform every card transaction (purchase, cash, payment, refund) carries a transaction type & category code, and every credit card account belongs to an interest-rate (APR) pricing group — CardDemo's disclosure group. This weekly chain keeps both sets of reference data current.

Transaction types are held twice. The master copy is in the DB2 tables CARDDEMO.TRANSACTION_TYPE and CARDDEMO.TRANSACTION_TYPE_CATEGORY, which colleagues maintain online (CTLI / CTTU) and in batch (MNTTRDB2). The second copy is a pair of 60-byte flat files that the base application loads into VSAM for transaction reporting; the module README calls this a "Dual Storage Strategy" in which TRANEXTR "creates VSAM-compatible files" (app/app-transaction-type-db2/README.md:139-142). Each Saturday the chain:

  • applies the week's batch add / update / delete records to the DB2 transaction-type table (MNTTRDB2);
  • backs up last week's extracts to GDGs and re-extracts both DB2 tables to their flat files (TRANEXTR);
  • rebuilds the APR pricing-group KSDS DISCGRP.VSAM.KSDS — the rate table the monthly interest charge reads — from its flat-file seed, with the cardholder-facing CICS files closed around the rebuild (CLOSEFIL → DISCGRP → WAITSTEP → OPENFIL).

If it does not run: batch transaction-type changes are not applied, DB2 changes never reach the flat files that feed the VSAM reference files used by transaction reporting, and the pricing-group KSDS is not rebuilt. If it stalls between CLOSEFIL and OPENFIL, the five CICS files (TRANSACT, CCXREF, ACCTDAT, CXACAIX, USRSEC) stay closed: colleague sign-on (USRSEC) and every VSAM-backed online card-account function is unavailable until an operator reopens them.

Gating conditions (Control-M, app/scheduler/CardDemo.controlm):
  • MNTTRDB2 has no INCOND; on completion it adds WEEKLY-TransactionTypesDBRefresh-MNTTRDB2 (ODATE=ODAT, SIGN=+) (:27-28).
  • TRANEXTR (:58-59) and CLOSEFIL (:33-34) each have that condition as their only INCOND (AND_OR="A"), so one event releases both smart folders, which then run in parallel.
  • Inside DisclosureGroupsRefresh each job adds its own WEEKLY-DisclosureGroupsRefresh-<job> condition and deletes its predecessor's (:35, 39-41, 45-47, 51-52).
  • Each smart folder also carries a folder-level OUTCOND …-MNTTRDB2 SIGN="-" (:55, :62), so whichever folder ends first deletes the condition the other may still need (Q-01).
  • No job has ON / DO statements, so a non-zero completion code is judged by the site's Control-M default, which is not in the repo (Q-08). TIMETO="23:00" is the latest submission time, not a completion deadline.
  • JCL step gating: TRANEXTR STEP20/30/40 COND=(0,NE), STEP50 COND=(4,LT) (app/app-transaction-type-db2/jcl/TRANEXTR.jcl:42,53,65,95). MNTTRDB2 and DISCGRP have no COND= on any step.
Scheduler sources: this chain exists only in Control-M; app/scheduler/CardDemo.ca7 has no LJOB for MNTTRDB2, TRANEXTR or DISCGRP, and its CLOSEFIL / WAITSTEP / OPENFIL entries belong to other networks (SCHID 030/031/032). The two schedulers also disagree on the daily chain — CA-7 SCHID=030 is CLOSEFIL → CBPAUP0J → POSTTRAN → WAITSTEP → OPENFIL (CardDemo.ca7:43,70,97,124, no TRANBKP anywhere in the file) while Control-M DAILY-TransactionBackup is CLOSEFIL → TRANBKP → WAITSTEP → OPENFIL (CardDemo.controlm:3-25). This document records each as written and does not merge them (Q-03).

6.3 Restart / checkpoint semantics

  • No job in the chain takes checkpoints.
  • COBTUPDT issues no COMMIT or ROLLBACK (none in COBTUPDT.cbl), so all successful statements commit together when the IKJEFT01 step ends normally.
  • Rerunning MNTTRDB2 with the same INPFILE is not idempotent: applied A records now fail as duplicates, D records fail with +100, and the job ends RC 4.
  • TRANEXTR is restartable at STEP40 once STEP30 has run, not from STEP10.
  • DISCGRP is fully rerunnable from STEP05; CLOSEFIL, WAITSTEP and OPENFIL are idempotent.
  • Control-M allows up to 5 reruns per job (MAXRERUN="5").
