DailyTransactionBackup Batch

Daily transaction file backup & re-define. In the overnight batch, close the card-platform CICS files, copy the Clubcard Credit Card transaction master AWS.M2.CARDDEMO.TRANSACT.VSAM.KSDS to a new TRANSACT.BKUP generation, delete the master and re-define it empty, wait 36 seconds, then re-open the files to colleagues and cardholders. No CardDemo business rules (pricing, interest, statements) run in this chain. Its requirements cover data safety, ordering and online availability.

1. Business purpose

For Tesco Bank, the CardDemo transaction master TRANSACT holds the posted Clubcard Credit Card transactions: purchases, cash, payments and refunds. Each record carries the 16-digit card number, the merchant and the amount (app/cpy/CVTRA05Y.cpy:4-18). Colleagues and cardholders read the file online through CICS FILE(TRANSACT) (app/csd/CARDDEMO.CSD:76-77). CICS keeps no journal or recovery log for it: the file is defined JOURNAL(NO), RECOVERY(NONE), BACKUPTYPE(STATIC) (app/csd/CARDDEMO.CSD:82-85). The overnight posting programme CBTRN02C opens the master OUTPUT (app/cbl/CBTRN02C.cbl:256), so each posting run replaces the file rather than adding to it.

This chain takes a copy of the master before it is replaced. TRANBKP (job card "REPRO and Delete Transaction Master", app/jcl/TRANBKP.jcl:1) copies every record to a new generation of the AWS.M2.CARDDEMO.TRANSACT.BKUP generation data group (GDG). It then deletes the cluster and its alternate index and re-defines the cluster empty (app/jcl/TRANBKP.jcl:23-67). CLOSEFIL and OPENFIL run before and after it so that CICS region CICSAWSA does not hold the dataset while IDCAMS deletes it (app/jcl/CLOSEFIL.jcl:26-30, app/jcl/OPENFIL.jcl:26-30). They also close and re-open the credit card account file (ACCTDAT), the card-to-account-to-customer link (CCXREF, and its account-key path CXACAIX) and colleague sign-on (USRSEC). WAITSTEP adds a fixed 36-second pause before the files are re-opened (app/jcl/WAITSTEP.jcl:20-26).

If the chain does not run:

  1. The next posting run overwrites the card transaction master and no copy of its earlier content exists.
  2. The monthly interest charge cycle's COMBTRAN step, which sorts TRANSACT.BKUP(0) (app/jcl/COMBTRAN.jcl:23-24), works from an old generation.
  3. If CLOSEFIL ran but OPENFIL did not, the five files stay closed to CICS. Colleague sign-on, account and card look-ups and transaction screens then fail until someone re-opens the files by hand.
Business capabilityHow this stream serves it
Card transaction history retentionKeeps the most recent images of the posted-transaction master as GDG generations TRANSACT.BKUP(+1); the GDG base is LIMIT(5) (app/jcl/DEFGDGB.jcl:24-28). The sample catalogue lists five active generations, G0072–G0076 (app/catlg/LISTCAT.txt:1631-1643).

Monthly interest chargeProvides the TRANSACT.BKUP(0) input that COMBTRAN merges with SYSTRAN(0) (the interest and fee transactions INTCALC generates) and reloads into the master (app/jcl/COMBTRAN.jcl:22-48).
Online card servicing for colleagues and cardholdersCloses and re-opens TRANSACT, CCXREF, ACCTDAT, CXACAIX and USRSEC in CICSAWSA so that batch and CICS never use the datasets at the same time (app/jcl/CLOSEFIL.jcl:26-30, app/jcl/OPENFIL.jcl:26-30). This is the outage window that an operational-resilience impact tolerance would measure (NFR-07).

Gating conditions: Control-M releases each job on its predecessor's OUT condition for the same ODATE, and the successor deletes that condition when it runs. CLOSEFIL adds DAILY-TransactionBackup-CLOSEFIL (app/scheduler/CardDemo.controlm:5). TRANBKP waits on it, deletes it and adds DAILY-TransactionBackup-TRANBKP (:9-11). WAITSTEP waits on that, deletes it and adds DAILY-TransactionBackup-WAITSTEP (:15-17). OPENFIL waits on that and deletes it without adding another (:21-22). The folder has no ON/DO, MAXRC or TIMEFROM statements, so a successor is released when its predecessor ends OK under the site default (Q-02). No return-code value is tested between jobs.

Inside TRANBKP the only step gate is STEP10 EXEC PGM=IDCAMS,COND=(4,LT) (app/jcl/TRANBKP.jcl:51): the re-define is bypassed if any earlier step ended above RC 4. The DELETE step has no COND (:37) and runs whatever the REPRO returned.

The two schedulers disagree. CA-7 has no TRANBKP. Its SCHID=030 daily network is CLOSEFIL → CBPAUP0J → POSTTRAN → WAITSTEP → OPENFIL (triggers at app/scheduler/CardDemo.ca7:43, :70, :97, :124; OPENFIL "N -- COMP TRIGGERS OTHER JOBS" at :138). This Control-M folder has TRANBKP and no POSTTRAN. This document describes the Control-M folder as written and does not assume the two are one combined chain (Q-01).

FR-01Before the backup starts, the five CICS files TRANSACT, CCXREF, ACCTDAT, CXACAIX and USRSEC are closed in region CICSAWSA, so no colleague or cardholder task holds the card transaction master open.app/jcl/CLOSEFIL.jcl:22-30When TRANBKP starts, online access to the transaction store is disabled (legacy: CEMT INQ FIL(TRANSACT) shows CLOSED) and stays disabled until OPENFIL runs.

FR-03Each successor deletes the condition that released it (OUTCOND SIGN="-"), so one predecessor completion releases exactly one successor run.app/scheduler/CardDemo.controlm:10, :16, :22After OPENFIL ends, no DAILY-TransactionBackup-* condition remains for that ODATE. FR-04The whole card transaction master is copied to a new backup generation before any record is deleted. The copy is unfiltered.app/jcl/TRANBKP.jcl:23-33 (STEP05R before STEP05 at :37); app/ctl/REPROCT.ctl:15The record count and byte content of TRANSACT.BKUP(+1) equal the master as it stood when CLOSEFIL completed, in ascending TRAN-ID order.
FR-05The backup is a new catalogued generation of fixed 350-byte records. If the copy step abends, the new generation is deleted. If REPRO ends with a non-zero RC but does not abend, the generation is still catalogued.app/jcl/TRANBKP.jcl:29-33 (DISP=(NEW,CATLG,DELETE))After a successful run the GDG has one more generation: LRECL 350, RECFM FB, layout CVTRA05Y. After an abended copy step, no new generation is catalogued. After a non-abend REPRO failure, a generation exists that may be partial (Q-09).
FR-06At most five backup generations are kept. A sixth rolls the oldest off.app/jcl/DEFGDGB.jcl:24-28After six consecutive successful runs exactly five generations are active and the earliest is no longer available as a relative generation. Whether it is also scratched depends on Q-03.
FR-07Downstream readers use the newest generation, whichever job wrote it. COMBTRAN reads TRANSACT.BKUP(0), and TRANREPT writes (+1) to the same GDG.app/jcl/COMBTRAN.jcl:23-24; app/jcl/TRANREPT.jcl:29-33A migrated backup store exposes a "latest generation". After TRANIDX, a read through the path by a TRAN-PROC-TS value returns every record with that timestamp, duplicates included.

FR-16The folder is ordered every calendar day of every month. Each job can be submitted until 23:00 on its ODATE and stays eligible for up to 7 days while it waits for its IN condition.app/scheduler/CardDemo.controlm:4, :8, :14, :20 (DAYS="ALL", JAN..DEC="1", TIMETO="23:00", MAXWAIT="7", MAXRERUN="5")The migrated schedule triggers the chain every day, including weekends and UK bank holidays. A job whose predecessor has not completed by 23:00 is not submitted that day and is held for up to 7 days. There are at most five automatic reruns.
FR-17No release decision between jobs depends on a numeric return code. A job that ends OK releases its successor; a job that does not end OK stops the chain. FR-18TRANBKP is not idempotent. A rerun after a successful copy creates another generation holding the now-empty master. That generation becomes BKUP(0) and pushes the real backup back one generation.app/jcl/TRANBKP.jcl:29-33 (unconditional (+1))Rerun behaviour is documented and tested. Either the migrated backup is idempotent per ODATE (preferred; the deviation needs sign-off, Q-09), or the runbook forbids a rerun once STEP05R has succeeded.
FR-19CICS keeps no journal or recovery log for TRANSACT, so the TRANBKP generation is the only point-in-time copy of posted card transactions. It must stay readable for the retention period.app/csd/CARDDEMO.CSD:76-85 (JOURNAL(NO), RECOVERY(NONE), BACKUPTYPE(STATIC))The migrated backup survives loss of the primary store and can restore the master to its CLOSEFIL-time state for any of the last five cycles.

6. Restart, recovery & error handling

6.1 Return-code conventions

RCMeaningDownstream effect
TRANBKP STEP05R RC 0REPRO copied every record to BKUP(+1) (app/jcl/TRANBKP.jcl:23-33).STEP05 and STEP10 run; the job ends OK; WAITSTEP is released.
TRANBKP STEP05R RC 4IDCAMS warning. The exact condition (for example an empty input) cannot be determined from the repo (Q-10).STEP10's COND=(4,LT) is not met, so the define still runs (:51). The job ends MAXCC 4. Control-M releases WAITSTEP if the site default treats RC 4 as OK (Q-02).
TRANBKP STEP05R RC 8–12REPRO failed without abending (for example an open or I/O error).The step ends normally, so BKUP(+1) is still catalogued, possibly partial (:29). STEP05 DELETE still runs because it has no COND (:37), so the master is deleted. STEP10 is bypassed (:51). 6.3 Restart / checkpoint semantics

There is no checkpoint and no commit interval. Each step is a single IDCAMS or SDSF invocation that either completes or does not. The JCL implies these restart rules:

  1. CLOSEFIL, WAITSTEP and OPENFIL can be rerun at any time without side effects (app/jcl/CLOSEFIL.jcl:26-30, app/jcl/WAITSTEP.jcl:22-26, app/jcl/OPENFIL.jcl:26-30).
  2. If TRANBKP STEP05R abended, the new generation is not kept (third DISP parameter DELETE, app/jcl/TRANBKP.jcl:29) and the later steps did not run, so it can be rerun from the top. If STEP05R ended with a non-zero RC without abending, the generation is catalogued and STEP05 has already deleted the master (:37). Uncatalogue that generation, restore the master from the previous one, then rerun.
  3. If TRANBKP failed in STEP10, restart at STEP10 only: the backup generation exists and the master is already gone. A rerun from the top would REPRO a missing or empty cluster and use up a generation (FR-18).
  4. Control-M allows MAXRERUN 5 and MAXWAIT 7 (app/scheduler/CardDemo.controlm:8) but defines no DO RERUN action. The JCL has no RESTART= parameter, so a step-level restart is an operator action.
  5. The recovery copy is the newest good generation, normally TRANSACT.BKUP(0). Restore sequence: DEFINE CLUSTER as in app/jcl/TRANBKP.jcl:54-67 → REPRO from the generation (following app/jcl/COMBTRAN.jcl:41-48) → TRANIDX (app/jcl/TRANIDX.jcl:22-54). The repo has no backout job.
