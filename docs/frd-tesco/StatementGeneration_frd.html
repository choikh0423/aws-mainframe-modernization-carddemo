StatementGeneration Batch

Monthly card statement run for the Clubcard Credit Card portfolio: customer statement generation (text / HTML / PDF). CA-7 network SCHID=030: CLOSEFIL → CREASTMT → TXT2PDF1 → WAITSTEP → OPENFIL. 1. Business purpose

For Tesco Bank this chain is the monthly card statement run for Clubcard Credit Card cardholders. It produces one statement for every Clubcard Credit Card in the card-to-account-to-customer link file (CARDXREF). CREASTMT takes the card transactions file (purchases, cash, payments and refunds held in AWS.M2.CARDDEMO.TRANSACT.VSAM.KSDS), re-keys it by card number so each card's transactions sit together, and runs the business programme CBSTM03A. For each card, that program reads the cardholder (CUSTDATA) and the credit card account (ACCTDATA), and writes the statement twice: as fixed 80-column plain text (STATEMNT.PS) and as 100-column HTML (STATEMNT.HTML) (app/jcl/CREASTMT.JCL:19-20, 79-96; app/cbl/CBSTM03A.CBL:8-9). TXT2PDF1 then renders the text statement to STATEMNT.PS.PDF with the TSO TXT2PDF utility (app/jcl/TXT2PDF1.JCL:21, 38-39).

The statement programme reads VSAM files that the online CICS region also serves, so the chain starts with CLOSEFIL and ends with OPENFIL. These take the CICS files offline and bring them back online, with a timed WAITSTEP before the re-open (app/jcl/CLOSEFIL.jcl:26-30; app/jcl/WAITSTEP.jcl:20-26; app/jcl/OPENFIL.jcl:26-30). While the files are closed, colleagues cannot service cardholders on the online screens that use them.

Under the Consumer Credit Act 1974, s.78(4), a creditor under a running-account agreement such as a credit card must give the debtor periodic statements. This chain is where CardDemo creates statement content. What it produces is narrower than a regulatory statement, though: name, address, account number, current balance, credit score, an itemised transaction list and a total. It has no statement date or period, credit limit, minimum payment, payment due date, APR or interest charged, or minimum-payment and persistent-debt messaging. This FRD specifies only what the source does and lists the regulatory gaps as open questions (Q-20 to Q-23).

If the chain does not run, the cycle gets no statements in any format (text, HTML or PDF), and the previous cycle's statement datasets stay catalogued until the next successful STEP030. If the chain starts but never reaches OPENFIL, the five CICS files stay closed and every online function that uses them fails until an operator re-opens them.

Gating conditions: The chain is a CA-7 trigger network, not a calendar schedule. Each job is released when its predecessor completes (TRIGGERED JOBS ... SCHID=030 QTM=0100 LEADTM=0000): CLOSEFIL→CREASTMT (CardDemo.ca7:465-468), CREASTMT→TXT2PDF1 (:494-495), TXT2PDF1→WAITSTEP (:521-522) and WAITSTEP→OPENFIL (:524-527). Inside CREASTMT, STEP020, STEP030 and STEP040 carry COND=(0,NE), so they are bypassed as soon as any earlier step ends with RC ≠ 0 (CREASTMT.JCL:56, 66, 79). DELDEF01 and STEP010 have no COND. TXT2PDF1's only step carries COND=(0,NE) (TXT2PDF1.JCL:26), which has no effect on the first step of a job. The listing shows no "good completion" RC requirement, so the repo does not say whether a non-zero CREASTMT still releases TXT2PDF1 (Q-05). CREASTMT and TXT2PDF1 are both flagged Y -- JOB MARKED AS MAINT ONLY (CardDemo.ca7:480, 507), so CA-7 does not track their dataset requirements. STATEMNT.PS is therefore not a CA-7 input requirement for TXT2PDF1, and only the job trigger orders them (Q-18).

Scheduler sources disagree on the daily chain, and that chain is documented here as written, not combined: In CA-7, SCHID=030 also holds the daily chain CLOSEFIL→CBPAUP0J→POSTTRAN→WAITSTEP→OPENFIL (CardDemo.ca7:18-147, and CardDemo.ca7 has no TRANBKP anywhere). The Control-M DAILY-TransactionBackup chain is CLOSEFIL→TRANBKP→WAITSTEP→OPENFIL, with no POSTTRAN (app/scheduler/CardDemo.controlm:3-25). StatementGeneration exists only in CA-7. CardDemo.controlm has no CREASTMT or TXT2PDF1 job, so this chain has no Control-M IN/OUT conditions (Q-01, Q-02). The dotted edge is the trigger listed in the OPENFIL block at CardDemo.ca7:529-532 (CLOSEFIL, SCHID=031), while the full OPENFIL block says N -- COMP TRIGGERS OTHER JOBS (:138) (Q-04).

6.3 Restart / checkpoint semantics

The chain has no checkpoints, commits or restart keys. CREASTMT is a full rebuild. DELDEF01 deletes and redefines the work store (CREASTMT.JCL:22-39), STEP010 / STEP020 recreate it (:44-62), STEP030 deletes the previous outputs (:66-75), and STEP040 creates them anew with DISP=(NEW,CATLG,DELETE), so an abend leaves no partial statement files (:87-96). The only valid restart point is the top of CREASTMT; restarting at STEP040 needs STEP030 rerun first (section 6.2). CBSTM03A holds the whole transaction set in working storage and writes statements only after loading it (CBSTM03A.CBL:730-761, 818-853, 316-329), so there is no in-flight state to recover. All four VSAM inputs are opened INPUT (CBSTM03B.CBL:136, 160, 184, 209), so no backout job exists or is needed. CLOSEFIL, WAITSTEP and OPENFIL are stateless and idempotent. There is no "already ran this cycle" guard: a second run regenerates the same statements, and if they had already been sent, cardholders could get duplicates. In the target, rerun identity comes from the job parameters (the business run date) (docs/migration/CardDemo_target_state.md:98).
