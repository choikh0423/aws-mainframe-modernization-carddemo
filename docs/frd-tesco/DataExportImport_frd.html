1. Business purpose

For Tesco Bank this chain is the portfolio data transfer (migration feed) of the Clubcard Credit Card platform (assumption A-02). It takes a full copy of the card book and turns it back into the platform's standard record layouts on the receiving side. CBEXPORT reads every cardholder (CUSTDAT), credit card account (ACCTDAT: balance, credit limit, cash limit), card-to-account-to-customer link (CCXREF), card transaction (TRANSACT) and Clubcard Credit Card plastic (CARDDAT), in that order. It writes them all to one file, AWS.M2.CARDDEMO.EXPORT.DATA. Every record carries a one-byte type code, a run timestamp, a running sequence number and a fixed branch/region stamp (app/cbl/CBEXPORT.cbl:8-10, app/cbl/CBEXPORT.cbl:27-30, app/cpy/CVEXPORT.cpy:9-19). CBIMPORT reads that file, routes each record on its type byte, and writes one flat file per entity. Records of an unknown type go to an error file (app/cbl/CBIMPORT.cbl:8-11, app/cbl/CBIMPORT.cbl:28-32).

The chain is run by hand. No CA-7 job, CA-7 trigger or Control-M folder names CBEXPORT, CBIMPORT or FTPJCLS, and the README batch run book (README.md:207-230) does not list them. The index gives the sequence as CBEXPORT → FTPJCL → CBIMPORT, but the source does not support it. The only real hand-off is the shared dataset: CBEXPORT writes AWS.M2.CARDDEMO.EXPORT.DATA (app/jcl/CBEXPORT.jcl:62-63) and CBIMPORT reads the same DSN (app/jcl/CBIMPORT.jcl:28-29). app/jcl/FTPJCL.JCL (job card FTPJCLS) PUTs an unrelated dataset, 'AWS.M2.CARDEMO.FTP.TEST', in ASCII mode (app/jcl/FTPJCL.JCL:36, :40). This FRD therefore shows the verified chain as CBEXPORT → CBIMPORT, with FTPJCL as a disconnected step (Q-06).

If the chain does not run, no portfolio copy is produced and a planned transfer or platform migration cannot proceed. The overnight batch, monthly card statements and monthly interest charges are not affected. CBEXPORT opens the masters INPUT only (app/cbl/CBEXPORT.cbl:200-233), and CBIMPORT writes new sequential datasets, never the VSAM masters (app/cbl/CBIMPORT.cbl:43-71, app/jcl/CBIMPORT.jcl:33-60). The chain contains no Clubcard points logic and no currency handling: amounts are moved as unitless numbers.

Gating conditions: There are no scheduler release rules. No CA-7 job or TRIGGERED JOBS entry names CBEXPORT, CBIMPORT or FTPJCLS (app/scheduler/CardDemo.ca7, 570 lines), and no Control-M INCOND/OUTCOND refers to them (app/scheduler/CardDemo.controlm, 92 lines). CBEXPORT STEP02 runs whatever STEP01 returns (app/jcl/CBEXPORT.jcl:24-43), and SET MAXCC = 0 hides the "cluster not found" from a first-run DELETE (app/jcl/CBEXPORT.jcl:27-28). Neither COBOL program sets RETURN-CODE. Success is GOBACK (app/cbl/CBEXPORT.cbl:158, app/cbl/CBIMPORT.cbl:171), and failure is an LE abend through CALL 'CEE3ABD' (app/cbl/CBEXPORT.cbl:579, app/cbl/CBIMPORT.cbl:484). FTPJCLS has no dataset dependency on either job (dashed lines). The chain is not wrapped in CLOSEFIL/OPENFIL (Q-07).

6.3 Restart / checkpoint semantics

Neither program has checkpoints, commit intervals or a restart key. Both are single-pass, read-to-end-of-file programs that open their outputs OUTPUT (app/cbl/CBEXPORT.cbl:235, app/cbl/CBIMPORT.cbl:205-245), so a restart is always a cold rerun from the first step. For CBEXPORT, the IDCAMS step guarantees a clean cluster (app/jcl/CBEXPORT.jcl:27-38). For CBIMPORT, the operator must first delete the catalogued outputs. No backout is needed because the chain never updates a master. A re-export gets a new run timestamp and restarts the sequence at 1 (app/cbl/CBEXPORT.cbl:123, :172-195). The target behaves differently: both Spring Batch steps are chunk-oriented (chunk 100) and restartable through the JobRepository. The writers save their byte position in the ExecutionContext and truncate back to it on reopen (docs/migration/streams/DataExportImport/DataExportImport_migration_plan.md §1).

NFR-07ConsistencyCBEXPORT reads masters that CICS may have open (DISP=SHR, outside any CLOSEFIL window), so a point-in-time snapshot of the card book is not guaranteed (Q-07).
NFR-08Operational resilience (FCA PS21/3, PRA SS1/21)The chain updates no master and is not scheduled, so it does not sit on the path of a card-servicing important business service. If Tesco Bank Operational Resilience classes a portfolio migration as one, its impact tolerance must be set for the transfer (A-04). The repo defines none.
NFR-09Record keeping (FCA SYSC 9, MLR 2017)The export file and the SYSOUT statistics are the only record that a transfer took place. CBEXPORT recreates the file on every run (app/jcl/CBEXPORT.jcl:27-38), and no GDG or archive keeps a prior copy. Retention of the transfer evidence, and of the transaction history it carries (MLR 2017: five years), must be decided (Q-15).

Transfer credentialsFTPJCL carries the host, user ID and a clear-text password as in-stream SYSIN cards (app/jcl/FTPJCL.JCL:33-35). The transfer is plain FTP in ASCII mode, not FTPS/SFTP (app/jcl/FTPJCL.JCL:30, 36). The target does not reproduce the credentials or the transfer.
Regulatory obligationsThe repo defines none; the following apply to a bulk extract of this content. PCI DSS v4.0: the file is in cardholder-data scope. Storing CVV after authorisation is prohibited (Req. 3.3.1), PAN must be unreadable wherever stored (Req. 3.5.1) and protected with strong cryptography in transit over open networks (Req. 4.2.1), and the hard-coded FTP password conflicts with Req. 8.6.2. UK GDPR / DPA 2018: the transfer needs a lawful basis and must be limited to what the purpose needs (Art. 5(1)(b)-(c), Art. 6). It needs appropriate security of processing (Art. 32), and, if the receiving host is outside the UK, a restricted-transfer mechanism (Art. 44-46). A DPIA is likely for a whole-book migration (Art. 35). Tesco Bank Data Protection Office to confirm. MLR 2017: transaction records must be kept for five years (reg. 40), which affects how long transfer evidence is retained (Q-15). FCA SYSC 9: keep orderly records of the transfer. PRA SS2/21: applies if the receiving party is a third-party service provider (A-03). FCA Consumer Duty (PRIN 2A), CONC and CCA 1974 (s.77A / s.78(4) statements): no direct requirement, because the chain makes no credit, pricing or statement decision. The receiving platform must keep account balances and limits intact so that statements and arrears handling stay correct after migration (FR-12).
