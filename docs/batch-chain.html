CardDemo · batch reference

Nightly batch chain (CA-7)

Built from app/scheduler/CardDemo.ca7, app/jcl/*, app/cbl/CBTRN02C.cbl, README.md and scripts/run_full_batch.sh. Line numbers refer to those files as committed.

1Overview

The CardDemo nightly chain (called CARDNITE in this doc) is the set of CA-7 scheduled jobs defined in app/scheduler/CardDemo.ca7. Every leg follows the same pattern:

  1. Quiesce CICS. CLOSEFIL sends CEMT SET FIL(...) CLO to region CICSAWSA via SDSF, so batch can update the VSAM files that the online application normally holds open (TRANSACT, CCXREF, ACCTDAT, CXACAIX, USRSEC).
  2. Do the batch work. Purge expired authorizations and post the day's transactions (leg 1). Refresh reference VSAM files and run the read/print utilities (leg 2). Produce statements (leg 3).
  3. Settle. WAITSTEP runs the COBSWAIT timer (36 seconds).
  4. Reopen. OPENFIL makes the files available to CICS again.

Interest calculation (INTCALC) and the transaction merge (COMBTRAN) are not in the CA-7 listing. They are scheduled in the Control-M definition (MONTHLY-InterestCalculation) and run in the full sequence of scripts/run_full_batch.sh. See §4.

3.5Reading the listing

  • Every job definition has the same attributes: SYSTEM-NAME=CARDDEMO, JCLLIB=&CARDDEMOPRODJCL, MSGCLASS=A, REGION=4096K, ELAPTM=2359. Every trigger has QTM=0100 LEADTM=0000.
  • Repeated jobs such as WAITSTEP, CLOSEFIL and OPENFIL usually appear as a bare 1LJOB,JOB=… header followed only by their triggers. Each one is a separate trigger context under a different SCHID or leg, not a second job definition.
  • The full OPENFIL definition (lines 126–150) shows N -- COMP TRIGGERS OTHER JOBS. Leg 3 still lists OPENFIL triggering CLOSEFIL SCHID=031 (line 532). The two can coexist only if that trigger is specific to that schedule ID. The listing doesn't say which is true.

Ordering. The 102 and 103 checks are two separate IFs that both run after a successful account read. When a transaction is both over limit and after expiry, 103 overwrites 102 and the reject record shows 103.

6.4Posting steps (2000-POST-TRANSACTION, line 424)

The program first copies the DALYTRAN fields into TRAN-RECORD (CVTRA05Y): id, type, category, source, description, amount, merchant id/name/city/zip, card number and original timestamp. It then sets TRAN-PROC-TS from Z-GET-DB2-FORMAT-TIMESTAMP (current date in YYYY-MM-DD-HH.MM.SS.mmm0000 form). Three steps follow:

  1. Update TCATBALF — 2700-UPDATE-TCATBAL (467). Key = XREF-ACCT-ID + DALYTRAN-TYPE-CD + DALYTRAN-CAT-CD.
    • Not found (status 23): 2700-A-CREATE-TCATBAL-REC runs INITIALIZE, sets TRAN-CAT-BAL = DALYTRAN-AMT and does a WRITE. It also displays 'TCATBAL record not found for key : … Creating.'
    • Found: 2700-B-UPDATE-TCATBAL-REC adds the amount to TRAN-CAT-BAL and does a REWRITE.
    • Any other status abends the program.
  2. Update account balance — 2800-UPDATE-ACCOUNT-REC (545). 
    ADD DALYTRAN-AMT TO ACCT-CURR-BAL
IF DALYTRAN-AMT >= 0   ADD DALYTRAN-AMT TO ACCT-CURR-CYC-CREDIT
ELSE                   ADD DALYTRAN-AMT TO ACCT-CURR-CYC-DEBIT
REWRITE FD-ACCTFILE-REC FROM ACCOUNT-RECORD
    A REWRITE INVALID KEY sets reason 109 / 'ACCOUNT RECORD NOT FOUND'. Posting has already been decided at that point, so the code is not checked: the transaction is still written and is not counted as a reject.
  3. Write transaction record — 2900-WRITE-TRANSACTION-FILE (562) runs WRITE FD-TRANFILE-REC FROM TRAN-RECORD. Any status other than 00, a duplicate key for example, abends the program.

7Downstream jobs

INTCALC · app/jcl/INTCALC.jcl

CBACT04C with PARM='2022071800' reads the TCATBALF balances that POSTTRAN built. For each balance it looks up the disclosure-group rate in DISCGRP and falls back to group DEFAULT on status 23. Monthly interest is TRAN-CAT-BAL × DIS-INT-RATE / 1200, written as system transactions to SYSTRAN(+1). For each account it adds the total interest to ACCT-CURR-BAL and resets CYC-CREDIT/CYC-DEBIT to 0. Fees (1400-COMPUTE-FEES) are "To be implemented".

COMBTRAN · app/jcl/COMBTRAN.jcl

Merges TRANSACT.BKUP(0) and SYSTRAN(0) with a SORT on TRAN-ID into TRANSACT.COMBINED(+1), then runs IDCAMS REPRO into TRANSACT.VSAM.KSDS. This puts the interest transactions into the transaction master next to the posted daily ones.

CREASTMT · app/jcl/CREASTMT.JCL

Sorts the transaction master into TRXFL keyed by card number + transaction id. CBSTM03A (with called subroutine CBSTM03B) then writes one statement per card in XREF, to STATEMNT.PS (text) and STATEMNT.HTML. CA-7 leg 3 follows it with TXT2PDF1.

8Discrepancies & notes

  • The chain name is ours. The string CARDNITE does not appear anywhere in this repository. The CA-7 listing does not name the chain; this doc uses the name as a label.
  • Leg 2 does not go CLOSEFIL1/2 → READCARD. Each fork branch goes through its own refresh job (TRANCATG / TCATBALF) and WAITSTEP. Both then trigger CLOSEFIL (030) → READACCT → READCARD → READCUST → READXREF.
  • CA-7 vs README. The CA-7 listing covers 15 distinct JCL members. ACCTFILE, CARDFILE, XREFFILE, CUSTFILE, TRANBKP, TRANEXTR, DISCGRP, DUSRSECJ, INTCALC, COMBTRAN and TRANIDX appear only in the README, the scripts and/or Control-M.
  • Optional-module JCL. CBPAUP0J (IMS/DB2/MQ authorizations) is in the CA-7 posting leg, but its JCL is in app/app-authorization-ims-db2-mq/jcl/, not app/jcl/. TRANEXTR is in app/app-transaction-type-db2/jcl/.
  • Hard-coded date. INTCALC passes the fixed PARM='2022071800', so it is not driven by the schedule date.
