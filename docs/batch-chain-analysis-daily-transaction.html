  • The planning chain is the union of the two. TRANBKP's placement between CLOSEFIL and CBPAUP0J is an inference, not a scheduler record. It is a hard data dependency, though: CBTRN02C opens TRANSACT OUTPUT (CBTRN02C.cbl L256), which needs the empty cluster that TRANBKP's STEP10 re-defines. TRANBKP therefore has to finish before POSTTRAN.
  • CA-7 also has a second SCHID=030 occurrence of CLOSEFIL (L159–162) that triggers TRANTYPE → WAITSTEP → CLOSEFIL1/CLOSEFIL2 (SCHIDs 031/032). That is the reference-data reload network and is out of scope here, but it re-uses the same CLOSEFIL/WAITSTEP JCL members.
  • All CA-7 job definitions in the chain show JCLLIB=&CARDDEMOPRODJCL, QTM=0100, LEADTM=0000, Y -- JOB MARKED AS MAINT ONLY.

5. Migration considerations

CICS batch-window coupling (CLOSEFIL / OPENFIL)

  • The batch window exists because VSAM files defined RLSACCESS(NO) cannot be updated by batch while CICS holds them open. Online users get NOTOPEN on TRANSACT, CCXREF, ACCTDAT, CXACAIX and USRSEC from CLOSEFIL until OPENFIL. USRSEC is closed too, which affects sign-on (COSGN00C reads USRSEC).
  • On a relational target with row-level locking and transactional batch, the close/open pair usually becomes a maintenance-mode flag or is dropped. Decide explicitly whether online stays available during posting. If it does, the posting job needs commit-interval isolation against concurrent online account updates.
  • SDSF/CEMT success is not checked in the JCL. A target replacement should verify state, for example with a health endpoint, rather than fire and forget.

IMS BMP dependency (CBPAUP0J)

  • CBPAUP0J needs a running IMS control region, the PSB/DBD libraries and the IMS-allocated database datasets. None of that is in the JCL, and all of it has to be replaced, for example with relational tables (pending_auth_summary/pending_auth_detail) or an IMS-compatible runtime.
  • The CHKP every N roots maps to a chunk commit. The IMS restart-from-checkpoint behavior maps to restartable chunked batch.
  • Parity flags to decide: the production SYSIN 00,00001,00001,Y sets expiry-days = 0. With WS-DAY-DIFF >= WS-EXPIRY-DAYS (L284), every detail qualifies for delete, and checkpoints run on every summary with debug output on. The summary-delete test reads IF PA-APPROVED-AUTH-CNT <= 0 AND PA-APPROVED-AUTH-CNT <= 0 (L156): the same field twice, where the declined count was probably intended. Preserve both as coded or log them as legacy defects; don't "fix" them silently.
  • Ordering: CA-7 runs the purge before POSTTRAN. CBTRN02C does not read the IMS database, so nothing visible in the code depends on this order. Confirm with the business before parallelizing.

GDG handling

  • TRANSACT.BKUP and DALYREJS are both LIMIT(5) SCRATCH, a rolling five-generation window. A target equivalent needs (a) generation naming (date or sequence suffix, or an object-store version), (b) automatic roll-off of the sixth generation, and (c) a relative-generation resolver for any downstream job that reads (0) or (-1).
  • DISP=(NEW,CATLG,DELETE) means a failed step leaves no generation. The target should only publish the new generation when the step succeeds.
  • TRANSACT.BKUP is the only transaction history. TRANBKP empties the master every day, so retention for audit or regulatory needs must be defined in the target. Five days is unlikely to be enough.

Packed-decimal and zoned fields (amounts, ACCNTID TYPE=P) need explicit precision/scale mapping. EBCDIC key collation differs from ASCII/UTF-8, so ordered scans (GN, sequential REPRO) can return rows in a different order on the target.

Scheduler trigger semantics (CA-7 SCHID vs Control-M INCOND/OUTCOND)

  • CA-7: job-completion triggers. On successful completion a job triggers its successors under a schedule ID (JOB=… SCHID=030 QTM=0100). The same JCL member appears under several SCHIDs (CLOSEFIL and WAITSTEP occur in both the posting and the reference-reload networks). In a target, a SCHID becomes a separate DAG or run context, not a shared node.
  • Control-M: condition-based. A job adds its own OUTCOND (SIGN="+") on OK and deletes its predecessor's condition (SIGN="-"). The successor waits on INCOND with ODATE="ODAT", so conditions are scoped to the order date. A target needs date-scoped run identity to stop yesterday's completion from releasing today's job.
  • The two definitions differ. Control-M's daily folder has no CBPAUP0J or POSTTRAN, and CA-7 has no TRANBKP. Pick one source of truth for cut-over and reconcile it with operations before the chain is rebuilt.
  • RC=4 is meaningful. CBTRN02C ends RC 4 whenever any record is rejected. Neither scheduler listing shows a condition-code rule, so check how each scheduler treats RC 4 (OK or NOTOK) in production and carry that rule into the target orchestration. Otherwise a day with rejects may block OPENFIL, or a real failure may pass.
  • WAITSTEP is a fixed 36-second sleep. In a target orchestrator this is usually replaced by an explicit readiness check, or removed.

Restart and rerun

  • TRANBKP must not be rerun after POSTTRAN has posted, because the delete/define would destroy the day's postings. POSTTRAN must not be rerun against an already-updated ACCTDATA/TCATBALF, because it would double-post. The safe restart point is "restore ACCTDATA + TCATBALF, re-run TRANBKP → POSTTRAN". Document this as the target recovery runbook.
