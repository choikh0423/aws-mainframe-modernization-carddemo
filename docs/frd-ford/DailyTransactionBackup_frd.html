DailyTransactionBackup Batch

Daily transaction file backup & re-define: quiesce the CICS VSAM files, copy the transaction master AWS.M2.CARDDEMO.TRANSACT.VSAM.KSDS to a new TRANSACT.BKUP GDG generation, delete and re-define the cluster empty, wait, and re-open the files to CICS. No CardDemo business logic runs in this chain; its requirements are data-safety and ordering semantics.

1. Business purpose

The transaction master AWS.M2.CARDDEMO.TRANSACT.VSAM.KSDS holds the posted card transactions that CICS reads online as FILE(TRANSACT) (app/csd/CARDDEMO.CSD:76-77). CICS keeps no recovery log for it: the file is defined JOURNAL(NO), RECOVERY(NONE), BACKUPTYPE(STATIC) (app/csd/CARDDEMO.CSD:82-85). The posting program CBTRN02C opens the master OUTPUT (app/cbl/CBTRN02C.cbl:256), so posting replaces the file instead of appending to it.

This chain keeps a copy of the master before it is replaced. TRANBKP (job card: "REPRO and Delete Transaction Master", app/jcl/TRANBKP.jcl:1) copies every record to a new generation of the AWS.M2.CARDDEMO.TRANSACT.BKUP GDG, then deletes the cluster and its alternate index and re-defines the cluster empty (app/jcl/TRANBKP.jcl:23-67). CLOSEFIL and OPENFIL bracket the work so that the CICS region CICSAWSA does not hold the dataset while IDCAMS deletes it (app/jcl/CLOSEFIL.jcl:26-30, app/jcl/OPENFIL.jcl:26-30). WAITSTEP adds a fixed 36-second pause before the files are re-opened (app/jcl/WAITSTEP.jcl:20-26).

If the chain does not run: (a) the next posting run overwrites the master with no copy of its prior content; (b) COMBTRAN, which sorts TRANSACT.BKUP(0) (app/jcl/COMBTRAN.jcl:23-24), combines a stale generation; (c) if CLOSEFIL ran but OPENFIL did not, the five files stay closed to CICS and every online function that reads them fails.

Business capabilityHow this stream serves it
Transaction history retentionKeeps the most recent images of the posted-transaction master as GDG generations TRANSACT.BKUP(+1), GDG base LIMIT(5) (app/jcl/DEFGDGB.jcl:24-28). The sample catalog lists five active generations G0072–G0076 (app/catlg/LISTCAT.txt:1631-1643).
Daily transaction postingLeaves an empty master defined KEYS(16 0), RECORDSIZE(350 350) (app/jcl/TRANBKP.jcl:54-67) for CBTRN02C's OPEN OUTPUT (app/cbl/CBTRN02C.cbl:256). Posting itself is scheduled only in CA-7 (Q-01).
Monthly interest cycleProvides the TRANSACT.BKUP(0) input that COMBTRAN merges with SYSTRAN(0) and reloads into the master (app/jcl/COMBTRAN.jcl:22-48).
Online card servicing availabilityCloses and re-opens TRANSACT, CCXREF, ACCTDAT, CXACAIX and USRSEC in CICSAWSA so batch and CICS never use the datasets at the same time (app/jcl/CLOSEFIL.jcl:26-30, app/jcl/OPENFIL.jcl:26-30).

Gating conditions: Control-M releases each job on its predecessor's OUT condition for the same ODATE, and the successor deletes that condition when it runs. CLOSEFIL adds DAILY-TransactionBackup-CLOSEFIL (app/scheduler/CardDemo.controlm:5); TRANBKP waits on it, deletes it and adds DAILY-TransactionBackup-TRANBKP (:9-11); WAITSTEP waits on that, deletes it and adds DAILY-TransactionBackup-WAITSTEP (:15-17); OPENFIL waits on that and deletes it without adding a new one (:21-22). The folder has no ON/DO or TIMEFROM statements, so a successor is released when its predecessor ends OK; no specific return code is tested between jobs. Inside TRANBKP the only step gate is STEP10 EXEC PGM=IDCAMS,COND=(4,LT) (app/jcl/TRANBKP.jcl:51): the re-define is bypassed if an earlier step ended above RC 4. The DELETE step has no COND (:37) and runs whatever the REPRO returned.

The schedulers disagree. CA-7 has no TRANBKP. Its SCHID=030 daily network is CLOSEFIL → CBPAUP0J → POSTTRAN → WAITSTEP → OPENFIL (triggers at app/scheduler/CardDemo.ca7:43, :70, :97, :124; OPENFIL "N -- COMP TRIGGERS OTHER JOBS" at :138). This Control-M folder has TRANBKP and no POSTTRAN. This document describes the Control-M folder as written and does not assert a combined chain (Q-01).

5. Functional requirements

IDRequirementSourceAcceptance criteria
FR-01Before the backup starts, the five CICS files TRANSACT, CCXREF, ACCTDAT, CXACAIX and USRSEC are closed in region CICSAWSA so no online task holds the transaction master open.app/jcl/CLOSEFIL.jcl:22-30When TRANBKP starts, online access to the transaction store is disabled (legacy: CEMT INQ FIL(TRANSACT) shows CLOSED) and stays disabled until OPENFIL runs.
FR-02Jobs run strictly in the order CLOSEFIL → TRANBKP → WAITSTEP → OPENFIL; each successor is released only by its immediate predecessor's condition for the same ODATE.app/scheduler/CardDemo.controlm:5, :9, :15, :21While CLOSEFIL has not ended OK, TRANBKP does not start; while TRANBKP has not ended OK, neither WAITSTEP nor OPENFIL starts.
FR-03Each successor deletes the condition that released it (OUTCOND SIGN="-"), so one predecessor completion releases exactly one successor run.app/scheduler/CardDemo.controlm:10, :16, :22After OPENFIL ends, no DAILY-TransactionBackup-* condition remains for that ODATE; running the folder again needs a new CLOSEFIL run.
FR-04The whole transaction master is copied to a new backup generation before any record is deleted. The copy is unfiltered.app/jcl/TRANBKP.jcl:23-33 (STEP05R before STEP05 at :37); app/ctl/REPROCT.ctl:15Record count and byte content of TRANSACT.BKUP(+1) equal the master as it stood when CLOSEFIL completed, in ascending TRAN-ID order.
FR-05The backup is a new cataloged generation of fixed 350-byte records, cataloged only if the copy step ends normally.app/jcl/TRANBKP.jcl:29-33After a successful run the GDG has one more generation, LRECL 350, RECFM FB, layout CVTRA05Y; after an abended copy step, no new generation is cataloged.
FR-06At most five backup generations are kept; a sixth rolls the oldest off.app/jcl/DEFGDGB.jcl:24-28After six consecutive successful runs exactly five generations are active and the earliest is no longer available as a relative generation. Whether it is also scratched depends on Q-03.
FR-07Downstream readers use the newest generation, whichever job produced it: COMBTRAN reads TRANSACT.BKUP(0), and TRANREPT writes (+1) to the same GDG.app/jcl/COMBTRAN.jcl:23-24; app/jcl/TRANREPT.jcl:29-33A migrated backup store exposes a "latest generation". The target must decide (Q-05) whether a TRANREPT run between two TRANBKP runs may become COMBTRAN's input, and test that decision.
FR-08After the copy, the base cluster and its alternate index are both deleted. A missing cluster or AIX is tolerated: IDCAMS MAXCC ≤ 8 is reset to 0.app/jcl/TRANBKP.jcl:40-45TRANBKP does not fail when the AIX or the cluster does not exist; after STEP05 neither TRANSACT.VSAM.KSDS nor TRANSACT.VSAM.AIX is cataloged.
FR-09The master is re-defined empty with exactly: INDEXED, KEYS(16 0), RECORDSIZE(350 350), SHAREOPTIONS(2 3), ERASE, CYLINDERS(1 5), VOLUMES(AWSHJ1), components ...KSDS.DATA and ...KSDS.INDEX.app/jcl/TRANBKP.jcl:54-67LISTCAT of the new cluster shows KEYLEN 16, RKP 0, AVGLRECL = MAXLRECL = 350, SHROPTNS(2,3), ERASE and the component names above; the cluster holds zero records.
FR-10The re-define runs only if every earlier step ended RC ≤ 4; the delete step runs unconditionally.app/jcl/TRANBKP.jcl:37 (no COND), :51 (COND=(4,LT))If STEP05R ends RC 8, STEP05 still runs and STEP10 is bypassed; if STEP05R ends RC 0 or 4, STEP10 runs.
FR-11When TRANBKP completes, the master holds zero records and has no alternate index or path; the next loader (POSTTRAN's OPEN OUTPUT or COMBTRAN's REPRO) starts from empty.app/jcl/TRANBKP.jcl:40-67; app/cbl/CBTRN02C.cbl:256; app/jcl/COMBTRAN.jcl:41-48A count of the transaction store right after TRANBKP is 0; a following POSTTRAN leaves it with exactly the records it posted.
FR-12The master's primary key is the 16-byte TRAN-ID at offset 0 and the record is 350 bytes. The cluster parameters follow the copybook.app/cpy/CVTRA05Y.cpy:4-5, :18; app/jcl/TRANBKP.jcl:58-59Inserting two records with the same TRAN-ID into the re-defined master is rejected as a duplicate key; a record longer than 350 bytes is rejected.
FR-13The processing-timestamp access path is not rebuilt by this chain. When TRANIDX runs it defines a NONUNIQUEKEY, UPGRADE alternate index on bytes 304–329 (TRAN-PROC-TS), a PATH over it, and populates it with BLDINDEX.app/jcl/TRANIDX.jcl:25-34, :42-44, :52-54; app/cpy/CVTRA05Y.cpy:17; app/scheduler/CardDemo.controlm:3-25 (no TRANIDX)After TRANBKP, the AIX is absent until TRANIDX (or TRANFILE) runs. After TRANIDX, a read through the path by a TRAN-PROC-TS value returns every record with that timestamp, duplicates included.
FR-14WAITSTEP pauses the chain for the number of centiseconds in columns 1–8 of its first SYSIN record (shipped value 00003600 = 36 s) and ends RC 0.app/jcl/WAITSTEP.jcl:20-26; COBSWAIT / PROCEDURE DIVISION (app/cbl/COBSWAIT.cbl:36-38); app/asm/MVSWAIT.asm:23, :26Elapsed time between TRANBKP end and OPENFIL start is at least 36 s; WAITSTEP ends RC 0 and reads or writes no business data.
FR-15After the wait, the same five CICS files are re-opened in CICSAWSA and the chain ends; OPENFIL releases nothing.app/jcl/OPENFIL.jcl:22-30; app/scheduler/CardDemo.controlm:20-24After OPENFIL, CEMT INQ FIL for all five files shows OPEN, ENABLED; the folder orders no further job.
FR-16The folder is ordered every calendar day of every month. Each job can be submitted until 23:00 on its ODATE and stays eligible for up to 7 days while it waits for its IN condition.app/scheduler/CardDemo.controlm:4, :8, :14, :20 (DAYS="ALL", JAN..DEC="1", TIMETO="23:00", MAXWAIT="7", MAXRERUN="5")The migrated schedule triggers the chain daily including weekends and holidays; a job whose predecessor has not completed by 23:00 is not submitted that day and is held up to 7 days; at most five automatic reruns.
FR-17No release decision between jobs depends on a numeric return code: a job that ends OK releases its successor, a job that does not end OK stops the chain. The only RC test is the in-job COND of FR-10.app/scheduler/CardDemo.controlm:3-25 (no ON/DO); app/jcl/TRANBKP.jcl:51A migrated chain treats "completed" as released and any other outcome as stopped, and adds no RC-4-is-OK rule between jobs that the legacy folder does not have.
FR-18TRANBKP is not idempotent: a rerun after a successful copy creates another generation holding the now-empty master, which becomes BKUP(0) and pushes the real backup back one generation.app/jcl/TRANBKP.jcl:29-33 (unconditional (+1))Rerun behavior is documented and tested: either the migrated backup is idempotent per ODATE (preferred; deviation needs sign-off, Q-09) or the runbook forbids a rerun once STEP05R has succeeded.
FR-19Because CICS keeps no journal or recovery log for TRANSACT, the TRANBKP generation is the only point-in-time copy of posted transactions and must stay readable for the retention period.app/csd/CARDDEMO.CSD:76-85 (JOURNAL(NO), RECOVERY(NONE), BACKUPTYPE(STATIC))The migrated backup survives loss of the primary store and can restore the master to its CLOSEFIL-time state for any of the last five cycles.
FR-20No other job may read or load the master while TRANBKP runs. Between STEP05 and STEP10 the cluster does not exist, and after STEP10 it is empty.app/jcl/TRANBKP.jcl:37-67; app/jcl/CREASTMT.JCL:45; app/jcl/CBEXPORT.jcl:55-56No reader of the master is scheduled inside the folder (none in app/scheduler/CardDemo.controlm:3-25); a migrated design serializes readers against the backup-and-empty step, and a reader started after it reads zero records without failing.

6.3 Restart / checkpoint semantics

There is no checkpoint and no commit interval: every step is one IDCAMS or SDSF invocation that either completes or does not. Restart rules that follow from the JCL:

  1. CLOSEFIL, WAITSTEP and OPENFIL can be rerun at any time without side effects (app/jcl/CLOSEFIL.jcl:26-30, app/jcl/WAITSTEP.jcl:22-26, app/jcl/OPENFIL.jcl:26-30).
  2. If TRANBKP failed in STEP05R, the new generation is not kept (third DISP parameter DELETE, app/jcl/TRANBKP.jcl:29). It can be rerun from the top only if STEP05 has not already deleted the cluster; because STEP05 has no COND (:37), check with LISTCAT first.
  3. If TRANBKP failed in STEP10, restart at STEP10 only: the backup generation exists and the master is already gone. A rerun from the top would REPRO a missing or empty cluster and use up a generation (FR-18).
  4. Control-M allows MAXRERUN 5 and MAXWAIT 7 (app/scheduler/CardDemo.controlm:8) but defines no DO RERUN action; the JCL has no RESTART= parameter, so a step-level restart is an operator action.
  5. The recovery copy is always the newest generation TRANSACT.BKUP(0). Restore sequence: DEFINE CLUSTER as in app/jcl/TRANBKP.jcl:54-67 → REPRO from the generation (the pattern of app/jcl/COMBTRAN.jcl:41-48) → TRANIDX (app/jcl/TRANIDX.jcl:22-54). No backout job exists in the repo.
