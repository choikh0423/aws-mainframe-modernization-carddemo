1. Business purpose

DataExportImport produces a complete, self-describing copy of the CardDemo master data and turns it back into the estate's normalized record layouts. CBEXPORT reads every record of the customer, account, card cross-reference, transaction and card VSAM clusters and writes them, in that order, to the single multi-record cluster AWS.M2.CARDDEMO.EXPORT.DATA. Each record carries a one-byte type code, a run timestamp, a global sequence number and a branch/region stamp (app/cbl/CBEXPORT.cbl:8-10, app/cbl/CBEXPORT.cbl:27-30, app/cpy/CVEXPORT.cpy:9-19). CBIMPORT reads that file, dispatches on the type byte, and writes one flat file per type plus an error file for records whose type it does not recognize (app/cbl/CBIMPORT.cbl:8-11, app/cbl/CBIMPORT.cbl:28-32).

The chain is operator-run. No CA-7 job or Control-M folder names CBEXPORT, CBIMPORT or FTPJCLS, and the README batch run book (README.md:207-230) does not list them. The index lists the sequence as CBEXPORT → FTPJCL → CBIMPORT. In source, the only real hand-off is the shared dataset: CBEXPORT writes AWS.M2.CARDDEMO.EXPORT.DATA (app/jcl/CBEXPORT.jcl:62-63) and CBIMPORT reads the same DSN (app/jcl/CBIMPORT.jcl:28-29). app/jcl/FTPJCL.JCL (job FTPJCLS) PUTs a different dataset, 'AWS.M2.CARDEMO.FTP.TEST', and references neither program nor the export file (app/jcl/FTPJCL.JCL:40). It is documented here as the transfer boundary (B-12), not as a gated step.

If the chain does not run, no estate copy is produced. Daily posting, statements and interest are unaffected: CBEXPORT opens the masters INPUT only (app/cbl/CBEXPORT.cbl:200-233) and CBIMPORT writes new sequential datasets, never the VSAM masters (app/cbl/CBIMPORT.cbl:43-71, app/jcl/CBIMPORT.jcl:33-60).

Business capabilityHow this stream serves it
Branch migration / bulk data transferProduces one file holding all five masters that can be shipped to another system (app/jcl/CBEXPORT.jcl:19-20). The "branch" is fixed at 0001/NORTH and the whole estate is exported (app/cbl/CBEXPORT.cbl:278-279).
Data onboarding on the receiving sideNormalizes the snapshot back into the copybook layouts CVCUS01Y (500), CVACT01Y (300), CVACT03Y (50), CVTRA05Y (350) and CVACT02Y (150) (app/cbl/CBIMPORT.cbl:81-104). The estate's load jobs use the same layouts.
Operational reconciliationBoth programs print per-type and total counts so the operator can reconcile export against import (app/cbl/CBEXPORT.cbl:563-573, app/cbl/CBIMPORT.cbl:465-478).
Data-quality reportingRecords of an unknown type go to AWS.M2.CARDDEMO.IMPORT.ERRORS and the run does not stop (app/cbl/CBIMPORT.cbl:425-446).

Gating conditions: There are no scheduler release rules. No CA-7 job or TRIGGERED JOBS entry names CBEXPORT, CBIMPORT or FTPJCLS (app/scheduler/CardDemo.ca7, 570 lines), and no Control-M INCOND/OUTCOND references them (app/scheduler/CardDemo.controlm, 92 lines). The operator owns the order, which follows the data dependency: CBIMPORT can only run after CBEXPORT has written AWS.M2.CARDDEMO.EXPORT.DATA (app/jcl/CBEXPORT.jcl:62-63, app/jcl/CBIMPORT.jcl:28-29). No step in the three jobs has COND= or IF/THEN. CBEXPORT STEP02 runs whatever STEP01 returns (app/jcl/CBEXPORT.jcl:24-43). SET MAXCC = 0 hides the "cluster not found" from the first-run DELETE (app/jcl/CBEXPORT.jcl:27-28). Neither COBOL program sets RETURN-CODE. Success is GOBACK (app/cbl/CBEXPORT.cbl:158, app/cbl/CBIMPORT.cbl:171); failure is an LE abend via CALL 'CEE3ABD' (app/cbl/CBEXPORT.cbl:579, app/cbl/CBIMPORT.cbl:484). FTPJCLS has no dataset dependency on either job (dashed). The chain is not wrapped in CLOSEFIL/OPENFIL (see Q-07).

6.3 Restart / checkpoint semantics

Neither program has checkpoints, commit intervals or a restart key. Both are single-pass, read-to-EOF programs that open their outputs OPEN OUTPUT (app/cbl/CBEXPORT.cbl:235, app/cbl/CBIMPORT.cbl:205-245), so a restart is always a cold rerun from the first step. For CBEXPORT, the IDCAMS step guarantees a clean cluster (app/jcl/CBEXPORT.jcl:27-38). For CBIMPORT, the operator must first delete the cataloged outputs. No backout is needed because the chain never updates a master. A re-export gets a new run timestamp and restarts the sequence at 1 (app/cbl/CBEXPORT.cbl:123, :172-195). The target is different: both Spring Batch steps are chunk-oriented and restartable through the JobRepository, and the writers truncate back to the last committed byte position (docs/migration/streams/DataExportImport/DataExportImport_migration_plan.md §1).

NFR-05Format portabilityThe export record holds binary (COMP) and packed (COMP-3) fields (app/cpy/CVEXPORT.cpy:16, 25, 41, 50, 52, 57, 71, 72, 87, 95, 96), so it must be transferred in binary. FTPJCL uses ASCII mode (app/jcl/FTPJCL.JCL:36), which would corrupt those fields.
NFR-06ObservabilityAll progress and statistics go to SYSOUT through DISPLAY (app/jcl/CBEXPORT.jcl:67, app/jcl/CBIMPORT.jcl:64). The target must reproduce the lines verbatim, as ExportStatistics / ImportStatistics / ExportImportSysout do.
NFR-07ConsistencyCBEXPORT reads masters that CICS may have open (DISP=SHR, outside any CLOSEFIL window), so a point-in-time-consistent snapshot is not guaranteed (Q-07).

9. Security & access

ItemValue
Job owner / RACF identityNot defined in repo. The JOB cards specify only NOTIFY=&SYSUID and no USER= (app/jcl/CBEXPORT.jcl:1-2, app/jcl/CBIMPORT.jcl:1-2, app/jcl/FTPJCL.JCL:1-2), and there is no scheduler RUN_AS.
Sensitive data handledFull PII and card data in the clear. Customer: SSN, government-issued ID, date of birth, phone numbers and addresses (app/cpy/CVEXPORT.cpy:25-41). Card: full PAN (app/cpy/CVEXPORT.cpy:76, 85, 94) and CVV (app/cpy/CVEXPORT.cpy:96). Account: balances and credit limits (app/cpy/CVEXPORT.cpy:47-60). The file covers the whole estate, not one branch (FR-03, FR-07).
Transfer credentialsFTPJCL carries the host, user ID and a clear-text password as in-stream SYSIN cards (app/jcl/FTPJCL.JCL:33-35). The transfer is plain FTP in ASCII mode, not FTPS/SFTP (app/jcl/FTPJCL.JCL:30, 36). The target does not reproduce the credentials or the transfer.
Regulatory obligationsNot defined in repo. A transferable flat file holding PAN and CVV would ordinarily be in PCI DSS scope, and storing CVV after authorization is prohibited. Customer PII falls under GLBA safeguards (Q-13).

Q-01AssumptionThe chain is manual: no CA-7 or Control-M definition exists for CBEXPORT, CBIMPORT or FTPJCLS, and the README run book omits them (README.md:207-230). The order comes from the data dependency. Confirm whether a production scheduler entry exists outside this repo.Batch operationsOpen
Q-02QuestionThe schedulers disagree on the daily chain that shares these masters. CA-7 SCHID=030 is CLOSEFIL → CBPAUP0J → POSTTRAN → WAITSTEP → OPENFIL, and CardDemo.ca7 has no TRANBKP (app/scheduler/CardDemo.ca7:43-124). Which one is authoritative, and must DataExportImport avoid overlapping it?Scheduling / migration architectOpen
Q-03DebtCBIMPORT.jcl has no CARDOUT DD, but the program SELECTs and OPENs CARD-OUTPUT (app/cbl/CBIMPORT.cbl:63-66, 233-238), so the legacy job abends at OPEN as shipped. The target writes the card file and treats the program as the specification. Confirm the intended DSN.Application ownerOpen
Q-04DebtIDCAMS KEYS(4 28) (app/jcl/CBEXPORT.jcl:32) puts the key at offset 28, but EXPORT-SEQUENCE-NUM starts at offset 27 (1 + 26 bytes; app/cpy/CVEXPORT.cpy:10-16). The defined key therefore covers the low 3 bytes of the sequence plus the first byte of the branch ID. This is harmless for sequential numbering below 224, but wrong for keyed access.Application ownerOpen
Q-05DebtBoth programs declare RECORD KEY IS EXPORT-SEQUENCE-NUM (app/cbl/CBEXPORT.cbl:68, app/cbl/CBIMPORT.cbl:40), but that field comes from CVEXPORT copied into WORKING-STORAGE (app/cbl/CBEXPORT.cbl:96, app/cbl/CBIMPORT.cbl:113). The FD records are plain PIC X(500) (app/cbl/CBEXPORT.cbl:92, app/cbl/CBIMPORT.cbl:79).
