1. Business purpose

MonthlyInterestCalculation is CardDemo's month-end interest run. After CLOSEFIL has the CICS region release the shared VSAM files, INTCALC runs CBACT04C. The program reads every transaction-category balance in TCATBALF in key order. For each balance it looks up the account's disclosure group and rate in DISCGRP, falling back to the DEFAULT group, and computes balance × rate ÷ 1200. It writes one System-sourced interest transaction per priced category to a new SYSTRAN generation, adds the account's total interest to its current balance, and zeroes the current-cycle credit and debit totals. COMBTRAN then sorts the interest transactions together with the latest transaction-master backup by transaction id and loads the result into the TRANSACT KSDS. WAITSTEP pauses 36 seconds and OPENFIL gives the files back to CICS.

If the chain does not run, accounts are not charged interest for the month, the cycle credit and debit totals carry over into the next cycle, and the interest transactions are missing from TRANSACT, which the statement job CREASTMT and the online transaction screens read. If it runs twice, interest is charged twice. Nothing in the program records that a balance has already been charged (FR-15, Q-06).

Business capabilityHow this stream serves it
Revolving-credit interest billingPrices each account's category balances at the disclosure-group rate and posts the total to the account balance (app/cbl/CBACT04C.cbl:462-470, :350-356).
Transaction history and statementsEach interest amount becomes a CVTRA05Y transaction (type 01, category 0005, source System) that COMBTRAN merges into the TRANSACT master read by CREASTMT and the CT00/CT01 screens (CBACT04C.cbl:482-500; app/jcl/COMBTRAN.jcl:22-48).
Billing-cycle resetSets ACCT-CURR-CYC-CREDIT and ACCT-CURR-CYC-DEBIT to zero when it updates each account (CBACT04C.cbl:353-354).
Pricing governanceRates are data: DISCGRP is keyed by account group, transaction type and category, with a mandatory DEFAULT group, so products can be re-priced without a code change (CBACT04C.cbl:415-460; app/cpy/CVTRA02Y.cpy:4-9).
Online availabilityThe CICS files are closed before the batch update and reopened after it, so batch gets exclusive VSAM access (app/jcl/CLOSEFIL.jcl:26-30, app/jcl/OPENFIL.jcl:26-30).

Gating conditions: The chain is defined only in Control-M (app/scheduler/CardDemo.controlm:64-92). CLOSEFIL has no INCOND and posts MONTHLY-InterestCalculation-CLOSEFIL (:65-66). Every later job has a single INCOND equal to its predecessor's OUTCOND for the same ODATE (AND_OR="A"). It deletes that condition (SIGN="-") and adds its own (SIGN="+"): INTCALC :70-72, COMBTRAN :76-78, WAITSTEP :82-84, OPENFIL :88-89. OPENFIL adds no condition, so the network ends there. Control-M posts an OUTCOND only when a job ends OK. The XML has no ON/DO or MAXRC override, so an INTCALC user abend U0999 or a non-zero COMBTRAN completion holds the chain. None of the JCL steps has a COND= parameter (app/jcl/INTCALC.jcl:22, app/jcl/COMBTRAN.jcl:22,41), so COMBTRAN STEP10 runs even if the SORT step ended non-zero. It is skipped only on an abend. No triggers, resources or cross-folder conditions are defined.
Scheduler differences: CA-7 (app/scheduler/CardDemo.ca7) has no INTCALC or COMBTRAN. It has CLOSEFIL, WAITSTEP and OPENFIL only inside other networks. The schedulers also disagree on the daily chain: CA-7 SCHID=030 is CLOSEFIL→CBPAUP0J→POSTTRAN→WAITSTEP→OPENFIL, while Control-M DAILY-TransactionBackup is CLOSEFIL→TRANBKP→WAITSTEP→OPENFIL. This document describes each source as written and does not assert a combined chain (Q-07, Q-09). The dashed TRANSACT.BKUP(0) node is shown because COMBTRAN's SORTIN reads it, not because this folder schedules TRANBKP (Q-04).

5. Functional requirements

IDRequirementSourceAcceptance criteria
FR-01Before any batch update, the five CICS files TRANSACT, CCXREF, ACCTDAT, CXACAIX and USRSEC are closed in region CICSAWSA. They are reopened after the chain. INTCALC is released only after the close completes, and OPENFIL only after WAITSTEP.app/jcl/CLOSEFIL.jcl:26-30; app/jcl/OPENFIL.jcl:26-30; app/scheduler/CardDemo.controlm:66,70,88While INTCALC and COMBTRAN run, no online transaction can update those files. In the target, the same exclusive-access guarantee is either provided or documented as not needed. After the chain, all five files are open and enabled.
FR-02INTCALC is one step, STEP15, running CBACT04C with a 10-character run-date PARM ('2022071800' in the JCL). The program does not parse or validate the PARM as a date. It uses it only as the prefix of the generated transaction ids.app/jcl/INTCALC.jcl:22; app/cbl/CBACT04C.cbl:176-178,476-480With PARM 2022071800 the run produces transaction ids 2022071800000001, 2022071800000002, and so on. The target rejects a run date that is not exactly 10 characters.
FR-03File open modes: TCATBALF, XREFFILE and DISCGRP are opened INPUT, ACCTFILE I-O and TRANSACT (SYSTRAN) OUTPUT. Any open status other than 00 abends the program before any record is processed.CBACT04C.cbl:236,254,272,291,309; 0000-TCATBALF-OPEN … 0400-TRANFILE-OPENWith an input dataset missing or still held by CICS, the job abends U0999 with the matching ERROR OPENING … message. No account is changed and no SYSTRAN generation is kept.
FR-04Balances are processed in TCATBALF key order (account id, transaction type code, transaction category code) by sequential read. Read status 10 ends the run normally. Any other status other than 00 abends.CBACT04C.cbl:28-32,61-67,325-348Given balances for accounts 00000000011 and 00000000010, account 10's transactions are generated first. An I/O error on TCATBALF logs ERROR READING TRANSACTION CATEGORY FILE and abends.
FR-05When the account id changes, the account record (by ACCT-ID) and the card cross-reference record (by alternate key XREF-ACCT-ID) are read once and reused for all of that account's categories. The per-account interest total is reset to zero.CBACT04C.cbl:194-205,372-376,393-398An account with three category balances causes exactly one ACCTFILE read and one XREFFILE read. All three generated transactions carry the same TRAN-CARD-NUM.
FR-06The interest rate for a balance comes from the DISCGRP record keyed by (ACCT-GROUP-ID, balance type code, balance category code).CBACT04C.cbl:210-213,415-420; app/cpy/CVTRA02Y.cpy:5-8For account group GOLD, type 01, category 0001, the rate stored under key GOLD      010001 is used, not the DEFAULT rate, when that row exists.
FR-07If the group-specific DISCGRP record is missing (status 23), the program logs DISCLOSURE GROUP RECORD MISSING and TRY WITH DEFAULT GROUP CODE, then retries once with group id DEFAULT and the same type and category. If the DEFAULT record is also missing, the run abends with ERROR READING DEFAULT DISCLOSURE GROUP.CBACT04C.cbl:416-439,443-460Remove the GOLD 01 0001 rate and the run uses the DEFAULT 01 0001 rate. Remove both and the job abends at that balance.
FR-08A rate of zero produces no interest transaction and leaves the account total unchanged. Fees are never computed because 1400-COMPUTE-FEES is an empty stub.CBACT04C.cbl:214-217,518-520A balance whose resolved rate is 0.00 produces no SYSTRAN record. The migrated job produces no fee transactions.
FR-09Monthly interest per category = TRAN-CAT-BAL × DIS-INT-RATE ÷ 1200. It is stored in PIC S9(09)V99 without ROUNDED, so it is truncated toward zero to two decimals. A non-zero rate on a zero balance still writes a 0.00 transaction.CBACT04C.cbl:168,214,462-468Balance 1000.00 at rate 18.50 gives 15.41, not 15.42. Balance -1000.00 at 18.50 gives -15.41. Balance 0.00 at 18.50 gives one transaction for 0.00.
FR-10The account's total interest is the sum of the per-category amounts after truncation.CBACT04C.cbl:467Three categories that each compute 0.333… produce three 0.33 transactions and a balance increase of 0.99, not 1.00.
FR-11Each computed interest amount produces one CVTRA05Y transaction with these fields: TRAN-ID = PARM + 6-digit sequence (starts at 000001 and increments once per transaction across the whole run); TRAN-TYPE-CD '01'; TRAN-CAT-CD = literal '05' moved into PIC 9(04), so stored as 0005; TRAN-SOURCE System; TRAN-DESC = Int. for a/c + 11-digit account id; amount = the truncated interest; merchant id 0; merchant name, city and zip blank; card number = the account's XREF card number.CBACT04C.cbl:173,473-495; app/cpy/CVTRA05Y.cpy:5-15The second transaction of the run, whichever account it belongs to, has id <PARM>000002. A record for account 00000000010 has TRAN-DESC starting Int. for a/c 00000000010 and category code 0005.
FR-12TRAN-ORIG-TS and TRAN-PROC-TS are both set to the same current clock time in DB2 format YYYY-MM-DD-HH.MM.SS.hh0000 (26 characters).CBACT04C.cbl:496-498,613-626Generated records have 26-character timestamps matching ^\d{4}-\d{2}-\d{2}-\d{2}\.\d{2}\.\d{2}\.\d{2}0000$, and ORIG equals PROC.
FR-13Interest transactions are written to the sequential TRANSACT DD of INTCALC. That is a new SYSTRAN(+1) GDG generation of fixed 350-byte records, in the order generated. INTCALC never writes the TRANSACT master. A write status other than 00 abends.app/jcl/INTCALC.jcl:37-41; CBACT04C.cbl:53-56,500-514After INTCALC, the master KSDS record count is unchanged. The new SYSTRAN generation has exactly one record per priced category, LRECL 350.
FR-14When the account id changes, and it is not the first account, the previous account is updated with a REWRITE: ACCT-CURR-BAL += total interest, ACCT-CURR-CYC-CREDIT = 0 and ACCT-CURR-CYC-DEBIT = 0. A rewrite status other than 00 abends.CBACT04C.cbl:194-199,350-369An account with balance 500.00, cycle credit 120.00, cycle debit 80.00 and total interest 7.70 reads back as 507.70 / 0.00 / 0.00 once the next account is reached.
FR-15Preserved quirk: the last account in TCATBALF key order is never updated, although its transactions are still generated. The end-of-file branch at :219-220 is unreachable, because PERFORM UNTIL END-OF-FILE = 'Y' tests before each pass, so the outer IF END-OF-FILE = 'N' is always true. Also, nothing marks a balance as already charged, so a rerun charges interest again.CBACT04C.cbl:188-191,219-221Parity test with two accounts: only the first has its balance and cycle totals changed. The second has SYSTRAN records but an unchanged ACCTDATA record. Running INTCALC twice doubles the first account's balance increase. Whether the target keeps this quirk is Q-06.
FR-16A missing account or XREF record for a balance abends the run. It first logs ACCOUNT NOT FOUND: + id, then ERROR READING ACCOUNT FILE or ERROR READING XREF FILE. There is no reject file and no skip.CBACT04C.cbl:372-391,393-413A TCATBALF row for an account that is not in ACCTDATA stops the job. Earlier accounts that were already rewritten stay updated in the legacy system, because there is no backout.
FR-17COMBTRAN STEP05R sorts TRANSACT.BKUP(0) followed by SYSTRAN(0) ascending on the 16-byte character field at position 1 (TRAN-ID). Output goes to a new TRANSACT.COMBINED(+1) generation with the SORTIN DCB. Duplicates are kept: this is a SORT with no SUM FIELDS.app/jcl/COMBTRAN.jcl:22-37Output record count = BKUP count + SYSTRAN count. Records are in ascending TRAN-ID order, LRECL 350.
FR-18COMBTRAN STEP10 loads every record of TRANSACT.COMBINED(+1) into the TRANSACT KSDS with REPRO INFILE(TRANSACT) OUTFILE(TRANVSAM). There is no REPLACE and no COND=, so the load runs even if the sort step ended non-zero.app/jcl/COMBTRAN.jcl:41-48Starting from an empty master, after STEP10 the master holds exactly the COMBINED records keyed by TRAN-ID. In the legacy system, loading a key that is already in the master is a duplicate-record error. The target behavior is stated in §10 and Q-05.
FR-19GDG handling: INTCALC allocates SYSTRAN(+1) with DISP=(NEW,CATLG,DELETE). COMBTRAN, the next job, reads it as (0) and allocates COMBINED(+1). The bases are LIMIT(5) SCRATCH, so a sixth generation rolls the oldest off.app/jcl/INTCALC.jcl:37-41; app/jcl/COMBTRAN.jcl:25-26,33-37; app/jcl/DEFGDGB.jcl:48-58A failed INTCALC leaves no new SYSTRAN generation, because the abnormal disposition is DELETE. 6.3 Restart / checkpoint semantics

The chain has no checkpoint or commit interval. CBACT04C rewrites each account as soon as it reaches the next account (app/cbl/CBACT04C.cbl:194-196). VSAM updates are therefore permanent at once, and a failed run leaves the first accounts charged and the rest not. The SYSTRAN generation is the only output removed on failure (DISP=(NEW,CATLG,DELETE), app/jcl/INTCALC.jcl:37). The program has no restart key and no already-processed marker, and app/jcl has no backout job. A cold rerun of INTCALC charges interest again on every account that was already updated (FR-15). The transaction-id sequence restarts at 000001 on every run (WS-TRANID-SUFFIX VALUE 0, CBACT04C.cbl:173). A second run with the same PARM therefore produces duplicate keys, which COMBTRAN's REPRO rejects.

Safe recovery is: restore ACCTDATA to its pre-run state (this chain does not provide a copy, Q-06), delete the partial SYSTRAN generation if it was cataloged, and rerun from CLOSEFIL. COMBTRAN can restart from STEP05R if the TRANSACT master is in the state TRANBKP leaves it, which is empty (app/jcl/TRANBKP.jcl:37-67). WAITSTEP, CLOSEFIL and OPENFIL are stateless and can be rerun.
