WeeklyReferenceRefresh Batch

Weekly DB2 transaction-type refresh and disclosure-group reload. On Saturdays, Control-M runs the DB2 transaction-type maintenance job MNTTRDB2. 1. Business purpose

CardDemo stores its transaction-type reference data in two places. The master copy is in the DB2 tables CARDDEMO.TRANSACTION_TYPE and CARDDEMO.TRANSACTION_TYPE_CATEGORY, which administrators maintain online (CTLI/CTTU) and in batch (MNTTRDB2). The second copy is a pair of 60-byte flat files that the base application loads into VSAM for transaction reporting. The module README describes this as a "Dual Storage Strategy" in which TRANEXTR "creates VSAM-compatible files" (app/app-transaction-type-db2/README.md:139-142). The weekly cycle does three things: it applies the week's batch maintenance records to DB2, re-extracts both DB2 tables to their flat files (with backups of the previous extract), and rebuilds the disclosure-group KSDS (the interest-rate table read by interest calculation) from its flat-file seed. CICS closes and reopens the online files around the rebuild.

If the cycle does not run, batch transaction-type changes are not applied and DB2 changes never reach the flat files that feed the VSAM reference files. The disclosure-group KSDS is also not rebuilt. If the chain stalls between CLOSEFIL and OPENFIL, the five CICS files stay closed. That blocks sign-on (USRSEC) and every VSAM-backed online transaction until an operator reopens them.

Gating conditions (Control-M, app/scheduler/CardDemo.controlm):
  • MNTTRDB2 has no INCOND. When it completes it adds WEEKLY-TransactionTypesDBRefresh-MNTTRDB2 (ODATE=ODAT, SIGN=+) (:27-28).
  • TRANEXTR (:58-59) and CLOSEFIL (:33-34) each have that condition as their only INCOND (AND_OR="A"). The same event releases both smart folders, and they then run in parallel.
  • Inside DisclosureGroupsRefresh, each job adds its own WEEKLY-DisclosureGroupsRefresh-<job> condition and deletes its predecessor's (:35, 39-41, 45-47, 51-52).
  • Each smart folder also carries a folder-level OUTCOND ... -MNTTRDB2 SIGN="-" (:55, :62), so whichever folder finishes first deletes the condition the other folder needs (Q-01).
  • No job has ON/DO statements, so a non-zero completion code is handled by the site's Control-M default, which is not defined in the repo (Q-08).
  • JCL step gating: TRANEXTR STEP20/30/40 run with COND=(0,NE) and STEP50 with COND=(4,LT) (app/app-transaction-type-db2/jcl/TRANEXTR.jcl:42,53,65,95). MNTTRDB2 and DISCGRP have no COND= on any step.
Scheduler sources: this chain exists only in Control-M. app/scheduler/CardDemo.ca7 has no LJOB entry for MNTTRDB2, TRANEXTR or DISCGRP. Its CLOSEFIL / WAITSTEP / OPENFIL entries belong to other networks (SCHID 030/031/032). The two schedulers also disagree on the daily chain:
  • CA-7 SCHID=030: CLOSEFIL → CBPAUP0J → POSTTRAN → WAITSTEP → OPENFIL (CardDemo.ca7:43,70,97,124). TRANBKP does not appear anywhere in CardDemo.ca7.
  • Control-M DAILY-TransactionBackup: CLOSEFIL → TRANBKP → WAITSTEP → OPENFIL (CardDemo.controlm:3-25).
This document records each source as written and does not merge them (Q-03).

5. Functional requirements

IDRequirementSourceAcceptance criteria
FR-01MNTTRDB2 is the chain head. When it completes, the scheduler adds WEEKLY-TransactionTypesDBRefresh-MNTTRDB2 for the order date. TRANEXTR and CLOSEFIL each wait on that condition and nothing else, so the same event releases both.app/scheduler/CardDemo.controlm:27-28, 33-34, 58-59For a given ODAT, neither TRANEXTR nor CLOSEFIL starts before MNTTRDB2 ends. After it ends, both become eligible together.
FR-02DisclosureGroupsRefresh runs strictly in sequence: CLOSEFIL → DISCGRP → WAITSTEP → OPENFIL. Each job adds its own condition, and its successor deletes it.CardDemo.controlm:35, 39-41, 45-47, 51-52No two jobs of the folder are active at the same time. After OPENFIL, no WEEKLY-DisclosureGroupsRefresh-* condition remains for that ODAT.
FR-03COBTUPDT reads INPFILE sequentially as fixed 53-byte records: column 1 = operation, columns 2-3 = type code, columns 4-53 = description. It reads until end of file.COBTUPDT.cbl:31-34, 39-46, 83, 91-107; MNTTRDB2.jcl:11-18A file of N records produces N PROCESSING <record> lines in file order.
FR-04The operation code dispatches each record. A inserts, U updates, D deletes, and * is a comment (IGNORING COMMENTED LINE). Any other value displays ERROR: TYPE NOT VALID and performs 9999-ABEND.COBTUPDT / 1003-TREAT-RECORD (:109-130)A * record changes nothing and does not affect the RC. A Z record changes nothing, logs the error text and sets RC 4.
FR-05A inserts (TR_TYPE, TR_DESCRIPTION) from columns 2-3 and 4-53. SQLCODE 0 displays RECORD INSERTED SUCCESSFULLY. A negative SQLCODE (for example a duplicate key) displays Error accessing: TRANSACTION_TYPE table. SQLCODE: followed by the code, and sets RC 4.COBTUPDT / 10031-INSERT-DB (:132-164)A new code creates exactly one row. A duplicate code leaves the table unchanged and sets RC 4.
FR-06U sets TR_DESCRIPTION on the row whose TR_TYPE matches. SQLCODE +100 displays No records found. and sets RC 4. A negative SQLCODE sets RC 4 with the error text.COBTUPDT / 10032-UPDATE-DB (:166-195)Updating 01 changes only that row. Updating a missing code changes nothing and sets RC 4.
FR-07D deletes the row whose TR_TYPE matches. +100 displays No records found. and sets RC 4. A negative SQLCODE (including the ON DELETE RESTRICT violation from TRANSACTION_TYPE_CATEGORY) sets RC 4 and leaves the row in place.COBTUPDT / 10033-DELETE-DB (:196-226); TRNTYCAT.ddl:6-7Deleting a type that still has categories leaves both tables unchanged and sets RC 4.
FR-08Errors do not stop the run. 9999-ABEND displays the message, moves 4 to RETURN-CODE and returns to the read loop. Later records are still applied, and the program issues no COMMIT or ROLLBACK, so accepted changes commit when the step ends normally.COBTUPDT / 9999-ABEND (:230-233); :93-96For the input [valid A, invalid op, valid U], both valid changes are in the table after the run and the invalid record is logged. For the step RC, see Q-15.
FR-09No field is validated before the SQL runs. The type code is passed as two characters with no numeric check, although the JCL comment says "NUMERIC VALUE". The description is the fixed 50-byte host variable, trailing blanks included.COBTUPDT.cbl:71-77, 145-146, 173; MNTTRDB2.jcl:16Record AXYtest inserts TR_TYPE='XY'. 6.3 Restart / checkpoint semantics

  • No job in the chain takes checkpoints.
  • COBTUPDT issues no COMMIT or ROLLBACK (none appears in COBTUPDT.cbl:80-236), so all successful statements commit together when the IKJEFT01 step ends normally.
  • Rerunning MNTTRDB2 with the same INPFILE is not idempotent: previously applied A records now fail as duplicates, D records fail with +100, and the job ends RC 4.
  • TRANEXTR is restartable at STEP40 once STEP30 has run, but not from STEP10.
  • DISCGRP is fully rerunnable from STEP05.
  • CLOSEFIL, WAITSTEP and OPENFIL are idempotent.
  • Control-M allows up to 5 reruns per job (MAXRERUN="5").
