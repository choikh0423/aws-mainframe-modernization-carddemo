StatementGeneration Batch

Customer statement generation (text / HTML / PDF). CA-7 network SCHID=030: CLOSEFIL → CREASTMT → TXT2PDF1 → WAITSTEP → OPENFIL. 1. Business purpose

StatementGeneration produces the cardholder statement for every card in the card/account cross-reference file. CREASTMT takes the posted transaction file (AWS.M2.CARDDEMO.TRANSACT.VSAM.KSDS), re-keys it by card number so each card's transactions are contiguous, and runs CBSTM03A. That program walks CARDXREF card by card, reads the customer and the account, and writes each statement twice: as fixed 80-column plain text (STATEMNT.PS) and as 100-column HTML (STATEMNT.HTML) (app/jcl/CREASTMT.JCL:19-20, 79-96; app/cbl/CBSTM03A.CBL:8-9). TXT2PDF1 then turns the text statement into STATEMNT.PS.PDF with the TSO TXT2PDF utility (app/jcl/TXT2PDF1.JCL:21, 38-39). Because the statement program reads VSAM files that CICS also serves, the chain is bracketed by CLOSEFIL and OPENFIL, which close and re-open the CICS files, with a timed WAITSTEP before the re-open (app/jcl/CLOSEFIL.jcl:26-30; app/jcl/WAITSTEP.jcl:20-26; app/jcl/OPENFIL.jcl:26-30).

If the chain does not run, no statements (text, HTML or PDF) are produced for the cycle, and the previous cycle's statement datasets stay cataloged until the next successful STEP030. If the chain starts but never reaches OPENFIL, the five CICS files stay closed and every online CardDemo function that uses them fails until an operator re-opens them.

Business capabilityHow this stream serves it
Cardholder statement productionOne statement per CARDXREF card: customer name and address, account id, current balance, FICO score, itemized transactions and a total (CBSTM03A.CBL:316-329, 458-504).
Statement delivery formatsPlain text (80-byte records) and HTML (100-byte records) from one pass (CBSTM03A.CBL:44-47, 293); PDF rendered from the text file (TXT2PDF1.JCL:38-39).
Card-keyed transaction viewWork copy of TRANSACT keyed by card number + transaction id (TRXFL.VSAM.KSDS), rebuilt on every run (CREASTMT.JCL:22-62).
Batch / online file hand-offCICS files closed before and re-opened after the batch work (CLOSEFIL.jcl:26-30, OPENFIL.jcl:26-30), with a 36-second delay before re-open (WAITSTEP.jcl:26).

Gating conditions: The chain is a CA-7 trigger network, not a calendar schedule. Each job is released when its predecessor completes (TRIGGERED JOBS ... SCHID=030 QTM=0100 LEADTM=0000): CLOSEFIL→CREASTMT (CardDemo.ca7:465-468), CREASTMT→TXT2PDF1 (:494-495), TXT2PDF1→WAITSTEP (:521-522), WAITSTEP→OPENFIL (:524-527). Inside CREASTMT, STEP020, STEP030 and STEP040 carry COND=(0,NE), so they are bypassed once any earlier step ends with RC ≠ 0 (CREASTMT.JCL:56, 66, 79); DELDEF01 and STEP010 have no COND. TXT2PDF1's only step carries COND=(0,NE) (TXT2PDF1.JCL:26), which has no effect on the first step of a job. The listing shows no "good completion" RC requirement, so whether a non-zero CREASTMT still releases TXT2PDF1 cannot be determined from the repo (Q-05).

Scheduler mismatch (documented as written, not combined): CA-7 SCHID=030 also holds the daily chain CLOSEFIL→CBPAUP0J→POSTTRAN→WAITSTEP→OPENFIL (CardDemo.ca7:18-147, no TRANBKP anywhere in the file), while Control-M DAILY-TransactionBackup is CLOSEFIL→TRANBKP→WAITSTEP→OPENFIL (app/scheduler/CardDemo.controlm:3-25). StatementGeneration exists only in CA-7; CardDemo.controlm has no CREASTMT or TXT2PDF1 job, so no Control-M IN/OUT conditions exist for it (Q-01, Q-02). The dotted edge is the trigger listed in the OPENFIL block at CardDemo.ca7:529-532 (CLOSEFIL, SCHID=031); the full OPENFIL block says N -- COMP TRIGGERS OTHER JOBS (:138) (Q-04).

5. Functional requirements

FR-01Before each run the card-keyed work store is rebuilt from scratch: TRXFL.SEQ and the TRXFL.VSAM.KSDS cluster are deleted, the condition code is reset (SET MAXCC = 0) so a first run with nothing to delete still succeeds, and the KSDS is redefined with a 32-byte key at offset 0 and fixed 350-byte records.app/jcl/CREASTMT.JCL:22-39Running the job twice in a row, or on an estate where the work store does not exist, ends DELDEF01 with RC 0 and leaves a work store holding only the current TRANSACT data.

6.3 Restart / checkpoint semantics

The chain has no checkpoints, commits or restart keys. CREASTMT is a full rebuild: DELDEF01 deletes and redefines the work store (CREASTMT.JCL:22-39), STEP010 / STEP020 recreate it (:44-62), STEP030 deletes the previous outputs (:66-75) and STEP040 creates them anew with DISP=(NEW,CATLG,DELETE), so an abend leaves no partial statement files (:87-96). The only valid restart point is the top of CREASTMT; restarting at STEP040 needs STEP030 rerun first (section 6.2). CBSTM03A holds the whole transaction set in working storage and writes statements only after loading it (CBSTM03A.CBL:730-761, 818-853, 316-329), so there is no in-flight state to recover. All four VSAM inputs are opened INPUT (CBSTM03B.CBL:136, 160, 184, 209); no backout job exists or is needed. CLOSEFIL, WAITSTEP and OPENFIL are stateless and idempotent. There is no "already ran today" guard: a second run regenerates the same statements. In the target, rerun identity comes from the job parameters (business run date) (docs/migration/CardDemo_target_state.md:98).
