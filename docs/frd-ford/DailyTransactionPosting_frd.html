1. Business purpose

DailyTransactionPosting is the CARDDEMO batch network that turns the day’s captured card transactions into posted history and updated balances. CLOSEFIL first takes five files away from the online region (app/jcl/CLOSEFIL.jcl:22-30) so batch can update them. CBPAUP0J runs the IMS BMP CBPAUP0C, which deletes pending authorizations older than the expiry window from the DBPAUTP0 database (app/app-authorization-ims-db2-mq/jcl/CBPAUP0J.jcl:24-25). POSTTRAN runs CBTRN02C (app/jcl/POSTTRAN.jcl:23): it reads the sequential daily file DALYTRAN, validates each record against the card cross-reference and the account master, writes accepted records to the transaction master TRANSACT, adds the amount to the account balances and to the per-account category balance, and writes rejected records with a reason trailer to a new DALYREJS generation (app/cbl/CBTRN02C.cbl:193-234). WAITSTEP waits 36 seconds (app/jcl/WAITSTEP.jcl:26) and OPENFIL gives the files back to CICS (app/jcl/OPENFIL.jcl:22-30).

If the network does not run, the day’s transactions are not posted: the online transaction screens show stale history, current balances and cycle credit/debit totals are wrong for the interest and statement cycles that read them, and expired authorizations stay in the pending-authorization database. If it stops after CLOSEFIL and before OPENFIL, the five CICS files stay closed and every online function that reads them (sign-on included, through USRSEC) fails.

Business capabilityHow this stream serves it
Transaction postingEach valid DALYTRAN record becomes a TRANSACT record stamped with a processing timestamp (CBTRN02C.cbl:424-444).
Account balance maintenanceACCT-CURR-BAL and ACCT-CURR-CYC-CREDIT / ACCT-CURR-CYC-DEBIT updated per posted transaction (CBTRN02C.cbl:545-560).
Category balancesOne TCATBALF balance per (account, type, category), created or incremented (CBTRN02C.cbl:467-542); read later by INTCALC and the category-balance print.
Exception handlingUnknown card, missing account, over-limit and post-expiry transactions are written to DALYREJS(+1) with a 4-digit reason and text (CBTRN02C.cbl:380-422, 446-465).
Authorization housekeepingExpired pending-authorization details are deleted and the account summary is deleted when its approved count reaches zero (CBPAUP0C.cbl:142-167, 277-348).
Online availabilityCICS files TRANSACT, CCXREF, ACCTDAT, CXACAIX, USRSEC closed before and reopened after the batch work (CLOSEFIL.jcl:26-30, OPENFIL.jcl:26-30).

Gating conditions: CA-7 releases each successor on completion of its predecessor through TRIGGERED JOBS ... SCHID=030 QTM=0100 LEADTM=0000 (CardDemo.ca7:43, 70, 97, 124). None of the five LJOB blocks lists a requirement, calendar or condition-code test, and the OPENFIL block reports N -- COMP TRIGGERS OTHER JOBS with no TRIGGERED JOBS section (CardDemo.ca7:126-148), so OPENFIL ends this network. No JCL member carries a COND= parameter and each has a single step, so a non-zero RC does not stop the chain by itself: POSTTRAN ending RC 4 because of rejects (CBTRN02C.cbl:229-231) still triggers WAITSTEP. Whether CA-7 withholds a trigger after CBPAUP0C’s RC 16 (CBPAUP0C.cbl:380-383) or a CBTRN02C U0999 abend (CBTRN02C.cbl:707-711) is not stated in the listing (Q-03). Scheduler mismatch: Control-M folder DAILY-TransactionBackup is CLOSEFIL → TRANBKP → WAITSTEP → OPENFIL, gated by IN/OUT conditions (CardDemo.controlm:4-24, DAYS="ALL", TIMETO="23:00", MAXRERUN="5"). It has no CBPAUP0J or POSTTRAN, and CardDemo.ca7 never mentions TRANBKP. This document records the CA-7 network as written and does not assert a combined chain (Q-01).

5. Functional requirements

IDRequirementSourceAcceptance criteria
FR-01CLOSEFIL closes exactly the CICS files TRANSACT, CCXREF, ACCTDAT, CXACAIX and USRSEC, in that order, in region CICSAWSA with CEMT SET FIL(x) CLO.app/jcl/CLOSEFIL.jcl:22-30The target quiesce step (or its documented removal) covers the data behind those five files and nothing else; the run log lists the five actions in order.
FR-02OPENFIL reopens the same five files with CEMT SET FIL(x) OPE, runs only after WAITSTEP completes, and triggers nothing in this network.app/jcl/OPENFIL.jcl:22-30; app/scheduler/CardDemo.ca7:124, 126-148After the chain the five files are available online; OPENFIL never starts before WAITSTEP ends; no successor is released by OPENFIL in the posting network.
FR-03CBPAUP0J runs CBPAUP0C as an IMS BMP under DFSRRC00 with PSB PSBPAUTB, using the DB PCB (number 2) over PAUTSUM0 / PAUTDTL1 with PROCOPT=AP.app/app-authorization-ims-db2-mq/jcl/CBPAUP0J.jcl:24-25; ims/PSBPAUTB.psb:17-20; cbl/CBPAUP0C.cbl:80-82The target CBPAUP0J job reads and deletes pending-authorization summaries and details only; it never inserts or replaces them.
FR-04CBPAUP0C reads one SYSIN card ee,fffff,ddddd,x: expiry days 2 digits (5 if non-numeric), checkpoint frequency (5 if spaces, zero or low-values), checkpoint display frequency (10 if spaces, zero or low-values), debug flag (anything but Y becomes N). The shipped card is 00,00001,00001,Y.CBPAUP0C.cbl:98-108, 189-209; CBPAUP0J.jcl:37With the shipped card the run logs CBPAUP0C PARM RECEIVED :00,00001,00001,Y and uses expiry 0, debug on; with a blank card it uses 5 / 5 / 10 / N.
FR-05A detail is expired when CURRENT-YYDDD − (99999 − PA-AUTH-DATE-9C) ≥ expiry days. An expired detail with response code '00' reduces the in-memory approved count by 1 and approved amount by PA-APPROVED-AMT; any other code reduces the declined count by 1 and declined amount by PA-TRANSACTION-AMT; the detail is then deleted (DLET).CBPAUP0C / 4000-CHECK-IF-EXPIRED, 5000-DELETE-AUTH-DTL (CBPAUP0C.cbl:277-325)With expiry 5 and details dated today, today−4 and today−5 (YYDDD), only the today−5 detail is deleted and its counters are subtracted. The comparison is plain YYDDD arithmetic, not calendar dates (Q-10).
FR-06After its details, a root is deleted when PA-APPROVED-AUTH-CNT ≤ 0. The source tests the approved count twice and never the declined count, and a kept root is never rewritten (no REPL), so the adjusted counters are not saved.CBPAUP0C.cbl:156-158, 328-349A root with approved count 0 and declined count 3 is deleted; a root with approved count 1 is kept with its stored counters unchanged (Q-11).
FR-07CBPAUP0C issues CHKP ID(WK-CHKPT-ID) when WS-AUTH-SMRY-PROC-CNT > P-CHKP-FREQ (strictly greater, then the counter resets) and once more at end of run. The checkpoint id is the constant RMAD0000 and no XRST is issued.CBPAUP0C.cbl:75-77, 160-164, 169, 352-374The final CHKP is always taken; a restart reprocesses from the first root. Because P-CHKP-FREQ is PIC X(5) and the counter is PIC 9(8), the interval actually used must be confirmed by a compiled test before the target picks a commit interval (Q-12).
FR-08Any DL/I status other than blank (or GB on GN, GE / GB on GNP) makes CBPAUP0C display the failing call and status, display CBPAUP0C ABENDING ..., set RETURN-CODE 16 and GOBACK. A clean run prints the four totals: summaries read, summaries deleted, details read, details deleted.CBPAUP0C.cbl:228-241, 259-271, 315-321, 340-346, 358-370, 173-176, 377-383A forced DLET failure ends the job RC 16 with no abend code; a clean run ends RC 0 and the four counters match the fixture.
FR-09CBTRN02C opens its six files in this order and mode: DALYTRAN INPUT, TRANFILE OUTPUT, XREFFILE INPUT, DALYREJS OUTPUT, ACCTFILE I-O, TCATBALF I-O. TRANFILE OUTPUT means posting loads the transaction master rather than appending. Any open status other than '00' abends.CBTRN02C.cbl:195-200, 236-343After a run the transaction master holds only this run’s transactions; a missing input ends with ERROR OPENING ..., FILE STATUS IS: NNNN and abend U0999.
FR-10Daily records are processed in file order in one pass. Status '10' ends the loop; any other non-'00' read status abends. Each record adds 1 to TRANSACTIONS PROCESSED, resets the reason to 0, then is either posted (reason 0) or rejected.CBTRN02C.cbl:202-219, 345-369For N input records, PROCESSED = N and posted + rejected = N; an empty file gives counts 0 and RC 0.
FR-11A record whose DALYTRAN-CARD-NUM is not in CARDXREF is rejected with reason 0100, text INVALID CARD NUMBER FOUND; the account checks are skipped.CBTRN02C / 1500-A-LOOKUP-XREF (CBTRN02C.cbl:370-392)Unknown card → one reject with trailer starting 0100INVALID CARD NUMBER FOUND; no account or category balance change.
FR-12The account is read by XREF-ACCT-ID from the cross-reference, never from the transaction. A missing account is rejected with 0101, ACCOUNT RECORD NOT FOUND.CBTRN02C / 1500-B-LOOKUP-ACCT (CBTRN02C.cbl:393-399)Card in XREF but account absent → trailer 0101ACCOUNT RECORD NOT FOUND.
FR-13Over-limit: WS-TEMP-BAL = ACCT-CURR-CYC-CREDIT − ACCT-CURR-CYC-DEBIT + DALYTRAN-AMT; the record passes when ACCT-CREDIT-LIMIT ≥ WS-TEMP-BAL, otherwise reason 0102 OVERLIMIT TRANSACTION. ACCT-CURR-BAL is not used.CBTRN02C.cbl:403-413Limit 1000.00, cycle credit 900.00, cycle debit 0: amount 100.00 is accepted, 100.01 is rejected 0102.
FR-14Expiry: when ACCT-EXPIRAION-DATE is less than DALYTRAN-ORIG-TS(1:10) (character compare), reason 0103 TRANSACTION RECEIVED AFTER ACCT EXPIRATION. The check runs even after an over-limit failure and overwrites 0102.CBTRN02C.cbl:414-420Expiry 2025-12-31 with origin timestamp 2025-12-31-23.59.59.000000 is accepted; 2026-01-01-… is rejected 0103; a record both over-limit and expired reports 0103 only.
FR-15A rejected record has no other effect and produces one 430-byte reject record: the unchanged 350-byte DALYTRAN image plus an 80-byte trailer (4-digit reason + 76-character description). The file is a new GDG generation, RECFM=F LRECL=430.CBTRN02C / 2500-WRITE-REJECT-REC (CBTRN02C.cbl:176-182, 446-465); POSTTRAN.jcl:34-38Bytes 1-350 of the reject equal the input record; 351-354 = reason; 355-430 = description padded with spaces; the account and category balances are unchanged.
FR-16A posted record copies ID, type, category, source, description, amount, merchant ID / name / city / ZIP, card number and origin timestamp from the daily record; TRAN-PROC-TS is set to the current time as YYYY-MM-DD-HH.MM.SS.hh0000. The daily record’s own PROC-TS is not used.CBTRN02C / 2000-POST-TRANSACTION, Z-GET-DB2-FORMAT-TIMESTAMP (CBTRN02C.cbl:424-438, 692-705)Posted bytes 1-304 equal input bytes 1-304; bytes 305-330 match \d{4}-\d{2}-\d{2}-\d{2}\.\d{2}\.\d{2}\.\d{2}0000 and fall inside the run window.
FR-17Category balance key = (XREF-ACCT-ID, type, category). If no record exists the program logs TCATBAL record not found for key : <key>.. Creating. and writes one with balance = amount; otherwise it adds the amount and rewrites. Any other status abends.CBTRN02C / 2700-UPDATE-TCATBAL (CBTRN02C.cbl:467-542)Transactions of 10.00 and −2.50 for a new key leave one record with balance 7.50 and one “Creating.” log line.
FR-18Account update: ACCT-CURR-BAL += amount; amount ≥ 0 adds to ACCT-CURR-CYC-CREDIT, otherwise to ACCT-CURR-CYC-DEBIT (negative values accumulate). The record is rewritten; INVALID KEY sets reason 0109, but the record is already being posted and the reason is reset before the next record, so 0109 never reaches the reject file.CBTRN02C / 2800-UPDATE-ACCOUNT-REC (CBTRN02C.cbl:545-560, 208)+25.00 raises current balance and cycle credit by 25.00; −25.00 lowers the balance by 25.00 and adds −25.00 to cycle debit; no reject record carries 0109.
FR-19Per posted record the update order is TCATBALF, then ACCTFILE, then TRANFILE. Effects accumulate in input order. 6.3 Restart / checkpoint semantics

POSTTRAN / CBTRN02C has no checkpoint, commit interval or restart key; it is one pass over DALYTRAN (CBTRN02C.cbl:202-219). TRANFILE is OPEN OUTPUT (:256), so a cold rerun reloads the transaction master, and DALYREJS(+1) DISP=(NEW,CATLG,DELETE) (POSTTRAN.jcl:34) gives a fresh reject generation. ACCTFILE REWRITEs (:554) and TCATBALF WRITE / REWRITEs (:510, :528) are made in place and are not reversed on abend, so a rerun after a partial run counts every already-posted transaction twice. The legacy recovery is therefore: restore ACCTDATA and TCATBALF, make TRANSACT reusable, rerun POSTTRAN from the top.

CBPAUP0J / CBPAUP0C takes EXEC DLI CHKP ID(WK-CHKPT-ID) when the per-interval root count exceeds P-CHKP-FREQ and once at end of run (CBPAUP0C.cbl:160-164, 169, 355), always with id RMAD0000 (:75-77) and no XRST. A restart reprocesses from the first root; work committed at earlier checkpoints is already applied and is not repeated.

CLOSEFIL, WAITSTEP, OPENFIL are stateless and can be rerun at any time. If the chain stops between CLOSEFIL and OPENFIL, run OPENFIL by hand to restore online service.
