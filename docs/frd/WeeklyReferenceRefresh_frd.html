1. Business purpose

CardDemo keeps its transaction-type reference data twice: as DB2 tables CARDDEMO.TRANSACTION_TYPE / CARDDEMO.TRANSACTION_TYPE_CATEGORY maintained by administrators (online CTLI/CTTU and the batch job MNTTRDB2), and as 60-byte flat files that are later copied into the VSAM KSDS files read by transaction reporting (app/app-transaction-type-db2/README.md:139-142). The weekly cycle applies the pending batch maintenance (MNTTRDB2 → COBTUPDT), then re-extracts both tables to AWS.M2.CARDDEMO.TRANTYPE.PS and AWS.M2.CARDDEMO.TRANCATG.PS after backing up the previous versions to a GDG (TRANEXTR). In parallel it rebuilds the disclosure-group file AWS.M2.CARDDEMO.DISCGRP.VSAM.KSDS from the sequential seed AWS.M2.CARDDEMO.DISCGRP.PS (DISCGRP), with the online files closed and re-opened around the load (CLOSEFIL / OPENFIL) and a fixed 36-second settle wait (WAITSTEP). The disclosure-group file supplies the interest rate per account group / transaction type / category to the monthly interest calculation (CBACT04C).

If the cycle does not run, transaction-type and category changes made in DB2 never reach the flat-file copies that feed the transaction report, and the disclosure-group VSAM file is not rebuilt from its seed. The online files CLOSEFIL closes stay closed if the chain stalls after CLOSEFIL, which blocks sign-on (USRSEC) and every VSAM-backed CICS transaction.

Gating conditions (Control-M, app/scheduler/CardDemo.controlm): MNTTRDB2 has no INCOND and adds WEEKLY-TransactionTypesDBRefresh-MNTTRDB2 (ODATE=ODAT, SIGN=+) on completion (:27-28). TRANEXTR (:58-59) and CLOSEFIL (:33-34) each carry that condition as their only INCOND (AND_OR=A), so both smart folders are released by the same event and run in parallel. Inside DisclosureGroupsRefresh each job adds WEEKLY-DisclosureGroupsRefresh-<job> and the successor removes it: CLOSEFIL +CLOSEFIL (:35); DISCGRP waits on CLOSEFIL, removes it, adds +DISCGRP (:39-41); WAITSTEP waits on DISCGRP, removes it, adds +WAITSTEP (:45-47); OPENFIL waits on WAITSTEP and removes it (:51-52). The MNTTRDB2 condition is removed by a SIGN="-" OUTCOND on both smart folders (:55 and :62) — whichever folder completes first deletes the release condition the other folder's first job still depends on (Q-01). Step gating inside TRANEXTR: STEP20/30/40 run only if every prior step ended RC 0 (COND=(0,NE), app/jcl/TRANEXTR.jcl:42,53,65); STEP50 tolerates RC 4 (COND=(4,LT), :95). MNTTRDB2 and DISCGRP steps have no COND=. No ON/DO statements define an OK/NOTOK threshold for the RC 4 that COBTUPDT can return (Q-08).

Scheduler-source gotcha: this chain exists only in Control-M. app/scheduler/CardDemo.ca7 has no LJOB entry for MNTTRDB2, TRANEXTR or DISCGRP; its CLOSEFIL / WAITSTEP / OPENFIL entries belong to other networks (SCHID 030/031/032). The two sources also disagree on the daily chain: CA-7 SCHID=030 is CLOSEFIL → CBPAUP0J → POSTTRAN → WAITSTEP → OPENFIL (CardDemo.ca7:43,70,97,124, no TRANBKP), while Control-M DAILY-TransactionBackup is CLOSEFIL → TRANBKP → WAITSTEP → OPENFIL (CardDemo.controlm:3-25, no POSTTRAN). Neither should be presented as a single combined daily chain (Q-03).

5. Functional requirements

IDRequirementSourceAcceptance criteria
FR-01MNTTRDB2 is the chain head. On its completion the scheduler adds condition WEEKLY-TransactionTypesDBRefresh-MNTTRDB2 for the order date; TRANEXTR and CLOSEFIL each wait on exactly that condition and nothing else, so both are released together.app/scheduler/CardDemo.controlm:27-28, 33-34, 58-59For a given ODAT neither TRANEXTR nor CLOSEFIL starts before MNTTRDB2 ends; after MNTTRDB2 ends both become eligible in the same scheduling pass.
FR-02DisclosureGroupsRefresh runs strictly serially: CLOSEFIL → DISCGRP → WAITSTEP → OPENFIL. Each job adds WEEKLY-DisclosureGroupsRefresh-<self> and the successor removes its predecessor's condition when it runs.app/scheduler/CardDemo.controlm:35, 39-41, 45-47, 51-52No two jobs of the folder are active simultaneously; after OPENFIL ends, none of the four folder conditions remains for that ODAT.
FR-03MNTTRDB2 reads INPFILE sequentially as fixed 53-byte records: column 1 operation, columns 2-3 transaction type, columns 4-53 description. The file is opened INPUT and read to end-of-file.app/app-transaction-type-db2/cbl/COBTUPDT.cbl:31-34, 39-46, 83, 91-103; jcl/MNTTRDB2.jcl:11-18A file of N records produces N PROCESSING lines in file order; records beyond column 53 are ignored; the loop ends on AT END.
FR-04The operation code dispatches: A insert, U update, D delete, * comment (skipped with IGNORING COMMENTED LINE); any other value displays ERROR: TYPE NOT VALID and raises the warning return code (FR-08).app/app-transaction-type-db2/cbl/COBTUPDT.cbl:109-130Record *xx... changes nothing and does not affect the RC; record Zxx... changes nothing, logs the error text, and the job ends RC 4.
FR-05A inserts (TR_TYPE, TR_DESCRIPTION) from columns 2-3 and 4-53. SQLCODE 0 displays RECORD INSERTED SUCCESSFULLY; a negative SQLCODE (e.g. duplicate primary key) displays Error accessing: TRANSACTION_TYPE table. SQLCODE:nnnn and raises RC 4.app/app-transaction-type-db2/cbl/COBTUPDT.cbl:137-163; ddl/TRNTYPE.ddl:4Inserting a new type creates one row with the 2-char code; inserting an existing code leaves the table unchanged and ends RC 4 with the error text.
FR-06U sets TR_DESCRIPTION where TR_TYPE matches. SQLCODE 0 displays RECORD UPDATED SUCCESSFULLY; SQLCODE +100 displays No records found. and raises RC 4; negative SQLCODE raises RC 4 with the error text.app/app-transaction-type-db2/cbl/COBTUPDT.cbl:171-194Updating code 01 changes only that row's description; updating a missing code changes nothing and ends RC 4 with No records found.
FR-07D deletes the row where TR_TYPE matches. SQLCODE 0 displays RECORD DELETED SUCCESSFULLY; +100 displays No records found. and raises RC 4; a negative SQLCODE (including the FK ON DELETE RESTRICT from TRANSACTION_TYPE_CATEGORY) raises RC 4 with the error text and leaves the row in place.app/app-transaction-type-db2/cbl/COBTUPDT.cbl:201-225; ddl/TRNTYCAT.ddl:6-7Deleting a type with categories leaves both tables unchanged and ends RC 4; deleting a type without categories removes exactly one row.
FR-08Error handling is non-fatal: 9999-ABEND displays the message, moves 4 to RETURN-CODE and returns to the read loop. Later records are still applied, the program issues no ROLLBACK, and the step ends with condition code 4 (never higher) when at least one record failed.app/app-transaction-type-db2/cbl/COBTUPDT.cbl:93-96, 230-233Input [valid A, invalid op, valid U]: both valid changes are present after the job; step CC = 4. Input with no failures: CC = 0.
FR-09No field validation is applied before the SQL: the type code is passed as 2 characters without a numeric check (despite the JCL comment "NUMERIC VALUE"), and the description is passed as the fixed 50-byte field including trailing blanks.app/app-transaction-type-db2/cbl/COBTUPDT.cbl:71-77, 145-146, 173; jcl/MNTTRDB2.jcl:16Record AXYtest inserts TR_TYPE XY; the stored description for a 4-character input is the 4 characters followed by 46 blanks (Q-13 for the target).
FR-10A failed OPEN of INPFILE displays OPEN FILE NOT OK but does not stop the program; no FILE STATUS is tested after READ.app/app-transaction-type-db2/cbl/COBTUPDT.cbl:83-88, 101-103With INPFILE unallocated or unreadable the job does not abend in COBTUPDT's own logic; the message is in SYSOUT (debt, Q-07).
FR-11Every record read is echoed as PROCESSING <53-byte record>, preceded by OPEN FILE OK and followed by the per-operation messages ADDING RECORD / UPDATING RECORD / DELETING RECORD.app/app-transaction-type-db2/cbl/COBTUPDT.cbl:85, 104-106, 112, 115, 118SYSOUT of a 3-record run contains exactly 3 PROCESSING lines with the literal three-space separator and the record text.
FR-12TRANEXTR STEP10/STEP20 copy the current TRANTYPE.PS and TRANCATG.PS to the next generation (+1) of their GDGs as FB 60 / BLKSIZE 600, DISP=(NEW,CATLG). STEP20 runs only if STEP10 ended RC 0. A missing source dataset is a JCL error.app/app-transaction-type-db2/jcl/TRANEXTR.jcl:31-49; app/jcl/DEFGDGD.jcl:28-29, 51-52After the job, generation n+1 of each GDG exists and is byte-identical to the previous PS; with LIMIT(5) the sixth run rolls off the oldest generation; a run without TRANTYPE.PS fails in STEP10 and performs no unload.
FR-13STEP30 deletes both PS datasets (DISP=(MOD,DELETE,DELETE)) so the unload can recreate them; it is bypassed if any earlier step ended non-zero.app/app-transaction-type-db2/jcl/TRANEXTR.jcl:53-61Between STEP30 and STEP40 neither PS dataset is catalogued; if STEP10/20 fail both datasets are untouched.
FR-14STEP40 unloads TRANSACTION_TYPE into a new TRANTYPE.PS as CHAR(60) records: TR_TYPE (2) + TR_DESCRIPTION cast to CHAR(50) (blank padded) + '00000000', ordered by TR_TYPE. The layout equals TRAN-TYPE-RECORD.app/app-transaction-type-db2/jcl/TRANEXTR.jcl:65-91; app/cpy/CVTRA03Y.cpy:4-7With the 7 seeded types the file is 7 × 60 bytes in ascending code order; record 1 is 01 + PURCHASE padded to 50 + eight zeros; it REPROs into a KSDS KEYS(2 0) RECORDSIZE(60 60) without error (app/jcl/TRANTYPE.jcl:40-41).
FR-15STEP50 unloads TRANSACTION_TYPE_CATEGORY into a new TRANCATG.PS as CHAR(60) records: TRC_TYPE_CODE (2) + TRC_TYPE_CATEGORY (4) + TRC_CAT_DATA cast to CHAR(50) + '0000', ordered by code then category. 6.3 Restart / checkpoint semantics

No job in the chain takes checkpoints. COBTUPDT issues no COMMIT or ROLLBACK (app/app-transaction-type-db2/cbl/COBTUPDT.cbl:50-236 contains none); each SQL statement that succeeds stays in effect regardless of later record failures, and the unit of work closes when the IKJEFT01 step ends. A rerun of MNTTRDB2 with the same INPFILE is not idempotent: every previously successful A record now fails as a duplicate and every successful D record now fails with No records found. (FR-05, FR-07), so the rerun ends RC 4 and the operator must trim the input to the failed records. TRANEXTR is restartable from the top as long as both PS datasets exist: STEP10/20 add one more GDG generation each (LIMIT(5) rolls off the oldest), STEP30 deletes, STEP40/50 rebuild. If a run fails after STEP30 and before STEP40/50 completes, the PS datasets are gone and a top restart JCL-errors in STEP10; restart at STEP40 (or STEP50) instead. DISCGRP is cold-rerunnable from STEP05 because it deletes and redefines the cluster every run. CLOSEFIL, WAITSTEP and OPENFIL are idempotent. Control-M allows MAXRERUN="5" automatic reruns and MAXWAIT="7" days in the active environment per job (app/scheduler/CardDemo.controlm:27,33,38,44,50,58). A failed DISCGRP leaves the five CICS files closed until OPENFIL is run manually (FR-17). The TRANEXTR comment that it "runs once a day" (jcl/TRANEXTR.jcl:19-21) contradicts the weekly folder (Q-06).
