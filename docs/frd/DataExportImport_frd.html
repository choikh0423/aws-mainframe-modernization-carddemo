1. Business purpose

The DataExportImport chain moves a complete copy of the CardDemo master data between systems. CBEXPORT reads every record of the customer, account, card cross-reference, transaction and card VSAM clusters and writes them, in that order, into a single multi-record export cluster AWS.M2.CARDDEMO.EXPORT.DATA whose records carry a one-byte type code, a run timestamp, a global sequence number and a branch/region stamp (app/cbl/CBEXPORT.cbl:5-10, app/cbl/CBEXPORT.cbl:27-30). FTPJCL is the estate's only transport artefact: a PGM=FTP job that pushes a mainframe dataset to an external FTP server (app/jcl/FTPJCL.JCL:22-29). CBIMPORT reads the export file and splits it back into one normalised flat file per record type, writing an error line for every record whose type it does not recognise (app/cbl/CBIMPORT.cbl:5-11, app/cbl/CBIMPORT.cbl:28-32).

The chain has no scheduler entry: neither CBEXPORT, CBIMPORT nor FTPJCLS appears in the CA-7 LJOB listing (app/scheduler/CardDemo.ca7, jobs listed at lines 18-337) or in any Control-M folder (app/scheduler/CardDemo.controlm, folders at lines 3, 26, 32, 57, 64), and the README's "Running Batch Jobs" run-book does not list them either (README.md:207-230). It is an operator-triggered chain whose order is fixed by the data flow: the export file must exist before it can be transferred or imported. If it does not run, no branch/estate data copy is produced; the daily posting and statement cycles are unaffected because neither program updates a CardDemo master (app/cbl/CBEXPORT.cbl:35-69 opens the masters INPUT only; app/cbl/CBIMPORT.cbl:43-71 writes new sequential datasets, not the VSAM masters).

Business capabilityHow this stream serves it
Branch migration / bulk data transferProduces a self-describing, single-file snapshot of all five masters that can be shipped to another system (app/jcl/CBEXPORT.jcl:19-20).
Data on-boarding on the receiving sideRe-normalises the snapshot into copybook-layout flat files (CVCUS01Y, CVACT01Y, CVACT03Y, CVTRA05Y, CVACT02Y) that the estate's load jobs (CUSTFILE, ACCTFILE, XREFFILE, TRANBKP, CARDFILE) consume (app/jcl/CBIMPORT.jcl:19-20, README.md:213-217).
Operational controlBoth programs print per-type and total record counts so the operator can reconcile export against import (app/cbl/CBEXPORT.cbl:563-573, app/cbl/CBIMPORT.cbl:465-478).
Data-quality reportingUnknown record types are written to a 132-byte error file instead of stopping the run (app/cbl/CBIMPORT.cbl:425-446).

Gating conditions: There are no scheduler release rules for this chain: no CA-7 TRIGGERED JOBS block names CBEXPORT, CBIMPORT or FTPJCLS (app/scheduler/CardDemo.ca7) and no Control-M INCOND/OUTCOND references them (app/scheduler/CardDemo.controlm). Ordering is the operator's responsibility and follows the data dependency: CBIMPORT and FTPJCLS can only run after CBEXPORT has ended, because both read AWS.M2.CARDDEMO.EXPORT.DATA (app/jcl/CBEXPORT.jcl:62-63, app/jcl/CBIMPORT.jcl:28-29). Inside the jobs no step carries COND= or IF/THEN: CBEXPORT STEP02 runs regardless of the IDCAMS return code of STEP01 (app/jcl/CBEXPORT.jcl:24-43), and the IDCAMS SET MAXCC = 0 after the DELETE masks a "cluster not found" on first run (app/jcl/CBEXPORT.jcl:27-28). Failure in either COBOL program is signalled by an LE abend (CALL 'CEE3ABD', app/cbl/CBEXPORT.cbl:579, app/cbl/CBIMPORT.cbl:484), not by a return code. Estate gotcha: the two scheduler sources disagree on the daily chain that shares these masters — CA-7 SCHID=030 runs CLOSEFIL → CBPAUP0J → POSTTRAN → WAITSTEP → OPENFIL (app/scheduler/CardDemo.ca7:43-124), Control-M DAILY-TransactionBackup runs CLOSEFIL → TRANBKP → WAITSTEP → OPENFIL (app/scheduler/CardDemo.controlm:3-50) — so the window in which CICS has TRANSACT/CCXREF/ACCTDAT closed cannot be asserted from a single source (see Q-02, Q-06). CLOSEFIL1/CLOSEFIL2 are not touched by this chain.

5. Functional requirements

IDRequirementSourceAcceptance criteria
FR-01Every CBEXPORT run starts from an empty export file: the export cluster is deleted (PURGE) and redefined before the program runs; a missing cluster on first run is not an error (SET MAXCC = 0).app/jcl/CBEXPORT.jcl:27-38Running the export twice yields a file containing only the second run's records; the first run on a clean system ends RC 0.
FR-02CBEXPORT opens the five masters INPUT and the export file OUTPUT; any file status other than 00 on OPEN displays ERROR: Cannot open <FD-NAME>, Status: nn and abends.app/cbl/CBEXPORT.cbl:198-240With one master absent, the job log shows that exact line naming the COBOL FD (e.g. CUSTOMER-INPUT) followed by CBEXPORT: ABENDING PROGRAM, and no export records are written.
FR-03Export order is by file then by key: all customers, then accounts, then cross-references, then transactions, then cards; each KSDS is read with ACCESS MODE IS SEQUENTIAL, i.e. ascending key order, and every record is exported (no selection).app/cbl/CBEXPORT.cbl:35-63, 151-157, 249-252The type bytes of the export file form exactly five contiguous runs C, A, X, T, D whose lengths equal the record counts of the five masters; within each run the mapped key fields are ascending.
FR-04Record type codes are C customer, A account, X card cross-reference, T transaction, D card, in byte 0 of the record.app/cbl/CBEXPORT.cbl:274, 343, 407, 462, 527; app/cpy/CVEXPORT.cpy:10Each export record's first byte is one of the five codes and matches its source file.
FR-05One run timestamp is captured at start (ACCEPT ... FROM DATE YYYYMMDD/TIME) and formatted as YYYY-MM-DD HH:MM:SS.00 (22 characters, hundredths literal .00) into the 26-byte EXPORT-TIMESTAMP of every record.app/cbl/CBEXPORT.cbl:172-195, 275; app/cpy/CVEXPORT.cpy:11-15All records of one run carry the identical timestamp at offset 1-26, ending in .00 followed by four spaces.
FR-06A single 1-based sequence counter is incremented once per written record across all five groups and stored as a 4-byte binary PIC 9(9) COMP at offset 27.app/cbl/CBEXPORT.cbl:123, 276-277; app/cpy/CVEXPORT.cpy:16Sequence numbers run 1..N without gaps or repeats across the whole file, N = total records exported.
FR-07Branch id and region code are constants '0001' and 'NORTH' on every record; there is no branch parameter.app/cbl/CBEXPORT.cbl:278-279, 347-348, 411-412, 466-467, 531-532Bytes 31-34 are 0001 and 35-39 are NORTH on every record regardless of input data.
FR-08Each export record is INITIALIZEd, then source fields are moved 1:1 into the type-specific REDEFINES of CVEXPORT, including its COMP and COMP-3 fields; unmapped tail bytes are spaces (alphanumeric) / zero (numeric).app/cbl/CBEXPORT.cbl:271-299, 340-362, 404-417, 459-482, 524-540; app/cpy/CVEXPORT.cpy:24-100For a known source record, the export record decoded with CVEXPORT yields identical field values (names, addresses, signed amounts incl. negative and zero, FICO, CVV, 26-char timestamps); FILLER areas are spaces.
FR-09A READ with status other than 00/10 or a WRITE with status other than 00 displays ERROR: Reading <FD>, Status: nn / ERROR: Writing export record, Status: nn and abends.app/cbl/CBEXPORT.cbl:258-266, 301-307 (and 327-335, 364-370, 391-399, 419-425, 446-454, 484-490, 511-519, 542-548)A write failure (e.g. export file full) terminates the run with those two lines and no success statistics.
FR-10CBEXPORT prints the fixed set of progress lines and, at end, per-type counts and a total, each counter as a 9-digit zero-padded number; total equals the sum of the five counts.app/cbl/CBEXPORT.cbl:138-144, 163-169, 245-255, 314-324, 378-388, 433-443, 498-508, 563-573Job log contains CBEXPORT: Total Records Exported: nnnnnnnnn equal to the file's record count and to the sum of the five per-type lines.
FR-11CBIMPORT opens the export file INPUT and six outputs OUTPUT (customer, account, xref, transaction, card, error); an OPEN failure displays ERROR: Cannot open <FD>, Status: nn and abends. Outputs are new datasets (DISP=(NEW,CATLG,DELETE)), so the import replaces rather than appends.app/cbl/CBIMPORT.cbl:198-245; app/jcl/CBIMPORT.jcl:33-60Missing export file → ERROR: Cannot open EXPORT-INPUT, Status: 35 then CBIMPORT: ABENDING PROGRAM; successful run creates all outputs with record lengths 500/300/50/350/150/132.
FR-12Dispatch is on EXPORT-REC-TYPE only: C/A/X/T/D records are mapped 1:1 back into CVCUS01Y/CVACT01Y/CVACT03Y/CVTRA05Y/CVACT02Y (all DISPLAY fields, signed amounts with trailing overpunch) and written to the matching output in input order.app/cbl/CBIMPORT.cbl:272-285, 288-320, 323-349, 352-369, 372-399, 402-422Export-then-import of a master file reproduces every field value; output files are byte-interchangeable with the corresponding app/data/ASCII unload layout.
FR-13No validation, de-duplication, sequence, timestamp, branch or referential check is performed on import; 3000-VALIDATE-IMPORT unconditionally displays CBIMPORT: Import validation completed and CBIMPORT: No validation errors detected. Duplicate keys are written as-is (outputs are sequential).app/cbl/CBIMPORT.cbl:272-285, 449-452An export file containing two records with the same CUST-ID produces two customer output records and the two validation lines are still printed.
FR-14A record whose type byte is not C/A/X/T/D is counted in WS-UNKNOWN-RECORD-TYPE-COUNT and one 132-byte error line is written: FUNCTION CURRENT-DATE (21 chars in X(26)) | type | 7-digit sequence | Unknown record type encountered padded to 50, then 43 spaces; processing continues.app/cbl/CBIMPORT.cbl:152-160, 283-284, 425-434A file with one Z record completes normally with Errors Written: 000000001, Unknown Record Types: 000000001, and ERROUT holds exactly one line in that layout.
FR-15A WRITE failure on a data output abends (ERROR: Writing <type> record, Status: nn), but a WRITE failure on the error file only displays ERROR: Writing error record, Status: nn and continues, still incrementing WS-ERROR-RECORDS-WRITTEN.app/cbl/CBIMPORT.cbl:312-318, 341-347, 361-367, 391-397, 414-420, 437-446Simulated error-file write failure: run completes with the message and the counter incremented; simulated customer-file write failure: run abends.
FR-16WS-TOTAL-RECORDS-READ counts every record read (including unknown types); per-type counters count records written; the end-of-run statistics print all eight counters as 9-digit numbers.app/cbl/CBIMPORT.cbl:140-147, 253, 465-478Total Records Read = sum of five Imported counts + Unknown Record Types.
FR-17Fatal errors in either program are signalled by <PGM>: ABENDING PROGRAM followed by CALL 'CEE3ABD' (LE abend); success is a normal GOBACK. No step carries COND=; neither program accepts PARM or SYSIN.app/cbl/CBEXPORT.cbl:158, 576-579; app/cbl/CBIMPORT.cbl:171, 481-484; app/jcl/CBEXPORT.jcl:24-43; app/jcl/CBIMPORT.jcl:22Successful run: all steps RC 0. Failure: step ends in an abend (no return code), message pair present in SYSOUT.
FR-18The transfer step uses in-stream FTP control cards: host, user id, password, ASCII, pwd, dir, cd /ftpfolder, PUT '<mainframe dsn>' <remote name>, QUIT; host/user/password are site placeholders to be edited before use. The hand-off of AWS.M2.CARDDEMO.EXPORT.DATA is therefore an operator/configuration concern, not program logic.app/jcl/FTPJCL.JCL:22-29, 30-41A migrated system exposes the transfer target (host/folder/credentials) as configuration outside the export and import components; no credential is embedded in program code.
FR-19CBIMPORT requires a card output (CARDOUT, 150-byte CVACT02Y records) even though CBIMPORT.jcl does not define it; the program is the specification.app/cbl/CBIMPORT.cbl:63-66, 101-104, 233-238, 402-422; app/jcl/CBIMPORT.jcl:22-65Importing a file with D records produces a card output file with one 150-byte record per D record.
FR-20Neither program mutates CardDemo master data: CBEXPORT only reads the masters; CBIMPORT only writes new flat files. Loading the import files into VSAM is left to the existing load jobs.app/cbl/CBEXPORT.cbl:200-228; app/cbl/CBIMPORT.cbl:43-71; app/jcl/CBIMPORT.jcl:33-60Master record counts and contents are identical before and after a full export/import cycle.
FR-21The export file is a KSDS keyed on the 4-byte sequence number (KEYS(4 28), 500-byte fixed records) and is written/read in ascending key order.app/jcl/CBEXPORT.jcl:30-36; app/cbl/CBEXPORT.cbl:65-69, 89-92; app/cbl/CBIMPORT.cbl:37-41, 76-79File length is an exact multiple of 500; records are retrievable in sequence-number order. (Key offset discrepancy: see Q-04.)

6. Restart, recovery & error handling

6.1 Return-code conventions

6.3 Restart / checkpoint semantics

Neither program has checkpoints, commit intervals or a restart key: both are single-pass, read-to-EOF programs that open their outputs with OPEN OUTPUT (app/cbl/CBEXPORT.cbl:235, app/cbl/CBIMPORT.cbl:205-240). Restart is always a cold rerun from the first step. For CBEXPORT the IDCAMS step guarantees a clean export cluster (app/jcl/CBEXPORT.jcl:27-38); for CBIMPORT the operator must first delete the catalogued outputs. There is no backout: the chain never updates a master, so nothing needs to be backed out (app/cbl/CBEXPORT.cbl:200-228, app/cbl/CBIMPORT.cbl:43-71). A re-export produces a new run timestamp and restarts the sequence at 1 (app/cbl/CBEXPORT.cbl:123, app/cbl/CBEXPORT.cbl:172-195).
