DailyTransactionBackup Batch

Daily quiesce of the CICS VSAM files, generation backup of the transaction master AWS.M2.CARDDEMO.TRANSACT.VSAM.KSDS to the TRANSACT.BKUP GDG, delete/re-define of the empty cluster, timed wait, and re-open of the files to CICS. No COBOL business program runs in this chain; its requirements are data-safety semantics.

1. Business purpose

The transaction master AWS.M2.CARDDEMO.TRANSACT.VSAM.KSDS is the only copy of the posted card transactions that CICS reads online (CSD FILE(TRANSACT), app/csd/CARDDEMO.CSD:76-77). It is defined with RECOVERY(NONE) and JOURNAL(NO) (app/csd/CARDDEMO.CSD:82-84), so CICS keeps no forward-recovery log for it. The posting program CBTRN02C opens the master OUTPUT (app/cbl/CBTRN02C.cbl:256), i.e. it replaces the file rather than appending to it. This chain exists to preserve the previous day's transactions before that replacement: TRANBKP copies every record to a new generation of the AWS.M2.CARDDEMO.TRANSACT.BKUP GDG and then deletes and re-defines the cluster empty (app/jcl/TRANBKP.jcl:23-67). CLOSEFIL and OPENFIL bracket the work so that CICS does not hold the dataset open while IDCAMS deletes it (app/jcl/CLOSEFIL.jcl:26-30, app/jcl/OPENFIL.jcl:26-30).

If the chain does not run, (a) the next POSTTRAN overwrites the master with no retained copy of the prior content, (b) COMBTRAN, which reads TRANSACT.BKUP(0) (app/jcl/COMBTRAN.jcl:23-24), combines a stale generation, and (c) if CLOSEFIL ran but OPENFIL did not, the five files stay closed to the CICS region and every online screen that reads them fails.

Business capabilityHow this stream serves it
Transaction history retentionKeeps the last five daily images of the posted-transaction master as GDG generations TRANSACT.BKUP(+1), LIMIT(5) SCRATCH (app/jcl/DEFGDGB.jcl:24-28; five generations G0072–G0076 are catalogued in app/catlg/LISTCAT.txt:1631-1643).
Daily transaction posting (S-11)Guarantees POSTTRAN starts from an empty, correctly defined master (KEYS(16 0), RECORDSIZE(350 350)) — the pre-condition CBTRN02C's OPEN OUTPUT relies on (app/jcl/TRANBKP.jcl:54-67, app/cbl/CBTRN02C.cbl:256).
Monthly interest cycle (S-12)Supplies the input TRANSACT.BKUP(0) that COMBTRAN merges with SYSTRAN(0) and reloads into the master (app/jcl/COMBTRAN.jcl:22-48).
Online card servicing availabilityCloses and re-opens TRANSACT, CCXREF, ACCTDAT, CXACAIX and USRSEC in region CICSAWSA so batch and CICS never share the datasets (app/jcl/CLOSEFIL.jcl:26-30, app/jcl/OPENFIL.jcl:26-30).

Gating conditions: Control-M releases each job on the predecessor's OUT condition for the same ODATE and deletes that condition when the successor runs: CLOSEFIL adds DAILY-TransactionBackup-CLOSEFIL (app/scheduler/CardDemo.controlm:5); TRANBKP has INCOND on it, removes it and adds DAILY-TransactionBackup-TRANBKP (:9-11); WAITSTEP consumes that and adds DAILY-TransactionBackup-WAITSTEP (:15-17); OPENFIL consumes that and adds nothing (:21-22), so the folder ends there. No job in the folder carries an ON/DO condition-code rule — release is on "job ended OK", not on a specific RC. Inside TRANBKP the only step gate is STEP10 EXEC PGM=IDCAMS,COND=(4,LT) (app/jcl/TRANBKP.jcl:51): the re-define is skipped if any earlier step returned RC > 4; the DELETE step has no COND and runs regardless of the REPRO result (:37). Scheduler disagreement: CA-7 has no TRANBKP at all. Its SCHID=030 daily network is CLOSEFIL → CBPAUP0J → POSTTRAN → WAITSTEP → OPENFIL (app/scheduler/CardDemo.ca7:43, :70, :97, :124; OPENFIL "N -- COMP TRIGGERS OTHER JOBS" at :138). The Control-M folder has TRANBKP and no POSTTRAN. This document describes the Control-M folder only and does not assert a combined CLOSEFIL → TRANBKP → POSTTRAN chain (Q-01).

5. Functional requirements

IDRequirementSourceAcceptance criteria
FR-01Before the backup starts, the five CICS files TRANSACT, CCXREF, ACCTDAT, CXACAIX and USRSEC are closed in region CICSAWSA so no online task holds the transaction master open.app/jcl/CLOSEFIL.jcl:22-30Given the chain is ordered, when TRANBKP starts, the online access path to the transaction store is disabled (legacy: CEMT INQ FIL(TRANSACT) shows CLOSED) and remains so until OPENFIL.
FR-02Jobs run strictly in the order CLOSEFIL → TRANBKP → WAITSTEP → OPENFIL; each successor is released only by its immediate predecessor's completion condition for the same ODATE.app/scheduler/CardDemo.controlm:5, :9, :15, :21With CLOSEFIL not yet ended OK, TRANBKP does not start; with TRANBKP not ended OK, WAITSTEP and OPENFIL do not start.
FR-03Each release condition is consumed by the successor (OUTCOND SIGN="-"), so one CLOSEFIL completion releases exactly one TRANBKP, one TRANBKP exactly one WAITSTEP, and so on.app/scheduler/CardDemo.controlm:10, :16, :22After OPENFIL ends, no DAILY-TransactionBackup-* condition remains for that ODATE; ordering the folder again requires a new CLOSEFIL run.
FR-04The entire content of the transaction master is copied to a new backup generation before any record is deleted (backup-before-empty).app/jcl/TRANBKP.jcl:23-33 (STEP05R precedes STEP05 at :37)Record count and byte content of TRANSACT.BKUP(+1) equal those of the master as it stood when CLOSEFIL completed; the copy is in ascending TRAN-ID (primary key) order.
FR-05The backup is a new catalogued generation with fixed 350-byte records; it is catalogued only if the copy step ends normally.app/jcl/TRANBKP.jcl:29-33 (DISP=(NEW,CATLG,DELETE), LRECL=350, RECFM=FB)After a successful run, the GDG has one more generation than before whose record length is 350 and whose layout is CVTRA05Y; after a failed copy step, no new generation is catalogued.
FR-06At most five backup generations are retained; creating a sixth scratches the oldest.app/jcl/DEFGDGB.jcl:24-28 (LIMIT(5) SCRATCH); app/catlg/LISTCAT.txt:1631-1643After six consecutive successful runs, exactly five generations exist and the earliest of the six is no longer available.
FR-07The most recent generation, whoever produced it, is the one downstream consumers read: COMBTRAN reads TRANSACT.BKUP(0), and TRANREPT also writes (+1) to the same GDG.app/jcl/COMBTRAN.jcl:23-24; app/jcl/TRANREPT.jcl:29-33A migrated backup store exposes a "latest generation" that is the newest image regardless of producing job, and TRANREPT runs between two TRANBKP runs do not cause COMBTRAN to read a stale TRANBKP image.
FR-08After the copy, both the base cluster and its alternate index are deleted; absence of either is tolerated (IDCAMS MAXCC ≤ 8 reset to 0).app/jcl/TRANBKP.jcl:40-45Running TRANBKP when the AIX (or the cluster) does not exist does not fail the job; after STEP05 neither TRANSACT.VSAM.KSDS nor TRANSACT.VSAM.AIX is catalogued.
FR-09The master is re-defined empty with exactly: INDEXED, KEYS(16 0), RECORDSIZE(350 350), SHAREOPTIONS(2 3), ERASE, CYLINDERS(1 5), VOLUMES(AWSHJ1), DATA component …KSDS.DATA, INDEX component …KSDS.INDEX.app/jcl/TRANBKP.jcl:54-67LISTCAT of the new cluster shows KEYLEN 16, RKP 0, AVGLRECL = MAXLRECL = 350, SHROPTNS(2,3), ERASE, and the component names above; the cluster contains zero records.
FR-10The re-define runs only if every earlier step ended with RC ≤ 4; the delete step runs unconditionally.app/jcl/TRANBKP.jcl:37 (no COND), :51 (COND=(4,LT))If STEP05R ends RC 8, STEP05 still executes and STEP10 is bypassed (FLUSH); if STEP05R ends RC 0 or 4, STEP10 executes.
FR-11On completion of TRANBKP the master holds zero records and no alternate index or path exists over it; the next loader (POSTTRAN's OPEN OUTPUT, or COMBTRAN's REPRO) therefore starts from empty.app/jcl/TRANBKP.jcl:40-67; app/cbl/CBTRN02C.cbl:256; app/jcl/COMBTRAN.jcl:41-48A count of the transaction store immediately after TRANBKP is 0; a subsequent POSTTRAN leaves it holding exactly the records it posted.
FR-12The primary key of the master is the 16-byte TRAN-ID at offset 0 and the record is 350 bytes — the cluster parameters must match the copybook, not the other way round.app/cpy/CVTRA05Y.cpy:4-5, :18; app/jcl/TRANBKP.jcl:58-59Inserting two records with the same TRAN-ID into the re-defined master is rejected as a duplicate key; a 351-byte record is rejected.
FR-13Rebuilding the access path by processing timestamp (TRANIDX) must define a NONUNIQUE, UPGRADE alternate index on the 26 bytes at offset 304 (TRAN-PROC-TS), RECORDSIZE(350,350), a PATH …AIX.PATH over it, and populate it with BLDINDEX from the base cluster.app/jcl/TRANIDX.jcl:25-34, :42-44, :52-54; app/cpy/CVTRA05Y.cpy:17After TRANIDX, reading via the path by a TRAN-PROC-TS value returns every record with that timestamp (duplicates allowed), and records written later through the base cluster are visible through the path (UPGRADE).
FR-14TRANIDX is not part of the DAILY-TransactionBackup folder or any CA-7 network; after TRANBKP the alternate index stays absent until TRANIDX (or TRANFILE) is run manually.app/scheduler/CardDemo.controlm:3-24 (no TRANIDX); app/scheduler/CardDemo.ca7 (no TRANIDX); README.md:230The migrated runbook either includes the index rebuild in the daily cycle or documents the manual step; no consumer depends on the AIX existing before TRANIDX has run.
FR-15WAITSTEP pauses the chain for the number of centiseconds in columns 1–8 of its single SYSIN record (shipped value 00003600 = 36 s) and always ends RC 0.app/jcl/WAITSTEP.jcl:20-26; app/cbl/COBSWAIT.cbl:31, :36-38; app/asm/MVSWAIT.asm:23, :26Elapsed time between TRANBKP end and OPENFIL start is ≥ 36 s; WAITSTEP completes with RC 0 and reads/writes no business data.
FR-16After the wait, the same five CICS files are re-opened in CICSAWSA, and the chain ends — OPENFIL releases nothing.app/jcl/OPENFIL.jcl:22-30; app/scheduler/CardDemo.controlm:20-24After OPENFIL, CEMT INQ FIL for TRANSACT, CCXREF, ACCTDAT, CXACAIX, USRSEC shows OPEN ENABLED; no further job is ordered by the folder.
FR-17The folder is ordered every calendar day of every month and each job must finish by 23:00; a job may wait up to 7 days for its condition and be rerun up to 5 times.app/scheduler/CardDemo.controlm:4, :8, :14, :20 (DAYS="ALL", JAN..DEC="1", TIMETO="23:00", MAXWAIT="7", MAXRERUN="5")The migrated schedule triggers the chain daily including weekends and holidays, flags any job still running at 23:00, and limits automatic reruns to five.
FR-18No release decision in the chain depends on a numeric return code: a job that ends OK releases its successor, a job that does not stops the chain. The only RC test is the in-job COND of FR-10.app/scheduler/CardDemo.controlm:3-24 (no ON/DO statements); app/jcl/TRANBKP.jcl:51A migrated chain treats "exit 0" as released and any other outcome as stop; it introduces no RC-4-is-OK tolerance between jobs that the legacy folder does not have.
FR-19TRANBKP is not idempotent: rerunning it after a successful copy creates a further generation containing the now-empty master, which becomes BKUP(0) and ages the real backup by one.app/jcl/TRANBKP.jcl:29-33 (unconditional (+1)); app/scheduler/CardDemo.controlm:8 (MAXRERUN="5")Documented and tested behaviour for a rerun: either the migrated backup is idempotent per ODATE (preferred, deviation to be approved) or the runbook forbids rerun after STEP05R succeeded (see Q-09).
FR-20The CICS TRANSACT file is defined RECOVERY(NONE), JOURNAL(NO), BACKUPTYPE(STATIC): the TRANBKP generation is the only point-in-time copy of posted transactions and must be durable for the retention period.app/csd/CARDDEMO.CSD:76-85The migrated backup artefact survives loss of the primary store and can restore the master to its state at CLOSEFIL time for any of the last five cycles.
FR-21Between CLOSEFIL and OPENFIL, batch readers of the master (CREASTMT SORTIN, CBEXPORT TRANSACT DD) that run concurrently see the master either complete (before STEP05) or empty (after STEP10), never a partially deleted cluster — the delete/define is a single IDCAMS boundary per step.app/jcl/TRANBKP.jcl:37-67; app/jcl/CREASTMT.JCL:45; app/jcl/CBEXPORT.jcl:55-56A reader started after TRANBKP completes reads zero records and does not fail on open; readers are not scheduled inside the folder (none in app/scheduler/CardDemo.controlm:3-24).

6.3 Restart / checkpoint semantics

There is no checkpoint and no commit interval: every step is a single IDCAMS or SDSF invocation that either completes or not. Restart rules that follow from the JCL: (1) CLOSEFIL, WAITSTEP and OPENFIL may be rerun at any time with no side effect (app/jcl/CLOSEFIL.jcl:26-30, app/jcl/WAITSTEP.jcl:22-26, app/jcl/OPENFIL.jcl:26-30). (2) TRANBKP that failed in STEP05R before cataloguing BKUP(+1) (DISP third parameter DELETE, app/jcl/TRANBKP.jcl:29) may be rerun from the top provided STEP05 has not already deleted the cluster; because STEP05 carries no COND (:37) that must be checked with LISTCAT first. (3) TRANBKP that failed in STEP10 must be restarted at STEP10 only (the backup generation already exists and the master is already gone); a rerun from the top would REPRO a missing or empty cluster and burn a generation (FR-19). (4) Control-M allows MAXRERUN 5 and MAXWAIT 7 (app/scheduler/CardDemo.controlm:8); the JCL has no RESTART= card, so step-level restart is an operator action. (5) The recovery copy for the master is always the newest generation TRANSACT.BKUP(0); the restore sequence is DEFINE CLUSTER (app/jcl/TRANBKP.jcl:54-67) → REPRO from the generation (pattern of app/jcl/COMBTRAN.jcl:41-48) → TRANIDX (app/jcl/TRANIDX.jcl:22-54). No backout job exists in the repo.
