1. Business purpose

The StatementGeneration chain produces the cardholder account statement for every card in the card/account cross-reference file. CREASTMT takes the posted transaction file (AWS.M2.CARDDEMO.TRANSACT.VSAM.KSDS), re-keys it by card number so that a card's transactions are contiguous, and runs CBSTM03A, which walks CARDXREF card by card, looks up the customer and account, and writes a statement in two renderings: a fixed-80-column plain-text file (STATEMNT.PS) and a 100-column HTML file (STATEMNT.HTML) (app/jcl/CREASTMT.JCL:19-20, 79-96; app/cbl/CBSTM03A.CBL:5-9). TXT2PDF1 then converts the text statement into STATEMNT.PS.PDF with the TSO TXT2PDF utility (app/jcl/TXT2PDF1.JCL:21, 38-39). Because the statement program reads the same VSAM files CICS serves online, the chain is bracketed by CLOSEFIL and OPENFIL, which close and re-open the CICS files, with a timed WAITSTEP before re-opening (app/jcl/CLOSEFIL.jcl:26-30; app/jcl/WAITSTEP.jcl:20-26; app/jcl/OPENFIL.jcl:26-30).

If the chain does not run, no customer statements (text, HTML or PDF) are produced for the cycle; the previous cycle's statement files remain cataloged until the next successful STEP030. If the chain starts but does not reach OPENFIL, the five CICS files stay closed and the online CardDemo transactions that use them fail until an operator re-opens them.

Business capabilityHow this stream serves it
Cardholder statement productionOne statement per CARDXREF card with customer name/address, account id, current balance, FICO score, itemised transactions and a total (CBSTM03A.CBL:316-329, 458-504).
Statement distribution formatsPlain-text (80-byte) and HTML (100-byte) renderings from one pass (CBSTM03A.CBL:44-47, 293); PDF from the text rendering (TXT2PDF1.JCL:38-39).
Transaction re-keying for statement useCard-keyed work copy of TRANSACT (TRXFL.VSAM.KSDS, key = card number + transaction id) rebuilt every run (CREASTMT.JCL:22-62).
Batch / online file hand-offCICS files are closed before and re-opened after the batch work (CLOSEFIL.jcl:26-30, OPENFIL.jcl:26-30), with a 36-second settle delay (WAITSTEP.jcl:26).

Gating conditions: The chain is a CA-7 trigger network, not a calendar: each job is released when its predecessor completes (TRIGGERED JOBS ... SCHID=030 QTM=0100 LEADTM=0000): CLOSEFIL→CREASTMT (CardDemo.ca7:465-468), CREASTMT→TXT2PDF1 (:494-495), TXT2PDF1→WAITSTEP (:521-522), WAITSTEP→OPENFIL (:524-527). Within CREASTMT, STEP020, STEP030 and STEP040 carry COND=(0,NE) and are bypassed as soon as any earlier step ends with RC ≠ 0 (CREASTMT.JCL:56, 66, 79); DELDEF01 and STEP010 have no COND. TXT2PDF1's single step also carries COND=(0,NE) (TXT2PDF1.JCL:26), which is vacuous because it is the first step of its job. CA-7 triggers on job completion and the listing does not show a "good completion" RC requirement, so whether a non-zero CREASTMT releases TXT2PDF1 is not determinable from the repo (Q-05). Estate gotcha: the two scheduler sources disagree — CA-7's SCHID=030 networks (CardDemo.ca7) and Control-M's folders (CardDemo.controlm) describe different daily chains (CA-7: CLOSEFIL→CBPAUP0J→POSTTRAN→WAITSTEP→OPENFIL, :18-147; Control-M DAILY-TransactionBackup: CLOSEFIL→TRANBKP→WAITSTEP→OPENFIL, CardDemo.controlm:3-25). The StatementGeneration chain exists only in CA-7; CardDemo.controlm has no CREASTMT or TXT2PDF1 job, so no INCOND/OUTCOND ordering is defined for it (Q-01, Q-02). The dotted edge is the abbreviated OPENFIL block at CardDemo.ca7:529-532, which lists CLOSEFIL under SCHID=031 (the PRTCATBL network) whereas the full OPENFIL block says N -- COMP TRIGGERS OTHER JOBS (:138) (Q-04).

5. Functional requirements

IDRequirementSourceAcceptance criteria
FR-01Before each run the card-keyed work store is rebuilt from scratch: TRXFL.SEQ and the TRXFL.VSAM.KSDS cluster are deleted, the condition code is reset (SET MAXCC = 0) so a first run with nothing to delete still succeeds, and the KSDS is redefined with a 32-byte key at offset 0 and fixed 350-byte records.app/jcl/CREASTMT.JCL:22-39Running the job twice in succession, or on an estate where the work store does not exist, ends DELDEF01 with RC 0 and leaves a work store whose only content is the current TRANSACT data.
FR-02The work copy is TRANSACT sorted by card number ascending then transaction id ascending, with each record re-laid out as COSTM01: card number (TRANSACT bytes 263-278) at 1-16, TRANSACT bytes 1-262 (tran id … merchant zip) at 17-278, TRANSACT bytes 279-328 at 279-328.app/jcl/CREASTMT.JCL:53-54; app/cpy/CVTRA05Y.cpy:4-18; app/cpy/COSTM01.CPY:20-36For every TRANSACT record there is exactly one work record whose key is TRAN-CARD-NUM + TRAN-ID and whose bytes 17-278 equal the source bytes 1-262; records are ordered by (card, tran id).
FR-03Legacy quirk, reproduced: the third OUTREC field copies 50 bytes from position 279 although ORIG-TS + PROC-TS are 52 bytes, so TRNX-PROC-TS holds only the first 24 characters of TRAN-PROC-TS and work-record bytes 329-350 are blank. CBSTM03A never reads the timestamps, so no statement output depends on them.app/jcl/CREASTMT.JCL:54; app/cpy/CVTRA05Y.cpy:16-18; app/cpy/COSTM01.CPY:34-36Given a TRANSACT record with a 26-character PROC-TS, the work record's PROC-TS field contains its first 24 characters followed by blanks, and the statement output is identical whether or not the timestamp fields are populated.
FR-04STEP020 loads every TRXFL.SEQ record into the keyed work store with IDCAMS REPRO; STEP020, STEP030 and STEP040 each carry COND=(0,NE), so the first non-zero step return code stops all later steps.app/jcl/CREASTMT.JCL:56-62, 66, 79Record count of the KSDS equals the sequential file's. Forcing STEP010 to end non-zero results in STEP020/030/040 being flushed (not executed) and the job ending non-zero.
FR-05STEP030 deletes the previous run's STATEMNT.HTML and STATEMNT.PS with DISP=(MOD,DELETE,DELETE) and succeeds whether or not they exist.app/jcl/CREASTMT.JCL:66-75After STEP030 neither dataset is cataloged; STEP030 ends RC 0 on a first run and on a rerun.
FR-06STEP040 writes two new outputs per run: the text statement as fixed 80-byte records (STMTFILE, FB 80/8000) and the HTML statement as fixed 100-byte records (HTMLFILE, FB 100/800); both are opened OUTPUT once at program start and closed once at the end.app/jcl/CREASTMT.JCL:87-96; app/cbl/CBSTM03A.CBL:39-47, 293, 339Every record of STATEMNT.PS is exactly 80 bytes and every record of STATEMNT.HTML exactly 100 bytes (blank-padded, truncated at the record length); the files contain only the current run's statements.
FR-07The four VSAM inputs are opened INPUT through CBSTM03B in the order TRNXFILE, XREFFILE, CUSTFILE, ACCTFILE: TRNXFILE and XREFFILE with sequential access, CUSTFILE and ACCTFILE with random (keyed) access. An OPEN status other than 00 or 04 displays ERROR OPENING <DD> and RETURN CODE: <status> and abends.app/cbl/CBSTM03A.CBL:296-314, 730-742, 765-777, 783-795, 801-813; app/cbl/CBSTM03B.CBL:31-53, 135-138, 159-162, 183-186, 208-211Removing any one of the four DDs (status 35) produces the two DISPLAY lines for that DD followed by ABENDING PROGRAM and a step abend; no statement output is written.
FR-08Legacy quirk, reproduced: immediately after opening TRNXFILE a priming sequential read is issued and only status 00/04 is accepted; an empty work store (status 10) is therefore an error (ERROR READING TRNXFILE / RETURN CODE: 10) and abends rather than producing statements with no transactions.app/cbl/CBSTM03A.CBL:744-761Running with an empty TRANSACT (hence empty TRXFL) ends STEP040 with an abend and the displayed return code 10; no statement file content is produced.
FR-09The whole work store is loaded into memory before any statement is written: consecutive records with the same card number are grouped, counting transactions per card (WS-TRCT), into a table of 51 cards × 10 transactions × (16 + 318 bytes); end of file (status 10) stops loading, any other status abends. Legacy quirk: there is no bounds check, so more than 51 cards or more than 10 transactions for one card overruns the table (undefined behaviour).app/cbl/CBSTM03A.CBL:225-233, 818-853For input within the limits, the table holds every (card, tran) pair with the per-card counts equal to the number of work records for that card. The migrated system must document and test its chosen behaviour at >51 cards or >10 transactions per card (see Q-10); it must not silently corrupt other cards' data.
FR-10One statement is produced per CARDXREF record, in ascending card-number order (sequential read of the KSDS). XREF read status 10 ends the run normally; any status other than 00/10 displays ERROR READING XREFFILE and abends.app/cbl/CBSTM03A.CBL:316-329, 345-366; app/cbl/CBSTM03B.CBL:37-41, 164-168Number of START OF STATEMENT lines in STATEMNT.PS equals the number of CARDXREF records; statements appear in card-number order; a CARDXREF with N records yields N statements and RC 0.
FR-11For each CARDXREF record the customer is read by key XREF-CUST-ID (9 bytes) and the account by key XREF-ACCT-ID (11 bytes). Any status other than 00 (e.g. 23 not found) displays ERROR READING CUSTFILE / ERROR READING ACCTFILE and abends — there is no skip-and-continue.app/cbl/CBSTM03A.CBL:368-414; app/cbl/CBSTM03B.CBL:188-193, 213-218A CARDXREF row pointing at a non-existent customer or account abends STEP040 with the corresponding DISPLAY lines and RETURN CODE: 23; statements for earlier cards already written remain in the (uncataloged, DISP DELETE) output.
FR-12The statement's transactions are those table entries whose card number equals the CARDXREF card, scanned from the first table entry until the entry's card number exceeds the CARDXREF card; each is written in table (transaction-id) order and its TRNX-AMT is added to a per-statement total WS-TOTAL-AMT (S9(9)V99) that is reset to zero for every statement. A card with no transactions still gets a complete statement with a zero total; work records whose card has no CARDXREF row are never reported.app/cbl/CBSTM03A.CBL:65, 324-326, 416-434Given card A with transactions 10.00 and -2.50 and card B with none: A's statement lists both lines and Total EXP: ... $ 7.50 ; B's statement has no detail line and total $ .00 . A work record for a card absent from CARDXREF appears on no statement. Legacy quirk: totals above 999,999,999.99 lose high-order digits (no diagnostic).
FR-13Text statement structure: lines are written in the order L0, L1, L2, L3, L4, L5, L6, L5, L7, L8, L9, L10, L11, L12, L13, L12, one L14 per transaction, L12, L14A, L15. Fixed lines: L0 = 31 * + START OF STATEMENT + 31 *; L5/L10/L12 = 80 -; L6 = 33 blanks + Basic Details + 34 blanks; L11 = 30 blanks + TRANSACTION SUMMARY + 30 blanks; L13 = Tran ID padded to 16 + Tran Details padded to 51 + Tran Amount; L15 = 32 * + END OF STATEMENT + 32 *.app/cbl/CBSTM03A.CBL:85-146, 435-437, 458-504, 679Byte-for-byte comparison of STATEMNT.PS against a golden file produced from a known fixture matches, including the duplicated L5 and L12 separator lines and the position of every fixed literal.
FR-14Name and address composition: L1 = first name, blank, middle name, blank, last name, blank — each component cut at its first embedded blank (STRING ... DELIMITED BY ' ') — in X(75) + 5 blanks. L2/L3 = address line 1/2 in X(50) + 30 blanks. L4 = address line 3, state code, country code, zip, each cut at its first blank and separated by single blanks, in X(80).app/cbl/CBSTM03A.CBL:90-100, 462-481; app/cpy/CUSTREC.cpy:6-14Customer Mary Ann/Lee/Smith renders L1 as Mary Lee Smith padded to 80 (the second word of a multi-word first name is dropped); L4 for line3 Apt 4, state WA, country USA, zip 98101 is Apt WA USA 98101 padded to 80.
FR-15Basic-details lines: L7 = Account ID : + the 11-digit account id left-justified in X(20) + 40 blanks; L8 = Current Balance : + ACCT-CURR-BAL edited as 9(9).99- (zero-padded 9 integer digits, decimal point, 2 decimals, - or blank) + 47 blanks; L9 = FICO Score : + the 3-digit score left-justified in X(20) + 40 blanks. 6.3 Restart / checkpoint semantics

There are no checkpoints, commits or restart keys anywhere in the chain. CREASTMT is a pure rebuild: DELDEF01 deletes and redefines the work store (CREASTMT.JCL:22-39), STEP010/STEP020 recreate it in full (:44-62), STEP030 deletes the previous outputs (:66-75) and STEP040 creates them anew with DISP=(NEW,CATLG,DELETE), so an abend leaves no partial statement files (:87-96). The only valid restart point is therefore the top of CREASTMT (cold rerun); restarting inside the job at STEP040 requires STEP030 to be rerun first (section 6.2). CBSTM03A holds the entire transaction set in working storage and writes statements only after it is loaded (CBSTM03A.CBL:730-761, 818-853, 316-329), so there is no in-flight state to recover. All four VSAM inputs are read-only (OPEN INPUT, CBSTM03B.CBL:136, 160, 184, 209); no backout job exists or is needed. CLOSEFIL, WAITSTEP and OPENFIL are stateless and idempotent. Rerun protection: the repo defines no "already run today" guard; a second run on the same day simply regenerates the same statements. In the target, rerun identity is carried by the job parameters (business run date), per docs/migration/CardDemo_target_state.md:98.
