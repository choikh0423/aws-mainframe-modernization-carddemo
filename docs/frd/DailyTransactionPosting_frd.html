1. Business purpose

DailyTransactionPosting is the CARDDEMO daily batch cycle that turns the day’s captured card transactions into posted history and updated balances. The CICS files are first taken offline (CLOSEFIL, app/jcl/CLOSEFIL.jcl:22-30) so batch holds them exclusively; expired pending authorisations are purged from the IMS DBPAUTP0 database (CBPAUP0J → CBPAUP0C, app/app-authorization-ims-db2-mq/jcl/CBPAUP0J.jcl:24-25); POSTTRAN runs CBTRN02C (app/jcl/POSTTRAN.jcl:23), which reads the sequential daily transaction file DALYTRAN, validates each record against the card cross-reference and account master, writes accepted records to the transaction master TRANSACT, rolls the amounts into the account master and the per-account transaction-category balances, and writes rejected records with a reason trailer to a new DALYREJS generation (app/cbl/CBTRN02C.cbl:193-234). WAITSTEP pauses 36 seconds (app/jcl/WAITSTEP.jcl:26) before OPENFIL gives the files back to CICS (app/jcl/OPENFIL.jcl:22-30).

If the chain does not run, no daily transactions are posted: online transaction enquiry (CT00/CT01) shows stale history, account current balances and cycle credit/debit totals are not updated (so authorisation and interest/statement cycles work from wrong figures), expired authorisations keep consuming the pending-authorisation database, and — if CLOSEFIL ran but OPENFIL did not — the five CICS files stay closed and every online function that touches them fails.

Business capabilityHow this stream serves it
Transaction postingEach valid DALYTRAN record becomes a TRANSACT record with a processing timestamp (CBTRN02C.cbl:424-444).
Account balance maintenanceACCT-CURR-BAL, ACCT-CURR-CYC-CREDIT / -DEBIT updated per posted transaction (CBTRN02C.cbl:545-560).
Spend-category reportingTCATBALF balance created or incremented per (account, type, category) (CBTRN02C.cbl:467-542); consumed by INTCALC and TRANREPT streams.
Exception handlingInvalid-card, missing-account, over-limit and post-expiry transactions are written to DALYREJS(+1) with a 4-digit reason and text (CBTRN02C.cbl:380-420, 446-465).
Authorisation hygienePending authorisations older than the expiry window are deleted from IMS and the account summary counts/amounts reduced (CBPAUP0C.cbl:277-348).
Online availabilityCICS files TRANSACT, CCXREF, ACCTDAT, CXACAIX, USRSEC closed before and reopened after batch (CLOSEFIL.jcl:26-30, OPENFIL.jcl:26-30).

Gating conditions: CA-7 releases each successor purely on completion of its predecessor via TRIGGERED JOBS ... SCHID=030 QTM=0100 LEADTM=0000 (CardDemo.ca7:43, 70, 97, 124); no job in the chain lists a requirement, calendar or condition-code test, and OPENFIL has no TRIGGERED JOBS block (CardDemo.ca7:126-158), so it ends the network. None of the five JCL members carries a COND= parameter (CLOSEFIL.jcl, CBPAUP0J.jcl, POSTTRAN.jcl, WAITSTEP.jcl, OPENFIL.jcl), and each has a single step, so a non-zero step RC does not by itself stop the chain — POSTTRAN ending RC 4 (rejects present, CBTRN02C.cbl:229-231) still triggers WAITSTEP. Whether CA-7 treats CBPAUP0C’s RC 16 (CBPAUP0C.cbl:382) or a CBTRN02C U0999 abend (CBTRN02C.cbl:707-711) as a failed completion that withholds the trigger is not stated in the LJOB listing (Q-05). Estate gotcha: the two scheduler sources disagree — CA-7 SCHID=030 is CLOSEFIL → CBPAUP0J → POSTTRAN → WAITSTEP → OPENFIL (no TRANBKP), while Control-M DAILY-TransactionBackup is CLOSEFIL → TRANBKP → WAITSTEP → OPENFIL (no POSTTRAN, no CBPAUP0J; CardDemo.controlm:4-24, RUN_AS="xuemingh", DAYS="ALL", TIMETO="23:00", MAXRERUN="5"). This document does not assert a single combined daily chain (Q-01).

5. Functional requirements

IDRequirementSourceAcceptance criteria
FR-01Before any batch update, CLOSEFIL closes exactly the CICS files TRANSACT, CCXREF, ACCTDAT, CXACAIX and USRSEC in region CICSAWSA with CEMT SET FIL(x) CLO; no other file is touched.app/jcl/CLOSEFIL.jcl:22-30In the target, the equivalent “online quiesce” (or its documented absence) is applied to the data behind those five files only; a run log shows the five close actions in that order.
FR-02OPENFIL is the last job of the network and reopens the same five files with CEMT SET FIL(x) OPE; it is released only after WAITSTEP completes.app/jcl/OPENFIL.jcl:22-30; app/scheduler/CardDemo.ca7:124, 126-158After the chain, the five files are available online; OPENFIL never runs before WAITSTEP has completed; no job is triggered after OPENFIL.
FR-03CBPAUP0J executes CBPAUP0C as an IMS BMP under DFSRRC00 with PSB PSBPAUTB (DB PCB PROCOPT=AP over PAUTSUM0/PAUTDTL1), using the second PCB.app/app-authorization-ims-db2-mq/jcl/CBPAUP0J.jcl:24-25; ims/PSBPAUTB.psb:17-20; cbl/CBPAUP0C.cbl:80-82Target job named CBPAUP0J runs the purge against the pending-authorisation summary/detail store with read + delete access only (no insert/replace).
FR-04CBPAUP0C reads one SYSIN control card ee,fffff,ddddd,x: expiry days (2 digits, default 5 if non-numeric), checkpoint frequency (default 5 if blank/0), checkpoint display frequency (default 10 if blank/0), debug flag (anything but Y → N). Shipped card is 00,00001,00001,Y, i.e. expiry 0 days.CBPAUP0C.cbl:98-108, 189, 196-208; CBPAUP0J.jcl:37Given card 00,00001,00001,Y the run uses expiry=0, chkp-freq=1, display-freq=1, debug on and logs CBPAUP0C PARM RECEIVED :00,00001,00001,Y; given a blank card it uses 5/5/10/N.
FR-05For every summary (GN PAUTSUM0) and each of its details (GNP PAUTDTL1), a detail is expired when today(YYDDD) − (99999 − PA-AUTH-DATE-9C) ≥ expiry days. An expired detail is deleted (DLET) and the parent summary is adjusted in memory: resp code ‘00’ → approved count −1 and approved amount − PA-APPROVED-AMT; otherwise declined count −1 and declined amount − PA-TRANSACTION-AMT.CBPAUP0C.cbl:223-226, 255-258, 280-293, 310-312Fixture with details dated today, today−4, today−5 and expiry=5: only the today−5 detail is deleted; the summary’s approved/declined counters and amounts decrease by exactly that detail’s values. Dates are compared on 9’s-complement YYDDD, not calendar dates (year boundary is not handled; see Q-09).
FR-06After its details are processed, a summary is deleted when PA-APPROVED-AUTH-CNT ≤ 0. The declined count is not tested (the source repeats the approved-count condition twice), and the adjusted summary is never rewritten (REPL) when it is kept. Quirk, preserved unless Q-10 is resolved.CBPAUP0C.cbl:156-158, 335-337A summary with approved count 0 and declined count 3 is deleted together with its remaining declined details; a summary with approved count 1 is kept with its stored counters unchanged on disk.
FR-07CBPAUP0C takes an IMS checkpoint (CHKP, id RMAD0000) after every P-CHKP-FREQ summaries and once more at end of run; the checkpoint id counter is never incremented and no XRST is issued.CBPAUP0C.cbl:75-77, 160-163, 169, 355With chkp-freq=1 a run over N summaries commits N+1 times; a restart begins from the first summary (deletions already committed are not undone).
FR-08Any DL/I status other than blank (or GB at end of database on GN, GE/GB at end of parent on GNP) makes CBPAUP0C display the failing call and status, set RETURN-CODE 16 and GOBACK; on success it prints four totals: summaries read, summaries deleted, details read, details deleted.CBPAUP0C.cbl:234-240, 261-270, 316-320, 341-345, 364-369, 173-176, 380-383A forced DLET failure ends the job RC 16 with CBPAUP0C ABENDING ...; a clean run ends RC 0 and the four counters equal the fixture outcome.
FR-09CBTRN02C opens its six files in this mode and order: DALYTRAN INPUT (sequential), TRANFILE OUTPUT (indexed, random by TRAN-ID), XREFFILE INPUT, DALYREJS OUTPUT, ACCTFILE I-O, TCATBALF I-O. Because TRANFILE is OUTPUT, posting loads the transaction master from empty rather than appending. Any non-‘00’ open status abends the step.CBTRN02C.cbl:29-61, 195-200, 238, 256, 275, 293, 311, 329Running POSTTRAN against a non-empty transaction master leaves only this run’s transactions; an unavailable input ends with ERROR OPENING ..., FILE STATUS IS: NNNN and user abend U0999.
FR-10Daily transactions are processed in file order in a single pass; status ‘10’ ends the loop, any other non-‘00’ read status abends. Each record increments TRANSACTIONS PROCESSED and is either posted (reason 0) or written to rejects (reason ≠ 0); the reason is reset to 0 before each record.CBTRN02C.cbl:202-219, 345-369For an input of N records, PROCESSED = N and POSTED + REJECTED = N; an empty file yields counts 0 and RC 0.
FR-11A transaction whose DALYTRAN-CARD-NUM has no CARDXREF record is rejected with reason 0100, text INVALID CARD NUMBER FOUND; the account lookup and all later checks are skipped.CBTRN02C.cbl:370-392Unknown card → one reject line with trailer 0100INVALID CARD NUMBER FOUND; no ACCT/TCATBAL change.
FR-12The account is located by XREF-ACCT-ID from the cross-reference (never from the transaction). A missing account is rejected with reason 0101, text ACCOUNT RECORD NOT FOUND.CBTRN02C.cbl:393-399Card present in XREF but its account absent → trailer 0101ACCOUNT RECORD NOT FOUND.
FR-13Over-limit rule: compute ACCT-CURR-CYC-CREDIT − ACCT-CURR-CYC-DEBIT + DALYTRAN-AMT; if ACCT-CREDIT-LIMIT is less than that value reject with 0102 OVERLIMIT TRANSACTION. Equality is accepted. ACCT-CURR-BAL is not used in the test.CBTRN02C.cbl:403-413Limit 1000.00, cycle credit 900.00, cycle debit 0, amount 100.00 → accepted; amount 100.01 → rejected 0102.
FR-14Expiry rule: if ACCT-EXPIRAION-DATE (10 chars) is alphanumerically less than the first 10 characters of DALYTRAN-ORIG-TS, reject with 0103 TRANSACTION RECEIVED AFTER ACCT EXPIRATION. The check runs even after an over-limit failure and overwrites reason 0102 with 0103 (quirk, preserved).CBTRN02C.cbl:414-420Expiry 2025-12-31, orig TS 2025-12-31-23.59.59.000000 → accepted; orig TS 2026-01-01-... → 0103. A transaction both over-limit and post-expiry reports 0103 only.
FR-15A rejected transaction has no side effects and produces exactly one 430-byte reject record: the unmodified 350-byte DALYTRAN image followed by an 80-byte trailer = 4-digit zero-padded reason + 76-char space-padded description. The reject file is a new GDG generation, RECFM=F LRECL=430.CBTRN02C.cbl:176-182, 211-216, 446-465; app/jcl/POSTTRAN.jcl:34-38Byte compare of reject record positions 1-350 with the input record is identical; positions 351-354 = reason; 355-430 = description padded. Account and category balances for the rejected card are unchanged.
FR-16A posted transaction copies TRAN-ID, TYPE-CD, CAT-CD, SOURCE, DESC, AMT, MERCHANT-ID/NAME/CITY/ZIP, CARD-NUM and ORIG-TS from the daily record unchanged; TRAN-PROC-TS is set to the current time formatted YYYY-MM-DD-HH.MM.SS.hh0000 (26 chars). The daily record’s own PROC-TS is discarded.CBTRN02C.cbl:425-438, 692-705Posted record fields 1-304 equal input fields 1-304; field 305-330 matches ^\d{4}-\d{2}-\d{2}-\d{2}\.\d{2}\.\d{2}\.\d{2}0000$ and is within the run window.
FR-17Category balance: key = (XREF-ACCT-ID, DALYTRAN-TYPE-CD, DALYTRAN-CAT-CD). If no TCATBALF record exists (status 23) one is created with balance = amount and the message TCATBAL record not found for key : <17-byte key>.. Creating. is logged; otherwise the amount is added and the record rewritten. 6.3 Restart / checkpoint semantics

POSTTRAN / CBTRN02C has no checkpoint, commit interval or restart key: it is a single VSAM load pass (CBTRN02C.cbl:202-219). TRANFILE is OPEN OUTPUT (:256), so a cold rerun reloads the transaction master from empty, and the JCL’s DALYREJS(+1) DISP=(NEW,CATLG,DELETE) (POSTTRAN.jcl:34) gives a fresh reject generation. However ACCTFILE REWRITEs (:554) and TCATBALF WRITE/REWRITEs (:510, :528) are applied in place and are not reversed on abend, so a rerun after a partial run double-counts every transaction that was posted before the failure. No backout job exists in app/jcl for ACCTDATA or TCATBALF (Q-12). Legacy procedure is therefore: restore ACCTDATA/TCATBALF, ensure TRANSACT is empty (TRANBKP), rerun POSTTRAN from the top.

CBPAUP0J / CBPAUP0C takes EXEC DLI CHKP ID(WK-CHKPT-ID) after every P-CHKP-FREQ summaries and at end of run (CBPAUP0C.cbl:160-163, 169, 355), with a constant id RMAD0000 (:75-77) and no XRST; a restart therefore reprocesses from the first summary, which is harmless because already-deleted segments are not re-read.

CLOSEFIL, WAITSTEP, OPENFIL are stateless and may be rerun at will. If the chain fails between CLOSEFIL and OPENFIL, OPENFIL must be run manually to restore online service.
