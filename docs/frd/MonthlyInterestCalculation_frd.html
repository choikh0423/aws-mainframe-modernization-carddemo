1. Business purpose

The MonthlyInterestCalculation chain is CardDemo's month-end interest run. Once the CICS region has released the shared VSAM files (CLOSEFIL), INTCALC runs CBACT04C, which browses every transaction-category balance (TCATBALF) in account order, looks up the account's disclosure group and the matching interest rate (DISCGRP, falling back to the DEFAULT group), computes balance × rate ÷ 1200 per category, writes one System-sourced interest transaction per priced category to a new SYSTRAN generation, and adds the account's total interest to its current balance while zeroing the current-cycle credit/debit totals. COMBTRAN then sorts the interest transactions together with the latest transaction-master backup by transaction id and loads the combined file back into the TRANSACT KSDS. WAITSTEP gives the catalog/VSAM activity time to settle and OPENFIL hands the files back to CICS.

If the chain does not run, cardholder accounts carry no interest charge for the month, the cycle credit/debit accumulators are not reset for the next cycle, and the interest transactions that the statement job (CREASTMT) and the online transaction screens read from TRANSACT are missing. If it runs twice, interest is charged twice (there is no "already posted" check — see FR-15, Q-06).

Business capabilityHow this stream serves it
Revolving-credit interest billingPrices each account's category balances with the disclosure-group rate and posts the total to the account balance (app/cbl/CBACT04C.cbl:462-470, 350-356).
Transaction history / statementsEach interest amount becomes a CVTRA05Y transaction (type 01, category 05, source System) merged into the TRANSACT master that CREASTMT and the CT00/CT01 screens read (CBACT04C.cbl:482-500; app/jcl/COMBTRAN.jcl:22-48).
Billing-cycle resetSets ACCT-CURR-CYC-CREDIT and ACCT-CURR-CYC-DEBIT to zero at each account change (CBACT04C.cbl:353-354).
Pricing governanceRates are external data (DISCGRP keyed by account group, transaction type and category) with a mandatory DEFAULT group, so products can be re-priced without a code change (CBACT04C.cbl:415-460; app/cpy/CVTRA02Y.cpy:5-9).
Online availabilityCICS files are closed before and reopened after the batch update so the batch programs get exclusive VSAM access (app/jcl/CLOSEFIL.jcl:26-30, app/jcl/OPENFIL.jcl:26-30).

Gating conditions: The chain is defined only in Control-M (app/scheduler/CardDemo.controlm:64-92). Each job's single INCOND is the predecessor's OUTCOND for the same ODATE (AND_OR="A"), and each job deletes the condition it consumed (SIGN="-") and adds its own (SIGN="+"): CLOSEFIL→INTCALC (:66,70-72), INTCALC→COMBTRAN (:76-78), COMBTRAN→WAITSTEP (:82-84), WAITSTEP→OPENFIL (:88-89). OPENFIL emits no OUTCOND, so the network ends there. Control-M only posts an OUTCOND when the job ends OK, so a failed INTCALC (user abend U0999, FR-20) or a COMBTRAN step RC > 0 holds the chain; there is no explicit MAXRC/ON-DO statement in the XML. Inside the JCL there are no COND= parameters on any step (app/jcl/INTCALC.jcl:22, app/jcl/COMBTRAN.jcl:22,41), so in COMBTRAN the IDCAMS STEP10 runs even when the SORT step ends with a non-zero RC (only an abend would skip it). Rerun policy: MAXRERUN="5", MAXWAIT="7" days, latest submission TIMETO="23:00" on every job (:65,69,75,81,87). Estate gotcha: CA-7 (app/scheduler/CardDemo.ca7) does not know INTCALC or COMBTRAN at all; it only lists CLOSEFIL, WAITSTEP and OPENFIL as members of other networks (SCHID 030 posting network CLOSEFIL→CBPAUP0J→POSTTRAN→WAITSTEP→OPENFIL). The two schedulers also disagree on the daily chain (Control-M DAILY-TransactionBackup runs TRANBKP, CA-7 SCHID 030 runs POSTTRAN); this document does not assert a combined daily chain. The dashed TRANBKP node is shown because COMBTRAN's SORTIN depends on its output, not because the folder schedules it.

5. Functional requirements

IDRequirementSourceAcceptance criteria
FR-01Before any batch update the five CICS files TRANSACT, CCXREF, ACCTDAT, CXACAIX and USRSEC are closed in region CICSAWSA, and after the chain they are reopened; INTCALC is released only after the close completes and OPENFIL only after WAITSTEP.app/jcl/CLOSEFIL.jcl:26-30; app/jcl/OPENFIL.jcl:26-30; app/scheduler/CardDemo.controlm:66-70,88-89During the INTCALC/COMBTRAN window the online screens that use those files are unavailable (or, in the target, the equivalent exclusive-access guarantee is documented as not needed); after the chain all five files are open/enabled again.
FR-02INTCALC is a single step STEP15 running CBACT04C with a 10-character run-date PARM ('2022071800' in the JCL). The PARM is not parsed or validated as a date and is used only as the prefix of generated transaction ids.app/jcl/INTCALC.jcl:22; app/cbl/CBACT04C.cbl:176-178,476-480Running with PARM 2022071800 yields transaction ids 2022071800000001, 2022071800000002, …; a run with a non-10-character parameter is rejected or documented as undefined.
FR-03File open modes: TCATBALF, XREFFILE and DISCGRP are opened INPUT, ACCTFILE is opened I-O, TRANSACT (SYSTRAN) is opened OUTPUT. Any open status other than 00 abends the program before any record is processed.app/cbl/CBACT04C.cbl:236,254,272,291,309; :237-248With a missing/unavailable input dataset the job ends with the user abend (FR-20), logs ERROR OPENING … plus FILE STATUS IS: NNNN, and no SYSTRAN record or account change is produced.
FR-04Balances are processed in TCATBALF key order (account id, transaction type code, transaction category code) by sequential read; read status 10 ends the run normally, any other non-00 status abends.app/cbl/CBACT04C.cbl:28-32,63-66,325-348Given balances for accounts 00000000011 and 00000000010, account 10's transactions are generated before account 11's; an I/O error on TCATBALF produces ERROR READING TRANSACTION CATEGORY FILE and the abend.
FR-05On each change of account id the account record (by ACCT-ID) and the card cross-reference record (by alternate key XREF-ACCT-ID) are read once and reused for all that account's categories; the per-account interest total is reset to zero.app/cbl/CBACT04C.cbl:194-205,372-376,393-398An account with three category balances causes exactly one ACCTFILE read and one XREFFILE read; all three generated transactions carry the same TRAN-CARD-NUM.
FR-06The interest rate for a balance is the DISCGRP record keyed by (ACCT-GROUP-ID, balance type code, balance category code).app/cbl/CBACT04C.cbl:210-213,415-420; app/cpy/CVTRA02Y.cpy:5-9Account group GOLD, type 01, category 0001 uses the rate stored under key GOLD 010001 and not the DEFAULT rate when that row exists.
FR-07If the group-specific DISCGRP record is missing (status 23), the lookup is retried once with group id DEFAULT and the same type/category, logging DISCLOSURE GROUP RECORD MISSING and TRY WITH DEFAULT GROUP CODE. If the DEFAULT record is also missing the run abends with ERROR READING DEFAULT DISCLOSURE GROUP.app/cbl/CBACT04C.cbl:416-439,443-460Remove the GOLD 01 0001 rate: interest uses the DEFAULT 01 0001 rate. Remove both: the job abends and no account is partially updated after that point.
FR-08A rate of zero produces no interest transaction and does not change the account total; fees are never computed (1400-COMPUTE-FEES is a stub).app/cbl/CBACT04C.cbl:214-217,518-520A balance whose resolved rate is 0.00 yields no SYSTRAN record; the migrated job produces no fee transactions of any kind.
FR-09Monthly interest per category = TRAN-CAT-BAL × DIS-INT-RATE ÷ 1200, stored in PIC S9(09)V99 without ROUNDED, i.e. truncated toward zero to two decimals; a non-zero rate on a zero balance still writes a 0.00 transaction.app/cbl/CBACT04C.cbl:168,214,462-468Balance 1000.00 at rate 18.50 ⇒ 15.41 (not 15.42); balance -1000.00 at 18.50 ⇒ -15.41; balance 0.00 at 18.50 ⇒ one transaction with amount 0.00.
FR-10The account's total interest is the sum of the already-truncated per-category amounts.app/cbl/CBACT04C.cbl:467Three categories each computing 0.333… produce three 0.33 transactions and a balance increase of 0.99, not 1.00.
FR-11Each computed interest amount produces one CVTRA05Y transaction: TRAN-ID = run-date PARM + 6-digit sequence (starting 000001, incremented once per transaction across the whole run), type 01, category 05, source System, description Int. for a/c + 11-digit account id, amount = the truncated interest, merchant id 0, merchant name/city/zip spaces, card number = the account's XREF card number.app/cbl/CBACT04C.cbl:173,473-495; app/cpy/CVTRA05Y.cpy:5-15The second generated transaction of the run (whatever its account) has id <PARM>000002; a record for account 00000000010 has TRAN-DESC starting Int. for a/c 00000000010.
FR-12Both TRAN-ORIG-TS and TRAN-PROC-TS are set to the same current-clock timestamp in DB2 format YYYY-MM-DD-HH.MM.SS.hh0000 (26 characters).app/cbl/CBACT04C.cbl:496-498,613-626Generated records have 26-character timestamps matching ^\d{4}-\d{2}-\d{2}-\d{2}\.\d{2}\.\d{2}\.\d{2}0000$ and ORIG = PROC.
FR-13Interest transactions are written to the sequential TRANSACT DD of INTCALC, i.e. a new SYSTRAN(+1) GDG generation, fixed 350-byte records, in generation order; INTCALC never writes the TRANSACT master. A write status other than 00 abends.app/jcl/INTCALC.jcl:37-41; app/cbl/CBACT04C.cbl:53-56,500-513After INTCALC the master KSDS record count is unchanged; the new SYSTRAN generation contains exactly the number of priced categories, LRECL 350.
FR-14When the account id changes (and it is not the first account), the previous account is updated: ACCT-CURR-BAL += total interest, ACCT-CURR-CYC-CREDIT = 0, ACCT-CURR-CYC-DEBIT = 0, via REWRITE; a non-00 rewrite status abends.app/cbl/CBACT04C.cbl:194-199,350-369Account with balance 500.00, cycle credit 120.00, cycle debit 80.00 and total interest 7.70 reads back as 507.70 / 0.00 / 0.00 once the next account is reached.
FR-15Preserved quirk: the last account in TCATBALF key order is never updated (its transactions are still generated) because the end-of-file update branch at :219-220 is unreachable — the inner IF END-OF-FILE = 'N' is always true when evaluated. Also, nothing marks a balance as "already charged", so a rerun charges interest again.app/cbl/CBACT04C.cbl:188-191,219-221Parity test: with two accounts, only the first has its balance/cycle totals changed; the second has SYSTRAN records but an unchanged ACCTDATA record. Running INTCALC twice doubles the balance increase of the first account. (Whether to keep this in the target is Q-06.)
FR-16A missing account record or missing XREF record for a balance abends the run after logging ACCOUNT NOT FOUND: + id and ERROR READING ACCOUNT FILE / ERROR READING XREF FILE. There is no reject file and no skip.app/cbl/CBACT04C.cbl:372-390,393-412A TCATBALF row for an account absent from ACCTDATA stops the job; earlier accounts already REWRITTEN stay updated (no backout).
FR-17COMBTRAN STEP05R sorts the concatenation of TRANSACT.BKUP(0) followed by SYSTRAN(0) ascending on the 16-byte character field at position 1 (TRAN-ID) into a new TRANSACT.COMBINED(+1) generation with the SORTIN DCB; duplicates are kept (SORT, not merge/SUM).app/jcl/COMBTRAN.jcl:22-37Output record count = BKUP count + SYSTRAN count; records are in ascending TRAN-ID order; LRECL 350.
FR-18COMBTRAN STEP10 loads every record of TRANSACT.COMBINED(+1) into the TRANSACT KSDS with REPRO INFILE(TRANSACT) OUTFILE(TRANVSAM); no REPLACE, no COND=, so the load runs even if the sort step ended non-zero.app/jcl/COMBTRAN.jcl:41-48Starting from an empty master, after STEP10 the master contains exactly the COMBINED records keyed by TRAN-ID. Loading into a master that already holds a key is reported as a duplicate-record error (see Q-05 for the required target behaviour).
FR-19GDG handling: INTCALC allocates SYSTRAN(+1) with DISP=(NEW,CATLG,DELETE); COMBTRAN reads it as (0) in the next job and allocates COMBINED(+1). Bases are LIMIT(5) SCRATCH, so the sixth generation rolls the oldest off.app/jcl/INTCALC.jcl:37-41; app/jcl/COMBTRAN.jcl:24-26,33-37; app/jcl/DEFGDGB.jcl:24-58A failed INTCALC leaves no new SYSTRAN generation (DELETE on abnormal end); a COMBTRAN rerun after a successful INTCALC reads the same SYSTRAN generation; only five SYSTRAN/COMBINED generations are retained.
FR-20Every detected error in CBACT04C ends in 9999-ABEND-PROGRAM: it logs ABENDING PROGRAM, the file status as FILE STATUS IS: NNNN, and calls CEE3ABD with code 999 and TIMING 0 (user abend U0999, no dump). Normal completion logs END OF EXECUTION OF PROGRAM CBACT04C and returns RC 0; there are no RC 4/8 paths.app/cbl/CBACT04C.cbl:181,230-232,628-648The migrated job exits 0 on success and a non-zero failure code (12 in BatchJobLauncher) on any of the error paths above; the log carries the start/end banners.
FR-21WAITSTEP pauses for the SYSIN value in centiseconds (00003600 = 36 s) between COMBTRAN and OPENFIL, with no other side effect.app/jcl/WAITSTEP.jcl:22-26; app/cbl/COBSWAIT.cbl:36-38Elapsed time between COMBTRAN end and OPENFIL start ≥ 36 s; a non-numeric card fails the step.
FR-22Ordering: INTCALC runs only after CLOSEFIL, COMBTRAN only after INTCALC, WAITSTEP only after COMBTRAN, OPENFIL only after WAITSTEP, for the same order date; a failed predecessor holds the chain, with up to 5 reruns and a 7-day wait.app/scheduler/CardDemo.controlm:65-91Orchestration test re-derives the four edges from the Control-M XML; no job of the chain can be started by the orchestrator while its predecessor's condition is absent.

6.3 Restart / checkpoint semantics

There is no checkpoint or commit interval anywhere in the chain. CBACT04C REWRITEs each account as soon as the next account is reached (app/cbl/CBACT04C.cbl:194-196), so VSAM updates are permanent immediately and a failed run leaves accounts 1…n-1 charged and the rest not. The SYSTRAN generation is the only output that is rolled back on failure (DISP=(NEW,CATLG,DELETE), app/jcl/INTCALC.jcl:37). The program has no restart key, no "already processed" marker and no backout job in app/jcl; a cold rerun of INTCALC re-charges interest on every account that was already updated (FR-15). The transaction-id sequence restarts at 000001 on every run (WS-TRANID-SUFFIX VALUE 0, CBACT04C.cbl:173), so a second run with the same PARM produces duplicate keys that COMBTRAN's REPRO will reject. Safe recovery therefore means: restore ACCTDATA to its pre-run state (not provided by this chain — Q-06), delete the partial SYSTRAN generation if it was catalogued, and rerun from CLOSEFIL. COMBTRAN is restartable from STEP05R provided the TRANSACT master is in the state TRANBKP leaves it (empty, app/jcl/TRANBKP.jcl:37-67). WAITSTEP, CLOSEFIL and OPENFIL are stateless and rerunnable.
