1. Business purpose

In the Gartner reading of CardDemo (A-01), MonthlyInterestCalculation is the month-end finance-charge run of Gartner's client billing and receivables (order-to-cash) estate. Once a month it applies a late-payment finance charge to every client billing account's open receivable, split by revenue category, and records each charge as a billable event so that it appears on the client's monthly statement and in the receivables ledger.

In order: CLOSEFIL asks CICS region CICSAWSA to release the online billing files so batch has them to itself. INTCALC runs CBACT04C, which reads every balance by revenue category (TCATBALF) in billing-account order. For each balance it finds the finance-charge rate group in DISCGRP (keyed by the account's ACCT-GROUP-ID plus charge type and category), falls back to the DEFAULT group, and computes balance × rate ÷ 1200. Each charge becomes one system-generated billable event written to a new SYSTRAN generation, tagged with the account's seat ID from CARDXREF. The total is added to the billing account's open receivable in ACCTDAT (dataset ACCTDATA) and the current-cycle credit and debit totals are reset to zero. COMBTRAN then sorts the finance-charge events together with the latest backup of the billable-event master and reloads TRANSACT. WAITSTEP pauses 36 seconds and OPENFIL gives the files back to the online service, so associates can sign on again.

If the chain does not run, no finance charge is raised for the month, the cycle totals are not reset, and the client statement job CREASTMT and the billable-event screens show no finance-charge lines. If it runs twice, clients are charged twice: nothing in CBACT04C records that an account has already been charged (FR-15, Q-06). Either outcome misstates accounts receivable and finance-charge income in Gartner's 10-K / 10-Q, so the chain is in scope for SOX Section 404 ICFR testing. Note that the source charges every non-zero balance at the group rate; it has no aging or past-due test (Q-09).

Business capabilityHow this stream serves it
Late-payment finance charges on open receivablesPrices each revenue-category balance at the rate-group rate and adds the total to the billing account's open receivable (app/cbl/CBACT04C.cbl:462-470, :350-356).

Monthly billing-cycle closeSets ACCT-CURR-CYC-CREDIT and ACCT-CURR-CYC-DEBIT to zero when each account is updated (CBACT04C.cbl:353-354).
Rate governance (Order-to-Cash / Revenue Accounting)Rates are reference data, not code: DISCGRP is keyed by rate group, charge type and revenue category, with a mandatory DEFAULT group, so a rate group can be repriced without a code change (CBACT04C.cbl:415-460; app/cpy/CVTRA02Y.cpy:5-9). Rate changes are a SOX change-management control.
Online billing availabilityThe CICS billing files are closed before the batch update and reopened after it (app/jcl/CLOSEFIL.jcl:26-30, app/jcl/OPENFIL.jcl:26-30). Associates cannot view or adjust client accounts during that window.

CardDemo amounts carry no currency; this document reads them as USD (A-04). The source has no currency field or conversion.

Gating conditions: The chain is defined only in Control-M (app/scheduler/CardDemo.controlm:64-92). CLOSEFIL has no INCOND and posts MONTHLY-InterestCalculation-CLOSEFIL (:65-66). Every later job has one INCOND equal to its predecessor's OUTCOND for the same ODATE (AND_OR="A"), deletes it (SIGN="-") and adds its own (SIGN="+"): INTCALC :70-72, COMBTRAN :76-78, WAITSTEP :82-84, OPENFIL :88-89. OPENFIL adds no condition, so the network ends there. Control-M posts an OUTCOND only when a job ends OK and the XML has no ON/DO or MAXRC override, so an INTCALC U0999 abend or a non-zero COMBTRAN completion holds the chain with the files still closed. No JCL step has a COND= parameter (app/jcl/INTCALC.jcl:22, app/jcl/COMBTRAN.jcl:22,41), so COMBTRAN STEP10 runs even if SORT ended non-zero. TIMETO="23:00" is the latest submission time, not a deadline. No triggers, resources or cross-folder conditions are defined.
Other sources: CA-7 (app/scheduler/CardDemo.ca7) has no INTCALC or COMBTRAN entry. The dashed TRANSACT.BKUP(0) node is shown because COMBTRAN's SORTIN reads it, not because this folder schedules TRANBKP (Q-04). scripts/run_interest_calc.sh submits a different order (§3, Q-04).

FR-01Before any batch update the five CICS files TRANSACT, CCXREF, ACCTDAT, CXACAIX and USRSEC are closed in region CICSAWSA, and they are reopened after the chain. INTCALC is released only after the close, and OPENFIL only after WAITSTEP.app/jcl/CLOSEFIL.jcl:26-30; app/jcl/OPENFIL.jcl:26-30; app/scheduler/CardDemo.controlm:66,70,88While INTCALC and COMBTRAN run, no online transaction updates those files. FR-02INTCALC is one step, STEP15, running CBACT04C with a 10-character run-date PARM ('2022071800'). The program does not validate the PARM as a date; it uses it only as the prefix of generated event ids.app/jcl/INTCALC.jcl:22; app/cbl/CBACT04C.cbl:176-178,476-480With PARM 2022071800 the run produces ids 2022071800000001, 2022071800000002, …. The target rejects a run date that is not exactly 10 characters.
FR-03Open modes: TCATBALF, XREFFILE and DISCGRP INPUT; ACCTFILE I-O; TRANSACT (SYSTRAN) OUTPUT. Any open status other than 00 abends before any record is processed.CBACT04C.cbl:236,254,272,291,309With an input dataset missing or still held by CICS, the job abends U0999 with the matching ERROR OPENING … message; no account changes.
FR-04Balances are processed in TCATBALF key order (account id, type code, category code) by sequential read. Status 10 ends the run normally; any other non-00 status abends.CBACT04C.cbl:28-32,325-348Given balances for accounts 00000000011 and 00000000010, account 10's events are generated first. An I/O error logs ERROR READING TRANSACTION CATEGORY FILE and abends.
FR-05When the account id changes, the billing account (by ACCT-ID) and the seat link (by alternate key XREF-ACCT-ID) are read once and reused for all that account's categories, and the account's charge total is reset to zero.CBACT04C.cbl:194-205,372-376,393-398An account with three category balances causes exactly one ACCTFILE read and one XREFFILE read; all three events carry the same TRAN-CARD-NUM (seat ID).
FR-06The rate for a balance comes from the DISCGRP record keyed by (ACCT-GROUP-ID, balance type code, balance category code).CBACT04C.cbl:210-213,415-420; app/cpy/CVTRA02Y.cpy:6-8For a group with its own row for type 01, category 0001, that rate is used, not the DEFAULT rate.
FR-07If the group-specific DISCGRP record is missing (status 23), the program logs DISCLOSURE GROUP RECORD MISSING and TRY WITH DEFAULT GROUP CODE, then retries once with group id DEFAULT and the same type and category. If DEFAULT is also missing it abends with ERROR READING DEFAULT DISCLOSURE GROUP.CBACT04C.cbl:416-439,443-460Remove a group's row and the run uses DEFAULT for that type/category. Remove both and the job abends at that balance.
FR-08A rate of zero produces no event and leaves the account total unchanged. No fees are charged: 1400-COMPUTE-FEES is an empty stub (* To be implemented).CBACT04C.cbl:214-217,518-520A balance whose resolved rate is 0.00 produces no SYSTRAN record. The migrated job produces no fee events.
FR-09Monthly finance charge per category = TRAN-CAT-BAL × DIS-INT-RATE ÷ 1200, stored in WS-MONTHLY-INT PIC S9(09)V99 without ROUNDED, so it is truncated toward zero to two decimals. A non-zero rate on a zero balance still writes a 0.00 event; a credit (negative) balance gives a negative charge.CBACT04C.cbl:168,214,462-468Balance 1000.00 at rate 18.50 gives 15.41 (not 15.42); −1000.00 gives −15.41; 0.00 gives one 0.00 event.
FR-10The account's total charge is the sum of the per-category amounts after truncation.CBACT04C.cbl:467Three categories that each compute 0.333… produce three 0.33 events and an open-receivable increase of 0.99, not 1.00.
FR-11Each charge is one CVTRA05Y event: TRAN-ID = PARM + 6-digit sequence (from 000001, across the whole run); TRAN-TYPE-CD '01'; TRAN-CAT-CD = literal '05' into PIC 9(04), stored 0005; TRAN-SOURCE System; TRAN-DESC = Int. for a/c + 11-digit account id; amount = truncated charge; merchant id 0; merchant name, city, zip blank; card number = the account's x-ref seat ID.CBACT04C.cbl:173,473-495; app/cpy/CVTRA05Y.cpy:5-15The second event of the run has id <PARM>000002. An event for account 00000000010 has TRAN-DESC starting Int. for a/c 00000000010 and category 0005.
FR-12TRAN-ORIG-TS and TRAN-PROC-TS are both the same current clock time in DB2 format YYYY-MM-DD-HH.MM.SS.hh0000 (26 characters).CBACT04C.cbl:496-498,613-626Generated events match ^\d{4}-\d{2}-\d{2}-\d{2}\.\d{2}\.\d{2}\.\d{2}0000$, and ORIG equals PROC.

6.3 Restart / checkpoint semantics

No job in the chain takes a checkpoint or has a commit interval. CBACT04C rewrites each account as soon as the next account starts (app/cbl/CBACT04C.cbl:194-199,350-356) and keeps no record of which accounts are done, so the run is not idempotent. A cold rerun after a partial or complete INTCALC charges again every account already updated. The only safe recovery is: restore ACCTDATA (and TRANSACT, if COMBTRAN ran) from the pre-run backup, then rerun from INTCALC with the same PARM so event ids are reproduced. This folder has no backup or backout job for ACCTDATA (Q-06). COMBTRAN can be rerun alone only against an empty or freshly redefined TRANSACT KSDS, because REPRO has no REPLACE (Q-05). CLOSEFIL, WAITSTEP and OPENFIL are stateless. Control-M allows five reruns (MAXRERUN="5") and keeps an unrun order seven days (MAXWAIT="7") (app/scheduler/CardDemo.controlm:65). The target commits 50 accounts per chunk (InterestCalculationJobConfiguration.java:58,125) and keeps the event-id sequence in the step execution context (TranIdSequenceTest.resumesFromTheExecutionContextOnRestart), so a failed target run keeps the chunks committed before the failure and a Spring Batch restart resumes after them.
