1. Business purpose

Read as Gartner's client billing and receivables (order-to-cash) estate (assumption A-01), this chain is the bulk extract and reload of the order-to-cash master data. Gartner would use it to move the client book to another platform, such as a new ERP or billing platform (assumption A-03). CBEXPORT reads, in this order, every client organization and client contact (CUSTDAT), every client billing account (ACCTDAT: open receivable, approved client credit line, cash limit), every seat-to-account link (CCXREF), every billable event and payment (TRANSACT: Research subscription invoices, Conferences registrations, Consulting fees, client payments, credits and adjustments) and every research seat / license entitlement (CARDDAT: seat ID, subscription term end). It writes them all to one file, AWS.M2.CARDDEMO.EXPORT.DATA. Every record carries a one-byte type code, a run timestamp, a running sequence number and a fixed branch/region stamp (app/cbl/CBEXPORT.cbl:8-10, app/cbl/CBEXPORT.cbl:27-30, app/cpy/CVEXPORT.cpy:9-19). CBIMPORT reads that file, routes each record on its type byte and writes one flat file per entity in the estate's standard layouts. Records of an unknown type go to an error file (app/cbl/CBIMPORT.cbl:8-11, app/cbl/CBIMPORT.cbl:28-32).

The chain is run by hand. No CA-7 job, CA-7 trigger or Control-M folder names CBEXPORT, CBIMPORT or FTPJCLS, and the README batch run book (README.md:207-232) does not list them. The only real hand-off is the shared dataset: CBEXPORT writes AWS.M2.CARDDEMO.EXPORT.DATA (app/jcl/CBEXPORT.jcl:62-63) and CBIMPORT reads the same DSN (app/jcl/CBIMPORT.jcl:28-29). app/jcl/FTPJCL.JCL (job card FTPJCLS) PUTs an unrelated dataset, 'AWS.M2.CARDEMO.FTP.TEST', in ASCII mode (app/jcl/FTPJCL.JCL:36, :40). The verified chain is therefore CBEXPORT → CBIMPORT through AWS.M2.CARDDEMO.EXPORT.DATA, with FTPJCL a disconnected stand-alone step. A sequence that places FTPJCL between the two jobs is not supported by source (Q-06).

If the chain does not run, Gartner gets no copy of the client book, and a planned ERP or billing-platform cut-over cannot load its opening client, billing-account, seat and open-receivable balances. Daily posting of billable events, monthly client statements and late-payment finance charges are not affected. CBEXPORT opens the masters INPUT only (app/cbl/CBEXPORT.cbl:200-233), and CBIMPORT writes new sequential datasets, never the VSAM masters (app/cbl/CBIMPORT.cbl:43-71, app/jcl/CBIMPORT.jcl:33-60). Because the extract carries the open receivables and the billable-event history that feed Gartner's revenue and receivables reporting, its completeness and accuracy matter for SOX 404 data-conversion controls (NFR-08).

Gating conditions: There are no scheduler release rules. No CA-7 job or TRIGGERED JOBS entry names CBEXPORT, CBIMPORT or FTPJCLS (app/scheduler/CardDemo.ca7, 570 lines), and no Control-M INCOND/OUTCOND refers to them (app/scheduler/CardDemo.controlm, 92 lines). The operator owns the order, which follows the data dependency: CBIMPORT can only run after CBEXPORT has written AWS.M2.CARDDEMO.EXPORT.DATA. None of the three jobs has a COND= or IF/THEN. CBEXPORT STEP02 runs whatever STEP01 returns (app/jcl/CBEXPORT.jcl:24-43), and SET MAXCC = 0 hides the "cluster not found" from a first-run DELETE (app/jcl/CBEXPORT.jcl:27-28). Neither COBOL program sets RETURN-CODE. Success is GOBACK (app/cbl/CBEXPORT.cbl:158, app/cbl/CBIMPORT.cbl:171), and failure is an LE abend through CALL 'CEE3ABD' (app/cbl/CBEXPORT.cbl:579, app/cbl/CBIMPORT.cbl:484). FTPJCLS has no dataset dependency on either job (dashed lines). The chain is not wrapped in CLOSEFIL/OPENFIL (Q-07).

6.3 Restart / checkpoint semantics

Neither program has checkpoints, commit intervals or a restart key. Both are single-pass, read-to-end-of-file programs that open their outputs OUTPUT (app/cbl/CBEXPORT.cbl:235, app/cbl/CBIMPORT.cbl:205-245), so a restart is always a cold rerun from the first step. For CBEXPORT, the IDCAMS step guarantees a clean cluster (app/jcl/CBEXPORT.jcl:27-38). For CBIMPORT, the operator must first delete the cataloged outputs. No backout is needed because the chain never updates a master. A re-export gets a new run timestamp and restarts the sequence at 1 (app/cbl/CBEXPORT.cbl:123, :172-195). The target behaves differently: both Spring Batch steps are chunk-oriented (chunk 100) and restartable through the JobRepository. The writers save their byte position in the ExecutionContext and truncate back to it on reopen (docs/migration/streams/DataExportImport/DataExportImport_migration_plan.md §1).

Regulatory obligationsThe repo defines none; the following apply to a bulk extract of this content for Gartner. SOX Section 404 (ICFR): the migration load of open receivables and billable events is a key data-conversion control; access to run the jobs and to the file must be restricted and logged, and completeness / accuracy reconciliation evidence retained for Internal Audit / SOX PMO (NFR-08). CCPA / CPRA: SSN, government ID and account data are sensitive personal information of California contacts; use must be limited to the stated purpose and the receiving party bound by service-provider terms. Gartner records-retention policy (assumption): governs how long the extract and its SYSOUT evidence are kept and how they are destroyed (A-05, Q-15).
