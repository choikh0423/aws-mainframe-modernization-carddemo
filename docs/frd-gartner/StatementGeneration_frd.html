1. Business purpose

For Gartner this chain is the monthly client account statement run of the order-to-cash (client billing & receivables) estate (entity mapping is an assumption, Q-26). It produces one statement for every research seat / license entitlement in the seat-to-account link file (CARDXREF). CREASTMT takes the billable-event file (Research subscription invoices, Conferences registrations, Consulting fees, client payments and credits / adjustments held in AWS.M2.CARDDEMO.TRANSACT.VSAM.KSDS), re-keys it by seat ID (the legacy card number) so each seat's billable events sit together, and runs the business program CBSTM03A. For each seat, that program reads the client organization / client contact (CUSTDATA) and the client billing account (ACCTDATA), and writes the statement twice: as fixed 80-column plain text (STATEMNT.PS) and as 100-column HTML (STATEMNT.HTML) (app/jcl/CREASTMT.JCL:19-20, 79-96; app/cbl/CBSTM03A.CBL:39-47). TXT2PDF1 then renders the text statement to STATEMNT.PS.PDF with the TSO TXT2PDF utility (app/jcl/TXT2PDF1.JCL:24-39).

The statement program reads VSAM files that the online CICS region also serves, so the chain starts with CLOSEFIL and ends with OPENFIL. These run PGM=SDSF and issue CEMT SET FIL(...) CLO / OPE against region CICSAWSA (the README wrongly says IEFBR14; the JCL wins), with a timed WAITSTEP (COBSWAIT → MVSWAIT) before the re-open (app/jcl/CLOSEFIL.jcl:22-30; app/jcl/WAITSTEP.jcl:22-26; app/jcl/OPENFIL.jcl:22-30). While the files are closed, Gartner associates in Billing & Collections cannot work client billing accounts on the online screens that use them.

What CardDemo produces is narrower than a complete Gartner client statement: client contact name and address, billing account number, open receivable (current balance), a legacy credit-score field, an itemized list of billable events and payments, and a total. It has no statement date or period, approved client credit line, aging buckets, payment due date, finance charge line, revenue-line subtotals (Research / Conferences / Consulting) or Gartner remit-to details. This FRD specifies only what the source does and lists the gaps as open questions (Q-20 to Q-24).

If the chain does not run, the cycle gets no client statements in any format (text, HTML or PDF), Billing & Collections has no statement to send with dunning on overdue receivables, and the previous cycle's statement datasets stay catalogued until the next successful STEP030. If the chain starts but never reaches OPENFIL, the five CICS files stay closed and every online billing function that uses them fails until an operator re-opens them.

Gating conditions: The chain is a CA-7 trigger network, not a calendar schedule. Each job is released when its predecessor completes (TRIGGERED JOBS ... SCHID=030 QTM=0100 LEADTM=0000): CLOSEFIL→CREASTMT (app/scheduler/CardDemo.ca7:465-468), CREASTMT→TXT2PDF1 (:494-495), TXT2PDF1→WAITSTEP (:521-522) and WAITSTEP→OPENFIL (:524-527). Inside CREASTMT, STEP020, STEP030 and STEP040 carry COND=(0,NE), so they are bypassed as soon as any earlier step ends with RC ≠ 0 (CREASTMT.JCL:56, 66, 79). DELDEF01 and STEP010 have no COND. TXT2PDF1's only step carries COND=(0,NE) (TXT2PDF1.JCL:26), which has no effect on the first step of a job. The listing shows no RC requirement on the triggers, so the repo does not say whether a non-zero CREASTMT still releases TXT2PDF1 (Q-05). CREASTMT and TXT2PDF1 are flagged Y -- JOB MARKED AS MAINT ONLY (CardDemo.ca7:480, 507), so STATEMNT.PS is not a CA-7 dataset requirement for TXT2PDF1; only the job trigger orders them (Q-18).

Scheduler sources disagree on the daily chain; this FRD does not combine them: In CA-7, SCHID=030 also holds the daily chain CLOSEFIL→CBPAUP0J→POSTTRAN→WAITSTEP→OPENFIL (CardDemo.ca7:18-147; CardDemo.ca7 has no TRANBKP anywhere). The Control-M DAILY-TransactionBackup folder is CLOSEFIL→TRANBKP→WAITSTEP→OPENFIL with IN/OUT conditions and no POSTTRAN (app/scheduler/CardDemo.controlm:3-25). StatementGeneration exists only in CA-7: CardDemo.controlm has no CREASTMT or TXT2PDF1 job, so this chain has no Control-M IN/OUT conditions (Q-01, Q-02). The dotted edge is the trigger listed in the OPENFIL block at CardDemo.ca7:529-532 (CLOSEFIL, SCHID=031), while the full OPENFIL block says N -- COMP TRIGGERS OTHER JOBS (:138) (Q-04).

5. Functional requirements

FR-01The card-keyed work store is rebuilt from scratch before each run. TRXFL.SEQ and the TRXFL.VSAM.KSDS cluster are deleted. The condition code is then reset (SET MAXCC = 0), so a first run with nothing to delete still succeeds. Finally the KSDS is redefined with a 32-byte key at offset 0 and fixed 350-byte records.app/jcl/CREASTMT.JCL:22-39Running the job twice in a row, or on an estate where the work store does not exist, ends DELDEF01 with RC 0 and leaves a work store holding only the current TRANSACT data.
FR-02The work copy is TRANSACT sorted by card number ascending, then transaction id ascending, with each record re-laid as COSTM01: card number (TRANSACT bytes 263-278) at 1-16, TRANSACT bytes 1-262 at 17-278, TRANSACT bytes 279-328 at 279-328.app/jcl/CREASTMT.JCL:53-54; app/cpy/CVTRA05Y.cpy:4-18; app/cpy/COSTM01.CPY:20-36Each TRANSACT record yields exactly one work record keyed TRAN-CARD-NUM + TRAN-ID, whose bytes 17-278 equal source bytes 1-262; records are in (card, transaction id) order.

OUTREC builds 328 bytes into a 350-byte SORTOUT, and the sort product, not the JCL, fills bytes 329-350. 6.3 Restart / checkpoint semantics

The chain has no checkpoints, commits or restart keys. CREASTMT is a full rebuild. DELDEF01 deletes and redefines the work store (CREASTMT.JCL:22-39), STEP010 / STEP020 recreate it (:44-62), STEP030 deletes the previous outputs (:66-75), and STEP040 creates them anew with DISP=(NEW,CATLG,DELETE), so an abend leaves no partial statement files (:87-96). The only valid restart point is the top of CREASTMT; restarting at STEP040 needs STEP030 rerun first (section 6.2). CBSTM03A holds the whole transaction set in working storage and writes statements only after loading it (CBSTM03A.CBL:730-761, 818-853, 316-329), so there is no in-flight state to recover. All four VSAM inputs are opened INPUT (CBSTM03B.CBL:136, 160, 184, 209), so no backout job exists or is needed. CLOSEFIL, WAITSTEP and OPENFIL are stateless and idempotent. There is no "already ran this cycle" guard: a second run regenerates the same statements, and if they had already been sent, clients could get duplicates. In the target, rerun identity comes from the job parameters (the business run date) (docs/migration/CardDemo_target_state.md:98).
